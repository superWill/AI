# RK3506 / RK3568 摄像头与视觉能力分工方案

> 状态:与外部评审(2026-07-03)交叉对齐后的共识版。实测数据来自 BL412B(RK3568J)板端验证。
> 关联文档:[雄迈 IP 摄像头接入方案](xiongmai-ip-camera-integration-plan.md)(RK3506 侧接入细节)、
> [`driver-monitor/README.md`](../driver-monitor/README.md)(RK3568 侧实现状态与性能门禁)、
> [`driver-monitor/docs/adr/0001-vision-security-boundaries.md`](../driver-monitor/docs/adr/0001-vision-security-boundaries.md)(能力与权限边界)。
> 口径约定:置信度 HIGH/MED/LOW/UNKNOWN;实测数据标注日期;未实测的吞吐一律不承诺。

---

## 1. 核心结论

RK3506 不承担本地视频 AI;RK3568 承担单路完整安防视觉链路。两个平台定位不同,不是档位高低的
裁剪关系,而是"视频的元数据"与"视频本身"的分工。(置信度 HIGH)

| 平台 | 定位 | 最大合理范围 |
|---|---|---|
| RK3506 | 摄像头管理 + 事件转发节点 | 在线状态、配置、低频快照、告警联动、云端转发、按需临时中转 |
| RK3568 / BL412 | 本地视觉分析节点 | 人体检测、ROI、事件录像、断网补传;(待评估)跟踪/越线/停留/人数 |

硬件依据:
- RK3506:三核 Cortex-A7,官方规格未列 NPU/视频编解码单元。口径为**「无公开证据支持做本地
  视觉 AI」**,不断言"无硬解"。(置信度 HIGH)
- RK3568:四核 Cortex-A55 + ~1 TOPS NPU + MPP 硬解 + RGA。NPU 推理链路已板端实测验证
  (librknnrt 2.3.2 / Driver 0.9.8)。(置信度 HIGH,2026-07-03 实测)

## 2. RK3506 方案(基础版)

### 2.1 原则:连续视频流不经过 RK3506——不拉、不存、不转发

RK3506 本职是供热网关(采集/控制/HMI/MQTT 是不能抖的关键业务)。它碰的是视频的**元数据**,
分三个面:

**控制面(管摄像头,不看画面)**
- ONVIF/RTSP 短连接探活:确认在线/离线/鉴权失败/拉流失败(连上→确认响应→断开,非持续拉流)
- 摄像头配置下发/备份,状态变化告警

**事件面(收结论,不做分析)**
- 接收智能摄像头自身的人形/移动检测告警、干接点信号,盖时间戳转发云端
- 联动:消防/设备/区域告警时,通知云端或 HMI 调取对应摄像头

**快照面(低频单张图,不是流)**
- 定时(如每分钟)或告警触发时向摄像头请求单张 JPEG(几十 KB),供 HMI 显示 + 上云
- 一张图与一路流的资源消耗差约四个数量级

### 2.2 红线(置信度 HIGH)

- 不持续解码视频;不在 CPU 上跑 YOLO/RetinaFace/行为分析
- 不做多路本地录像、转码、7×24 视频上传
- 摄像头业务不进入热源控制或消防联动的关键实时进程
- 视频流不进 MQTT 遥测主题(只发状态/事件/快照地址/告警摘要)

### 2.3 唯一允许碰视频的形态:按需临时中转(置信度 MED)

云端需要实时看画面且摄像头无法直连时,RK3506 可建**短时哑转发**通道(RTP 包原样转发,
不解码不转码),看完即拆,设总带宽上限。持续 7×24 转发明确排除:一路子码流 ~1Mbps,
对 4G 回传站点的流量与带宽都不成立,且挤占遥测通道。

### 2.4 架构

```text
智能摄像头
  ├─ 摄像头自身:人形/移动检测、SD 卡录像
  ├─ RK3506:在线监测、事件接收、快照、HMI、云端转发
  └─ 云端:事件管理、录像调阅、进一步分析
```

若必须使用无检测能力的普通摄像头:加装 RK3568 视觉盒(见下),RK3506 仍只接收分析结果。

保护性资源配置起点(**GUESS,非验收指标,须压测修正**):摄像头管理服务限单核 ~10-15% CPU、
~32MB 内存、低磁盘 I/O 权重。

## 3. RK3568 / BL412 方案(增强版)

### 3.1 目标处理链

```text
主码流 ──不解码直接分段录像──→ 环形存储(P2a 离线逻辑已实现)
子码流 ──MPP硬解──→ [RGA预处理,未接] ──→ YOLOv8n人体检测 ──→ 跟踪/越线/停留/人数(未实现)
                                              └→ RetinaFace按需 ──→ 事件+图片+录像上传(P2c-a 离线逻辑已实现)
```

关键设计:
- **主码流全程不解码**:压缩数据按 GOP 边界直接分段存盘,VPU 与内存带宽零消耗;
  事件发生时按时间段关联录像(P2a 证据链:pin 段不淘汰、pre-roll 地板、两阶段确认)
- **AI 只吃子码流**:模型输入上限 640×640,解主码流(4 倍以上像素)做检测是纯浪费——
  解码/搬运/缩放开销 ~10 倍,精度零收益。高清价值走"子码流检测定位 → 主码流关联录像/抠图存证"
- **逐级过滤金字塔**:运动检测(纯 CPU,便宜)门控 → 人体确认(NPU,贵)→ K/M 时间持久性 + ROI
  → `person_observation` 事件。NPU 只在有动静时工作
- **事实与判断分离**(ADR-0001):视觉只产 `person_observation`(事实),永不产
  intrusion/confirmed(判断);不确定只升通知优先级,不改事件分类

### 3.2 能力现状(2026-07-03 板端实测对齐)

| 环节 | 状态 |
|---|---|
| MPP 硬解 + RTSP 取流 | ✅ 实测通过 |
| RetinaFace 320 单模型全链路 | ✅ ~8.3 fps,摄像头角度摆正后 90% 检出(112/124 帧) |
| YOLOv8n rk3568 INT8 模型 | ✅ 已转换(Docker + rknn-toolkit2 2.3.2,COCO 20 图校准)上板,load/init/inference 通;真机检出+吞吐待测 |
| ROI 区域过滤 | ✅ 已实现(`driver-monitor/src/roi/mask.py`,7 tests) |
| RGA 硬件预处理 | ❌ 未接——当前两条路径均 CPU 缩放(GStreamer videoscale / numpy) |
| 目标跟踪、越线、停留、人数 | ❌ 未实现,独立算法模块,受性能门禁约束(见 §5) |
| 双模型并发吞吐 | UNKNOWN——640 输入是 320 的 4 倍像素,8.3 fps 基线不可外推 |

> 基线注记:[实测 2026-07-03] RetinaFace 320×320 单模型链路(RTSP→MPP 硬解→预处理→NPU→状态机)
> ~8.3 FPS。该数据不代表 YOLOv8n、双模型并发或完整安防链路性能。

### 3.3 第一阶段可交付的分析能力

人体出现/离开、首帧强制保存、ROI 区域进出、检测到人脸时保存原始帧(机会性,非必达——
子码流上 10 米外人脸仅 ~10px,超出 RetinaFace 能力)、事件前 ~5s 至离开后 ~3-5s 录像关联、
断网本地缓存恢复补传。

### 3.4 第一阶段明确不做

人脸身份识别、跨摄像头 ReID、行为识别(打架/跌倒/吸烟)、多大模型并发、视频大模型/本地 NLU。

### 3.5 检测分辨率的适用边界(置信度 MED,待距离扫描实测)

640 输入检人的经验底线是目标在模型输入内 ≥20-30px 高:室内近中距(≤10-15m)富余;
远距/广角远端临界。人脸苛刻一个量级(脸 ≈ 人体高 1/7):疲劳场景(<1m)90% 检出已验证,
安防场景人脸只能机会性抓取。IR 夜间召回须单独实测(ADR F3),白天指标不可外推。
基准测试应含**距离扫描**(2/5/10/15m 各采一组)以确定真实有效检测距离。

## 4. 业务隔离措施(不影响采集/控制/HMI/通信)

- systemd 硬限制:CPUQuota、MemoryMax、IOWeight、自动重启(置信度 HIGH,COMMON)
- 采集/控制/MQTT 进程高调度优先级;视觉进程低 nice + 低 I/O 优先级
- 录像目录独立容量配额,不占满系统盘
- NPU/摄像头/录像故障只产健康告警,不阻塞控制循环
- 内存不足降级序:停人脸检测 → 降人体检测频率 → 停图片保存 → 停 AI;核心业务永不退出
- 云端上传限速 + 异步,不在视频线程同步等网络
- 起点参考值(**GUESS,须压测修正**):BL412(4GB)视觉服务 ~768MB 内存上限、~1-1.5 核配额

## 5. 路数与性能门禁

### 5.1 路数口径

"几路"须按环节分开回答,**不能用视频解码规格推导 AI 路数**(置信度 HIGH):

- VPU 解码预算(4K@60 ≈ 5 亿像素/s)对子码流(800×448@25 ≈ 900 万像素/s)不是瓶颈
- 真实瓶颈顺序:**NPU(单核,所有路排队)→ 内存带宽 → 磁盘写入 → CPU 缩放(RGA 未接期间)**
- 当前"主码流+子码流"对 VPU/NPU 只算**一路**(主码流不解码、不进模型)
- RK3568 先按 1 台设备 1 路完整链路设计;多路扩展走"多路录像、轮询 AI"
  (录像便宜可多路,NPU 检测预算分时间片,每路响应线性变慢,置信度 MED)
- 多路 AI 的具体数字 = YOLOv8n 单模型基准 fps ÷ 每路要求帧率,基准出来前任何路数承诺都是 GUESS

### 5.2 性能门禁(下一步唯一任务)

**先完成 YOLOv8n 单模型板端基准(真机检出率 + fps + CPU/内存/温度 + 距离扫描),
再决定是否接双模型与 RGA;基准出来前不新增分析算法模块(跟踪/越线/停留/人数)。**

后续验证顺序(每过一关解锁下一步):

1. YOLOv8n 640 单模型吞吐
2. YOLOv8n + RetinaFace 门控串行吞吐
3. CPU、NPU、内存、温度
4. 与正常业务共存时的控制周期抖动
5. 24 小时录像 + 推理 + 上传 soak

## 6. 第一阶段验收边界(2026-07-03 评审对齐)

**验收链:检测有人 → 保存第一帧 → 事件期间保存人脸代表帧 → 人离开后保存完整录像 → 可靠上传云端。**
完成这条链并现场验收通过,才能宣称"满足基础安防需求";在此之前的准确表述是
**「技术路线能够满足基础安防,代码尚未达到可交付状态」**。

对照验收链的实现缺口(按依赖序,✅=已具备的底座):

| 验收环节 | 底座 | 缺口 |
|---|---|---|
| 检测有人 | ✅ YOLOv8n 上板推理通 + 确认状态机 + ROI | 真实场景召回/吞吐基准(§5.2 门禁) |
| 保存第一帧 | ✅ 纯 stdlib PNG 编码器(`util/png_writer.py`) | 确认链未接帧保存——事件目前只挂录像段引用,不产图片 |
| 人脸代表帧 | ✅ RetinaFace 板上验证 | 安防链未接 RetinaFace 门控调用与选帧逻辑 |
| 完整录像 | ✅ 环形存储/事件→片段映射离线逻辑(P2a) | 真实分段录像(P2b splitmuxsink)未接实机 |
| 可靠上传 | ✅ outbox/分类/升级离线逻辑(P2c-a) | 真实云端接口(P2c-b paho-mqtt + P2c-c 平台契约)未接 |
| 整体 | — | RGA 预处理、24h 稳定性、IR 夜间召回(ADR F3) |

本方案**不承诺**(置信度 HIGH):身份识别;打架/跌倒/吸烟等行为识别;夜间/遮挡/远距离全场景
无漏检;多路同时高帧率 AI;替代消防或其他安全认证链路。

## 7. 产品档位

- **RK3506 基础版**:摄像头接入、状态、快照、智能摄像头事件转发、云端联动
- **RK3568 增强版**:人体检测、ROI、事件录像、可靠上传;跟踪/越线/停留/人数待门禁解锁

强行在 RK3506 上做本地人体 AI 会降低系统稳定性且投入产出不成立(置信度 HIGH);
RK3568 "完整链路可行"当前是架构推断(MED)而非压测结论——排期时不得把 UNKNOWN 当已知。
