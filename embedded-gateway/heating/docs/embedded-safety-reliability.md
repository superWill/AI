# 安全失效与可靠性(敢不敢上线的分水岭)

> 这一层 AI 帮不上多少——它只会把你要的功能写出来,**不会告诉你"这样写会烧锅炉"**。
> 安全是**责任,不只是技术**。配套:[常识清单 §9](embedded-common-sense.md) · [安全规则草案](safety/safety-rules-draft.md) · [踩坑清单](embedded-pitfalls.md)

---

## 0. 一条总原则:分层兜底,软件永远不是最后一道防线

```
机械限位/泄压阀  >  硬接线联锁  >  MCU/PLC 硬保护  >  软件逻辑  >  云端
   越靠左越可靠、越不依赖"程序没 bug"
```
- **真正危险的保护要往左做**(机械/硬接线),不要只写在软件里。
- 软件做的是"正常控制 + 第一道软保护",**它会崩、会卡、会有 bug**——所以它后面必须还有人兜底。
- 每写一个能动执行器的功能,问自己:**"它坏了会怎样?伤不伤人/设备?谁兜底?"**

## 1. 五件必须做的事(对应你的控制面板/网关)

### ① 限值校验 —— 任何写入前,卡边界
你的面板现在 `setpoint +/-`、`switch` 直接写 Modbus。**写之前必须过限值**,而且限值要在**靠近设备的一侧**强制(不能只靠 UI 里 clamp,因为配置可被改)。

```c
/* 控制写入的安全闸:面板 enqueue_write 之前、或采集线程发出之前都该过一遍 */
int safe_write(int addr, int reg, int val) {
    /* 硬编码的"硬限值"——不随 panel_config 改,这是最后的软防线 */
    if (reg == R_SET) {                 /* 目标温度寄存器 */
        if (val < 200 || val > 850)     /* 20.0~85.0℃,越界拒绝 */
            { log_block("setpoint out of hard range", val); return 0; }
    }
    if (reg == R_PUMP && val == 1) {     /* 启泵前的联锁(见②) */
        if (!interlock_ok_to_start_pump())
            { log_block("pump start blocked by interlock", val); return 0; }
    }
    enqueue_write(addr, reg, val);       /* 通过才真正下发 */
    return 1;
}
```
> 关键:**UI 限值是给人看的(防手滑),硬限值是给安全用的(防误配/防 bug)**。两道都要。

### ② 联锁(Interlock)—— 条件不满足就拒绝
"启泵前必须有水""超温必须停"这类**因果约束**。
```c
int interlock_ok_to_start_pump(void) {
    int supply_t = last_value(ADDR_SUPPLY, REG_TEMP);   /* 用最近采集值 */
    if (supply_t > 850) return 0;        /* 超温不许启泵 */
    if (water_pressure() < MIN_PRES) return 0;  /* 缺水不许启泵(防干转) */
    return 1;
}
```

### ③ 失联/超时 → 回退到安全默认
云端/上位机断了、设定值过期(`valid_until` 超时),**不能傻等,要回退本地安全策略**。
```
收到设定值 → 记 valid_until = now + N 秒
每个控制周期:if (now > valid_until) 用本地安全默认(如按室外温度的兜底曲线),别再用过期的远程值
```
(你的 `gateway_mqtt.py` 数据契约里已经有 `valid_until` 的影子——把它落到控制环。)

### ④ 看门狗 —— 程序卡死/跑飞,硬件把它复位
软件再小心也可能死锁/卡住。**硬件看门狗**:程序定时"喂狗",超时没喂 → 硬件自动复位整机。
```sh
# 喂狗:周期性写 /dev/watchdog(busybox 板子,放 init 自启)。停止喂狗 N 秒后硬复位。
# 见 safety-examples/watchdog_feed.sh
```
- 喂狗要放在**主循环健康的地方**,别放在一个独立的定时器线程里(那样主循环死了它还在喂,等于没用)。

### ⑤ 掉电保护 —— 写一半断电不能损坏
关键参数/配置**写一半突然断电**会损坏文件。用**原子写**:写临时文件 → `fsync` → `rename` 覆盖(rename 在同一文件系统上是原子的)。
```python
def save_atomic(path, data):
    tmp = path + ".tmp"
    with open(tmp, "w") as f:
        f.write(data); f.flush(); os.fsync(f.fileno())
    os.replace(tmp, path)           # 原子替换:要么旧的要么新的,不会半截
```
> 你的配置后台 `config_server.py` 现在是直接 `json.dump` 覆盖——改成原子写,断电就不会把 `panel_config.json` 写坏。

## 2. 设计时的自检三问(每加一个控制功能都问)
1. **它坏了会怎样?**——执行器卡在最大、传感器读错、网络断了,分别什么后果?
2. **谁兜底?**——这个危险有没有机械/硬接线在软件之外挡着?
3. **失效是否安全?**——断电/断网/崩溃时,系统停在**安全态**还是危险态?(阀门掉电该开还是该关?泵该停。)

## 3. 上线前安全检查清单
- [ ] 所有**能动执行器**的控制,写入前过**硬限值**(不只 UI clamp)。
- [ ] 危险动作有**联锁**(启泵防干转、超温停)。
- [ ] 远程/上位机设定值有**超时回退**到本地安全默认。
- [ ] **硬件看门狗**已启用,喂狗点在主循环健康处。
- [ ] 关键配置/参数**原子写**(掉电不坏)。
- [ ] 失效方向安全(掉电/断网→执行器停在安全态)。
- [ ] 真正致命的保护**做在软件之外**(机械/硬接线/独立硬保护)。
- [ ] 配置后台/控制口有**鉴权**(别让谁都能远程改设定值)。

## 4. 落到你现在的系统(具体改哪)
| 改动点 | 现状 | 要做 |
|---|---|---|
| 面板控制写入(main.c) | `enqueue_write` 直接发 | 包一层 `safe_write` 硬限值+联锁 |
| 配置保存(config_server.py) | 直接覆盖 | 改**原子写** + 加鉴权 |
| 网关控制环 | 无超时回退 | 远程设定值带 `valid_until`,过期回退 |
| 整机 | 仅软件崩溃重启 | 加 `/dev/watchdog` 硬看门狗 |

> 一句话:**先把"控制写入硬限值 + 看门狗 + 原子写配置"这三样补上,就从"能跑"迈到了"敢上线"。**
