# 设备接入的两种路径 · 边缘加设备 vs 云端加设备

> 用途：界定"往系统里加一个现场设备"在**边缘(RK3506)** 和 **云端(后管)** 两条路径下分别怎么走、各自可行性、以及不可逾越的安全边界。
> 版本：2026-06-23（草案）
> 关联：[运行时激活回滚设计](runtime-activate-reload-design.md) · [设备模板设计](../point-table/device-template-design-notes.md) · [MQTT 协议草案](../protocols/mqtt-protocol-draft.md) · [数据接口契约](../protocols/upstream-platform-data-contract.md) · [云后管方案](../product/heating-cloud-admin-spec.md)

## 0. 设计原则

> **草稿在谁手上写可以变；"安全地把草稿变成运行配置"这件事，永远在网关本地完成。**

加设备本质是**边缘关注点**（接的是现场 Modbus/firebus 的寄存器）。云端可以参与"编排/下发"，但校验、激活、安全、回滚必须落在网关。云不可达时，加设备失败**不得影响在跑的站**。

---

## 1. 先分清两层"设备"

| 层 | 指什么 | 标识 | 谁的台账 |
|---|---|---|---|
| **站点/网关** | 一台 RK3506 = 一个换热站 | `device_id`（stn-001） | 云端 `station` 表（首报自动注册） |
| **现场设备/点位** | 挂在网关下的热量表、变频器、AI/DI 模块、MCU | `point_id`（pri_supply_temp…） | 网关 `config_draft.json` 的 `devices[]` |

本文说的"加设备"= **加现场设备/点位**（下层）。加站点是网关首次上报时云端自动发生的，不在此列。

---

## 2. 现有的本地配置流水线（事实基础）

网关已具备一条**纯本地、零依赖**的配置闭环：

```
config_draft.json ──compiler.py──► 编译产物 ──loader.py──► app.py 运行配置 ──► 激活(带回滚)
(devices[] 草稿)   (校验+编译,纯函数)  (point_registry/      (适配回内核)      (runtime-activate-
                                       poll_plan/                              reload-design)
                                       safety_policy)
```

- `devices[]` 每条选一个**协议模板**：`heat_meter_modbus` / `energy_meter_modbus` / `vfd_modbus` / `rs485_8ai_modbus` / `rs485_8di_modbus` / `private_mcu` …，填 Modbus 地址/寄存器，映射成 `point_id`。
- `compiler.py`：**编译期就做安全校验**（schema 约束 + x-compiler-constraints），零依赖、可在 RK3506 上跑。
- 激活带**运行时回滚**（见 [runtime-activate-reload-design](runtime-activate-reload-design.md)）。

→ **"加设备" = 往 `config_draft.json` 加一条 device → 编译 → 激活。** 两条路径只是"谁来写这条草稿"。

---

## 3. 路径①：边缘加设备（不联云）✅

```
现场人员/工程 ──编辑 config_draft.json──► compiler.py 校验 ──► loader.py ──► 激活(回滚兜底)
                                                                              │
                                                                       网关开始采集新设备
```

- 全程**在网关本地、零依赖、不碰云**。断网照做。这是**边缘自治**的体现，也是设计本意。
- 可行性：**现成能力，直接可用。**

> 唯一附带成本：本地新加点位的**语义**（中文名/单位/类型）云端一开始不认识。但只要网关把新 `point_id` 的遥测往上发，云端 `ingest_worker` 照样落库；云端 `metric_def` 补一条标签即可（见路径②-A 的"云端发现"）。**数据不丢，语义需补。**

---

## 4. 路径②：云端加设备（联云）✅ —— 两种做法

### A. 边缘登记 + 云端发现（推荐先做，低风险）
设备仍在**边缘**定义；网关把设备/点位清单**上报**，云端后管**自动出现**新设备，运营在后管补语义元数据。

```
网关(本地加设备) ──上报设备/点位清单──► 云端后管自动发现 ──► 运营补语义(标签/单位/类型)
```
- **对称于现在站点的自动注册**（首报建 `station`），扩展到"设备/点位"只是小改动。
- 不改变"配置在边缘"的事实，风险最低。

### B. 云端下发草稿（cloud-down provisioning，规模化时做）
在后管里编辑 `config_draft`（选模板、填寄存器）→ 经下行通道推到网关 → **网关本地跑同一个 `compiler.py` 校验 → 激活 → 回滚兜底 → 回传结果**。

```
后管编辑草稿 ──下行下发──► 网关 compiler 校验 ──► 激活/回滚 ──► command_reply 回传
   (云端编排)              (本地安全把关)          (本地)         (上行)
```
- **可行且不贵**：网关已有"安全地应用一份草稿"的全套流水线，云端只负责"写草稿 + 推下去"。
- 要扩的部分：把下行从现在的"只发设定值（`property/set`）"扩成"能发整份点表草稿"（新增一个下行 topic + command_type，沿用契约的命令应答模型）。
- 价值：在办公室远程给几百个站配设备，不用逐台现场操作。

---

## 5. 不可逾越的安全边界 🔒

无论谁写草稿，三条铁律不破：

1. **校验与激活只在网关本地跑** —— 云能写草稿，**不能绕过** `compiler.py` 校验和 `safety_policy` 严格模式。
2. **坏草稿网关必须能拒绝/回滚** —— 复用现有运行时激活回滚，活配置永不被破坏。
3. **云不可达时网关用已激活配置照常跑** —— 加设备失败属"编排失败"，不影响在跑的站与本地控制/安全。

---

## 6. 推荐演进路线（两段式）

| 阶段 | 做什么 | 风险 |
|---|---|---|
| 现在 | 路径① 本地加设备（已具备）+ 路径②-A 云端发现（小改 ingest/后管） | 低 |
| 规模化后 | 路径②-B 云端下发草稿（扩下行 + 复用激活回滚闭环） | 中（下行配置链路 + 安全把关） |

一句话：**先让"边缘加、云端看"，要远程批量配站时再做"云端编排、边缘执行"。**
