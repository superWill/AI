## 引言：为什么要从 0 和 1 推导

在单片机开发过程之中，通信几乎是绕不开的一部分。

我们需要让 MCU 和传感器进行通信，需要让 MCU 和 Flash 交换数据，也需要让两块控制板之间传递状态，甚至还可能需要让几十个节点在几十米乃至上百米的线缆上进行通信。

于是我们会接触到 UART、SPI、I²C、RS-485、CAN 等各种各样的接口。

很多人在刚开始学习这些通信接口的时候，会采用一种比较零散的方式：

- UART 有 TX 和 RX；
- SPI 有 SCLK、MOSI、MISO 和 CS；
- I²C 有 SCL 和 SDA；
- RS-485 使用 A、B 差分线；
- CAN 有 CANH 和 CANL。

紧接着再去记波特率、起始位、停止位、CPOL、CPHA、ACK、NACK、显性位、隐性位……最后往往形成了这样一种状况：每一种协议似乎都学过，但是一旦让自己去设计一套新的通信链路，却不知道究竟为什么要采用这些机制。

实际上，MCU 通信从最底层来看，所有通信最终都只是在解决一个问题：

> 如何让一颗芯片内部的 0 和 1，可靠地跨越物理空间，到达另外一颗芯片内部，并且重新还原成为有意义的数据。

但是从这个问题继续往下推，我们很快就会遇到一连串新的问题：

- 接收端什么时候读取信号？
- 多个 Bit 如何区分边界？
- 一组数据从哪里开始、到哪里结束？
- 总线上有多个设备的时候，数据究竟发给谁？
- 多个设备同时发送怎么办？
- 线路受到干扰以后，如何判断数据错了？
- 数据量非常大的时候，CPU 难道要一直盯着通信接口搬运每一个字节吗？

正是这些问题，一层一层推动了各种通信机制的出现。这也是写本文的初衷，本文会从最底层的 0 和 1 开始，一步一步推导 MCU 的数据传输方式。最终我们会建立这样一条完整链路：

```
电压
 ↓
Bit
 ↓
Byte
 ↓
Frame
 ↓
Packet
 ↓
Message
 ↓
完整通信系统
```

当这条链路真正打通以后，再去理解 USB、Ethernet、Bluetooth、Wi-Fi 等更加复杂的通信系统，其实也依旧是在解决相似的问题，只不过层次更多、规模更大而已。

## 前言、MCU 之间，为什么不能"直接说话"？

### 0.1 MCU 的世界里，所有数据最终都是 0 和 1

通信的本质其实非常简单：

> 就是把发送端的一串 0 和 1，在接收端重新恢复出来。

问题在于，内存里面的 0 和 1 只是逻辑概念。另外一颗 MCU 并不能直接看到这块内存。我们必须想办法把这些逻辑数据变成可以跨越芯片边界传播的物理信号。

▷ 图：内存中的逻辑 0/1 与芯片外物理信号世界的对照示意（见原始 mhtml）

### 0.2 数据的物理跨越：内存变量如何变成引脚电平

假设 MCU A 中有：

```c
uint8_t data = 0x5A;
```

其二进制形式为：

```
0x5A = 0101 1010
```

如果要把它发送给 MCU B，至少需要经历下面的过程：

```
MCU A 内存中的数据
        ↓
通信外设或软件逻辑
        ↓
把 Bit 转换为引脚电平
        ↓
PCB 走线或者线缆
        ↓
MCU B 输入引脚检测电平
        ↓
通信外设重新恢复 Bit
        ↓
组合成为 Byte
        ↓
写入 MCU B 内存
```

这里已经出现了两个世界。

一个是软件世界：变量、Byte、Bit、数据结构。

另外一个是物理世界：电压、电流、边沿、时钟、阻抗、噪声。

通信协议真正做的事情，就是建立这两个世界之间的桥梁。

▷ 图：软件世界与物理世界之间由通信协议架桥的示意（见原始 mhtml）

### 0.3 两颗 MCU 通信必须解决的七个核心问题

假设现在没有 UART，没有 SPI，没有 I²C，也没有任何现成协议。只给我们两颗 MCU 和若干根导线。要让它们可靠地交换数据，至少需要解决七个核心问题。

1. **Bit 怎么表示？** 是高电平表示 1、低电平表示 0，还是反过来？
2. **什么时候读取 Bit？** 信号在不停变化，接收端必须知道应该在哪一个时刻采样。
3. **一组数据从哪里开始，到哪里结束？** 连续的一串 Bit 如果没有边界，就不知道哪 8 位属于一个 Byte，也不知道哪几个 Byte 属于一条完整消息。
4. **数据发给谁？** 如果总线上挂着很多设备，就必须解决寻址问题。
5. **谁可以发送？** 如果两个设备同时驱动总线，而且输出不同电平，就可能产生冲突。
6. **如何知道数据有没有传错？** 线路可能受到干扰，Bit 可能翻转，因此需要校验、确认甚至重传。
7. **如何提高传输效率？** 如果 CPU 每发送一个字节都要一直等待，那么高速通信很快就会拖垮处理器。

后面我们会看到：UART、SPI、I²C、CAN 以及 DMA，本质上都可以看作对这些问题的不同解决方案。

▷ 图：七个核心通信问题的总览图（见原始 mhtml）

## 一、从 0 和 1 到电压：MCU 如何把数据变成真实电信号

### 1.1 为什么数字系统选择 0 和 1

自然界中的电压本身是连续变化的。比如一根线上可能出现：

```
0V
0.1V
0.8V
1.7V
2.4V
3.3V
```

理论上，我们可以规定：

```
0.3V 表示数字0
0.6V 表示数字1
0.9V 表示数字2
1.2V 表示数字3
……
```

这样一根线似乎一次就可以表示很多状态。可是问题马上出现了。线路中存在：

- 电源波动；
- 电磁干扰；
- PCB 串扰；
- 温度变化；
- 器件工艺偏差；
- 接地噪声。

本来是 1.2V 的信号，到接收端可能变成 1.08V。那么它到底应该识别成为哪个数字？

数字电路采用 0 和 1 的一个重要原因，就是可以留出较大的噪声裕量。我们不要求电压刚好等于 0V 或 3.3V，而是只需要处于某个有效范围。

▷ 图：多电平细分 vs 二值电平的噪声裕量对比（见原始 mhtml）

### 1.2 Bit、Byte、Word 与十六进制的数据本质

一个 Bit 只能表示 `0` 或 `1`。

两个 Bit 可以表示：

```
00
01
10
11
```

也就是 4 种状态。8 个 Bit 可以表示 `2^8 = 256` 种状态。这就是一个 Byte。例如 `0101 1010`。

直接观察二进制比较困难，因此工程中经常使用十六进制：

```
0101 = 5
1010 = A
```

于是 `0101 1010 = 0x5A`。

十六进制并不是另一种数据。它只是二进制更加适合人阅读的一种表达方式。

Word 则与 CPU 架构以及具体上下文有关。在某些 MCU 中 `Word = 16 bit`，在另外一些系统中可能把 `Word = 32 bit`。因此实际通信协议中最好直接使用：

```c
uint8_t
uint16_t
uint32_t
```

这类明确位宽的类型，而不是依赖模糊的 Word 含义。

▷ 图：Bit / Byte / Word / 十六进制的层次关系（见原始 mhtml）

### 1.3 0 和 1 如何对应真实电压：VIH、VIL 与逻辑电平

假设一颗 MCU 工作在 3.3V。很多初学者会简单认为 `0V = 0`、`3.3V = 1`。

实际情况更加复杂。数字输入引脚通常会定义两个重要参数：

```
VIL：能够保证识别为低电平的最大输入电压
VIH：能够保证识别为高电平的最小输入电压
```

例如某个器件可能规定：

```
Vin ≤ VIL  → 一定识别为0
Vin ≥ VIH  → 一定识别为1
```

而中间区域 `VIL < Vin < VIH` 通常属于不确定区域。

具体数值必须查阅芯片数据手册，不能认为所有 3.3V MCU 都具备完全相同的门限。这也是为什么不同电压域之间进行通信时，需要检查：

- 1.8V 输入能否识别 3.3V 高电平；
- 3.3V 输入是否可以直接承受 5V；
- 是否需要电平转换器；
- 输入是否 5V tolerant。

通信首先是电气问题，其次才是协议问题。

▷ 图：VIL / VIH 门限与不确定区域的电平划分图（见原始 mhtml）

### 1.4 GPIO：理解 MCU 数字输入输出的第一入口

GPIO 是 General Purpose Input/Output，也就是通用输入输出。它可以工作成为：输入、输出、复用功能、模拟功能。

如果配置成为输出，就可以通过寄存器或者 HAL 接口控制引脚：

```c
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_0, GPIO_PIN_SET);
```

引脚输出高电平。再执行：

```c
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_0, GPIO_PIN_RESET);
```

引脚输出低电平。另外一颗 MCU 把相连引脚配置为输入：

```c
state = HAL_GPIO_ReadPin(GPIOB, GPIO_PIN_0);
```

这样其实已经完成了最基础的一次数字通信。MCU A 输出 1，MCU B 读取 1。MCU A 输出 0，MCU B 读取 0。这就是所有数字通信协议最底层的基础。

▷ 图：两颗 MCU 通过 GPIO 输出/输入完成一次最基础的电平传递（见原始 mhtml）

### 1.5 推挽、开漏、上拉、下拉到底在解决什么

推挽输出可以主动输出高电平，也可以主动输出低电平。可以理解成为：

```
输出1：主动连接到VCC
输出0：主动连接到GND
```

优点是：

- 上升快；
- 下降快；
- 驱动能力强；
- 适合高速信号。

但是如果两个推挽输出直接连接到一起，一个输出高、一个输出低，就相当于一边强拉 VCC，一边强拉 GND，可能产生较大短路电流。因此推挽非常适合点对点连接，但是不适合很多设备随意共线输出。

开漏输出通常只能主动拉低。输出高电平时并不主动输出高，而是让引脚进入高阻状态。这时候依靠外部上拉电阻把线路拉高。于是：

```
任何设备拉低 → 总线为0
所有设备释放 → 总线为1
```

这种特性非常适合多设备共享同一根线。I²C 之所以大量使用开漏结构，后面就会看到原因。

输入引脚如果悬空，可能由于噪声随机识别为 0 或 1。因此可以使用：

```
上拉：默认保持高
下拉：默认保持低
```

它们给线路提供一个确定的默认状态。

▷ 图：推挽输出与开漏+上拉电阻的电路结构对比（见原始 mhtml）

### 1.6 第一个通信问题：有了高低电平，如何传递有效数据

现在我们已经可以发送一个 Bit，例如高电平 = 1、低电平 = 0。

但是马上又出现一个新问题。如果要发送 `01011010`，是不是只需要让一根线依次变化：

```
0 → 1 → 0 → 1 → 1 → 0 → 1 → 0
```

看起来似乎可以。可是接收端会问：

- 每一个电平保持多久？
- 我什么时候应该读取？
- 连续两个 1 的时候，线路根本不变化，我怎么知道这是两个 Bit，而不是一个长时间的 1？

于是通信从"电平表示"进入到了 **"时间组织"** 的问题。

▷ 图：连续相同电平导致 Bit 边界无法辨认的波形示意（见原始 mhtml）

## 二、最原始的通信：一根导线如何传递一个 Bit

### 2.1 最简单的双 MCU 单线通信模型

假设两颗 MCU 共地，并连接一根 DATA 线：

```
MCU A                    MCU B
 GPIO_OUT ───────────── GPIO_IN
 GND      ───────────── GND
```

A 输出 `1`，B 就能读取 `1`。A 输出 `0`，B 就能读取 `0`。

这已经是一种最简单的单向通信。

▷ 图：双 MCU 共地单线连接的最小通信模型（见原始 mhtml）

### 2.2 单 Bit 通信：状态信号与握手信号

事实上，在真实系统中，大量控制信号本身就是这种单 Bit 通信。例如：

```
READY
BUSY
RESET
ENABLE
FAULT
INTERRUPT
DATA_VALID
```

假设 MCU A 完成数据准备以后，把 READY 拉高。MCU B 检测到 READY 后开始处理。这实际上就是一种握手。

甚至很多复杂高速总线，最底层也依然会存在类似：

```
Valid
Ready
Request
Acknowledge
```

这类单 Bit 控制信号。

▷ 图：READY/BUSY 类单 Bit 握手信号的时序示意（见原始 mhtml）

### 2.3 从单 Bit 到多 Bit：数据量增加带来的新问题

如果只传递"开 / 关"、"忙 / 空闲"、"成功 / 失败"，一根线就够了。

但是我们要传递 `0x5A`，需要 8 个 Bit。于是最简单的思路是：

> 那就直接用 8 根线。

这就是并行通信。

▷ 图：一根线传一个 Bit 到八根线传一个 Byte 的过渡示意（见原始 mhtml）

### 2.4 通信架构第一次分叉：并行传输与串行传输

假设要传输 `10110110`。

**并行方式**：使用 8 根线：

```
D7 = 1
D6 = 0
D5 = 1
D4 = 1
D3 = 0
D2 = 1
D1 = 1
D0 = 0
```

一次就可以传输 8 Bit。

**串行方式**：只使用一根 DATA：

```
1 → 0 → 1 → 1 → 0 → 1 → 1 → 0
```

需要分成多个时间片逐 Bit 发送。于是出现了最经典的工程取舍：

```
空间换时间
或者
时间换空间
```

并行通信使用更多导线，换取一次传输更多 Bit。串行通信减少导线，代价是需要按照时间顺序组织数据。

▷ 图：并行 8 线同时传输与串行单线分时传输的对比（见原始 mhtml）

### 2.5 并行与串行的核心取舍：速度、引脚、距离与复杂度

并行通信的直观优势是"一次时钟传很多 Bit"，但是需要大量引脚。例如 16 位数据总线可能需要：

```
16根数据线
若干地址线
读写控制线
片选
时钟
```

对于一颗只有几十个 GPIO 的 MCU，这个成本非常高。

串行通信只需要少量信号线，更容易：

- 节省引脚；
- 降低连接器成本；
- 降低 PCB 布线复杂度；
- 延长通信距离。

但是串行通信又引入了新的问题：

> 数据都在同一根线上排队发送，接收端究竟如何确定每一个 Bit 的位置？

这个问题会推动 UART 和 SPI 的出现。

▷ 图：并行与串行在引脚数 / 速度 / 距离 / 复杂度上的取舍矩阵（见原始 mhtml）

## 三、从并行到串行：多个 Bit 到底应该怎么传

### 3.1 8 位并行总线的基本工作原理

假设 MCU A 与 MCU B 之间连接 `D0～D7` 和 `CLK`。

发送端先把 `0x5A` 放到 D0～D7。然后产生一个时钟边沿：

```
D7..D0 = 01011010
CLK     = ↑
```

接收端在这个时刻同时读取 8 根数据线。一次就能够获得一个 Byte。

▷ 图：8 位并行总线在时钟边沿一次锁存一个 Byte 的时序（见原始 mhtml）

### 3.2 并行通信为什么简单而高效

并行通信最大的优点是直接。8 位总线一次传一个 Byte。16 位总线一次传 16 Bit。32 位总线一次传 32 Bit。

很多 MCU 的外部存储接口正是采用这种方式。例如访问异步 SRAM 时，CPU 可以同时输出：地址、数据、读写控制信号。因此协议逻辑简单，而且单次访问效率非常高。

▷ 图：MCU 并行访问外部 SRAM 的地址/数据/控制线示意（见原始 mhtml）

### 3.3 GPIO 占用、PCB 布线与硬件成本问题

问题在于，引脚数量会快速膨胀。例如一个 16 位外部存储接口可能需要：

```
16根数据线
20多根地址线
若干控制线
```

加起来很容易超过 40 根。这意味着：

- MCU 封装需要更多 Pin；
- PCB 需要更多走线；
- 连接器成本增加；
- 跨板传输非常困难。

于是串行化开始变得有吸引力。

▷ 图：并行接口引脚数膨胀对封装与 PCB 布线的影响（见原始 mhtml）

### 3.4 高速并行通信的时序偏斜、串扰与信号完整性

当速度逐渐提高以后，并行总线还会遇到一个更麻烦的问题：

> 这些线能够不能同时到达？

假设发送端理论上同时改变 8 根数据线。实际 PCB 中：

```
D0 长度 = 30mm
D1 长度 = 42mm
D2 长度 = 51mm
……
```

每一根线传播时间不同。于是接收端看到的 8 Bit 并不是绝对同时稳定。这就是 Skew，也就是时序偏斜。速度越高，一个 Bit 的有效时间越短，线路之间微小的延迟差就越严重。

与此同时，还会出现：

- 串扰；
- 反射；
- 过冲；
- 下冲；
- EMI；
- 同时翻转噪声。

因此高速并行总线往往需要：

- 等长；
- 阻抗控制；
- 终端匹配；
- 更严格的时序设计。

▷ 图：走线长度差引起的时序偏斜（Skew）波形示意（见原始 mhtml）

### 3.5 为什么越来越多的数据传输开始串行化

高速串行通信看似每次只发送少数 Bit，但可以把串行速率做得非常高。更重要的是，串行化可以显著减少需要保持同步的数据线数量。

这也是为什么现代高速接口大量采用串行方式，例如：

```
PCIe
USB
SATA
Ethernet
MIPI
SerDes
```

它们的物理结构都越来越倾向于"少量高速差分通道"，而不是"几十根并行数据线"。

▷ 图：现代高速接口从多线并行走向少量高速差分通道的趋势（见原始 mhtml）

### 3.6 并行通信在 FMC、SDRAM、RGB LCD 中的留存场景

串行通信并没有完全取代并行通信。在板内短距离、吞吐量高、接口结构明确的场景，并行总线依旧具备价值。例如：

**FMC/FSMC**：MCU 使用并行总线访问：

```
SRAM
NOR Flash
LCD Controller
FPGA
```

**SDRAM**：SDRAM 通常拥有：

```
地址线
数据线
Bank地址
时钟
控制信号
```

属于高速并行接口。

**RGB LCD**：传统 RGB LCD 可能使用：

```
R[7:0]
G[7:0]
B[7:0]
PCLK
HSYNC
VSYNC
DE
```

每一个像素时钟并行传输 RGB 数据。

因此并行和串行并不是谁绝对更先进，而是根据具体场景进行工程选择。

▷ 图：FMC / SDRAM / RGB LCD 等并行接口的留存场景（见原始 mhtml）

### 3.7 串行通信的新难题：接收端怎么识别每一个 Bit

现在我们决定节省引脚，只保留一根 DATA。发送 `0xF0`，假设高位先发送 `11110000`，线路可能呈现：

```
HIGH ────────────────┐
                     │
LOW                  └────────────────
```

接收端看到前面持续一段高电平。它必须知道：

```
这里究竟是4个1
还是3个1
还是5个1？
```

这说明串行通信最重要的问题不是"有没有数据线"，而是：

> 如何建立时间基准。

## 四、串行通信第一难题：接收端到底什么时候读数据

### 4.1 Byte 如何被拆解成连续的 Bit 流

假设发送 `0xA5`，二进制为 `1010 0101`。

串行发送必须规定发送顺序。例如低位先发送：

```
Bit0 → Bit7

1 0 1 0 0 1 0 1
```

或者高位先发送：

```
Bit7 → Bit0

1 0 1 0 0 1 0 1
```

这个例子刚好对称。换成 `0x96 = 1001 0110`：

低位先发送：`0 1 1 0 1 0 0 1`
高位先发送：`1 0 0 1 0 1 1 0`

因此协议必须明确 **MSB First 还是 LSB First**。

▷ 图：MSB First 与 LSB First 两种发送顺序的对比（见原始 mhtml）

### 4.2 只有一根 DATA 线为什么无法可靠识别数据

假设规定每个 Bit 保持 `10us`。发送端输出：

```
Bit0   0～10us
Bit1   10～20us
Bit2   20～30us
……
```

接收端必须用自己的定时器在对应时刻采样。问题是两颗 MCU 的时钟不可能完全一致。发送端晶振可能存在 `+0.5%` 误差，接收端可能存在 `-0.5%` 误差。

随着连续 Bit 数量增加，采样点会逐渐漂移。因此串行通信必须解决：

> 发送端和接收端如何建立共同的时间尺度？

▷ 图：双方晶振误差累积导致采样点漂移的示意（见原始 mhtml）

### 4.3 串行通信的第一核心问题：采样时刻与位同步

接收端不能随便读。理想情况下，应当在一个 Bit 最稳定的位置进行采样，例如 Bit 中间。假设 `Bit Time = 10us`，那么可以在：

```
5us
15us
25us
35us
……
```

附近采样。问题在于，第一个 5us 从哪里开始计算？也就是说，除了知道 Bit 多长以外，还必须知道"第一个 Bit 从什么时候开始"。这就是同步问题。

▷ 图：在 Bit 中间采样与起始时刻未知的位同步问题（见原始 mhtml）

### 4.4 两条技术路线：异步通信与同步通信

解决同步问题，最直接可以产生两条路线。

**路线一：不发送时钟。** 双方提前约定"每秒发送多少 Bit"。发送端和接收端各自依靠本地时钟计时。为了防止长期漂移，每隔一小段数据重新进行一次同步。这就是异步串行通信的基本思路。UART 就属于这一类。

**路线二：直接发送时钟。** 既然接收端不知道什么时候读，那么发送端直接再给一根 CLK。例如：

```
CLK上升沿到了
→ 现在读取DATA
```

这就是同步通信。SPI 就是典型代表。

因此 UART 和 SPI 的根本区别之一其实不是"接口长得不一样"，而是：

> 一个依靠事先约定时间，一个把时间基准直接发送过去。

▷ 图：异步（约定波特率）与同步（随路时钟）两条路线的分叉图（见原始 mhtml）

### 4.5 波特率与时钟信号分别解决什么问题

UART 使用波特率，例如：

```
9600
115200
921600
```

如果每一个符号携带一个 Bit，那么 115200 baud 可以近似理解为"每秒 115200 个 Bit 时间单位"。因此：

```
Bit Time = 1 / 115200
         ≈ 8.68us
```

发送端和接收端都按照约 8.68us 为一个 Bit。

SPI 则直接使用 `SCLK`。例如 `10MHz` 意味着每个时钟周期 `100ns`。接收端不需要长期估计发送端速度，因为每一个 Bit 都伴随着时钟。

▷ 图：波特率约定计时 vs SCLK 随路时钟的采样机制对比（见原始 mhtml）

### 4.6 单工、半双工与全双工的数据方向模型

除了时间问题，还要考虑数据方向。

**单工**：只能单向通信：

```
A ─────→ B
```

例如某些单向广播设备。

**半双工**：双方都能发送，但是不能同时：

```
A ←────→ B
```

某一个时刻只能有一方驱动线路。RS-485 常见两线制连接就是典型半双工。

**全双工**：双方可以同时发送：

```
A TX ─────→ RX B
A RX ←───── TX B
```

UART 使用独立 TX 和 RX 时属于全双工。SPI 也通常具备独立 MOSI 和 MISO，因此可以在时钟驱动下同时收发。

▷ 图：单工 / 半双工 / 全双工三种数据方向模型（见原始 mhtml）

## 五、不增加时钟线怎么办：一步步推导 UART

### 5.1 异步通信的核心：双方提前约定传输速率

假设我们不想增加时钟线。那么只能让两颗 MCU 提前约定 `波特率 = 115200`。

发送端和接收端各自用自己的本地时钟生成约 `8.68us` 的 Bit Time。这样即使没有 CLK，也可以按照时间推测每一位的位置。

但是还缺少一个问题：

> 接收端什么时候开始计时？

如果线路长时间空闲，接收端不知道第一个数据什么时候到来。于是需要一个明显的"开始信号"。

▷ 图：无时钟线时依靠约定速率+开始信号的异步通信思路（见原始 mhtml）

### 5.2 波特率、Bit Time 与时钟误差

假设 UART 配置：

```
115200 baud
8 data bits
1 stop bit
no parity
```

一个 Bit：

```
Tbit = 1 / 115200
     ≈ 8.68us
```

发送一个标准 8N1 字节需要：

```
1 Start
8 Data
1 Stop
```

总计 `10 Bit`。因此理论上传输一个 Byte 需要：

```
10 × 8.68us
≈ 86.8us
```

有效数据吞吐量约为：

```
115200 / 10
≈ 11520 Byte/s
```

这也说明：

> 波特率并不等于有效字节吞吐量。

由于发送端和接收端晶振都有误差，所以 UART 不允许无限连续地依赖本地计时而不重新同步。这就是为什么每个字符前面都存在 Start Bit。

▷ 图：8N1 帧内 10 个 Bit 的时间构成与吞吐量计算（见原始 mhtml）

### 5.3 起始位：如何告诉接收端"数据开始了"

UART 空闲状态通常为高电平。发送一个字符时，发送端先把线路拉低一个 Bit Time：

```
Idle = 1
        ↓
Start = 0
```

接收端检测到 `1 → 0` 的下降沿以后，就知道：一个新的字符开始了。

然后接收端从这个位置开始计时。例如等待半个 Bit Time，到 Start Bit 中心进行确认，再按照一个 Bit Time 的间隔采样后续数据。

所以 Start Bit 的本质是：

> 重新建立字符级时间同步。

▷ 图：Start Bit 下降沿触发接收端重新对齐采样时钟（见原始 mhtml）

### 5.4 停止位：如何定义一次传输的结束

数据位发送完成以后，发送端把线路恢复为高电平。这个高电平持续至少一个规定的 Bit Time，就是 Stop Bit。

Stop Bit 的作用包括：

- 表示当前字符结束；
- 让线路恢复空闲状态；
- 给下一次 Start Bit 的下降沿创造条件；
- 给收发双方提供一定重新同步空间。

如果接收端在预期 Stop Bit 的位置没有检测到高电平，就可能报告 `Framing Error`，也就是帧错误。

▷ 图：Stop Bit 恢复空闲电平与 Framing Error 的判定（见原始 mhtml）

### 5.5 奇偶校验：最基础的错误检测机制

假设发送 `10110010`，其中 1 的数量为 4。

**偶校验**：要求"数据位 + 校验位"中 1 的总数量为偶数。当前已经是偶数，因此 Parity Bit 为 `0`。

**奇校验**：要求 1 的总数量为奇数。当前有 4 个 1，因此 Parity Bit 为 `1`。

奇偶校验可以发现部分单 Bit 错误。但是它的能力有限。如果两个 Bit 同时翻转，奇偶性可能仍然不变。因此复杂通信协议通常会在 UART 字节流上再增加 `Checksum`、`CRC` 等更强的校验机制。

▷ 图：奇校验与偶校验的 Parity Bit 计算示例（见原始 mhtml）

### 5.6 UART 完整帧结构与逐位传输时序

最常见配置 `8N1`，含义是：

```
8 Data Bits
No Parity
1 Stop Bit
```

一帧可以表示为：

```
Idle
  │
  │ Start  D0 D1 D2 D3 D4 D5 D6 D7 Stop
──┐
  └────┐     ┌───┐ ...
       └─────┘
```

UART 通常低位先发送。例如 `0x53 = 0101 0011`，从 D0 到 D7：

```
1 1 0 0 1 0 1 0
```

完整顺序：

```
Start 0
D0    1
D1    1
D2    0
D3    0
D4    1
D5    0
D6    1
D7    0
Stop  1
```

▷ 图：0x53 一帧完整的逐位传输波形（见原始 mhtml）

### 5.7 MCU 硬件 UART 外设与寄存器数据流转

真实 MCU 中，我们通常不使用 GPIO 软件延时去模拟 UART，而是使用硬件 UART 外设。

发送过程大致如下：

```
CPU写UART发送寄存器
        ↓
TX Data Register
        ↓
发送移位寄存器
        ↓
自动添加Start/Data/Parity/Stop
        ↓
TX引脚输出电平
```

接收过程：

```
RX引脚检测Start
       ↓
硬件过采样
       ↓
逐Bit恢复数据
       ↓
接收移位寄存器
       ↓
RX Data Register/FIFO
       ↓
产生RX中断或DMA请求
       ↓
CPU读取
```

很多 UART 并不是每个 Bit 只采样一次，而会使用更高频内部时钟进行过采样，例如常见的 8 倍或者 16 倍采样，以提高采样稳定性。

▷ 图：硬件 UART 收发两条寄存器数据通路（见原始 mhtml）

### 5.8 UART、TTL、RS-232、RS-485 到底有什么区别

这是工程中非常容易混淆的一组概念。

**UART** 主要定义：

```
Bit按照什么时间发送
Start
Data
Parity
Stop
```

它属于数字通信逻辑层面的异步串行机制。

**TTL/CMOS UART**：MCU 引脚直接输出 `0V / 3.3V` 或 `0V / 5V`。这只是 UART 信号的一种电气实现。常说的"TTL 串口"实际上通常是"UART 帧格式 + CMOS/TTL 单端电平"。

**RS-232** 定义了另一套物理层电气规范，使用正负电压，并且逻辑极性与普通 MCU UART 电平表示方式并不完全相同。MCU UART 一般不能直接连接标准 RS-232 接口，需要：

```
UART
 ↓
RS-232 Transceiver
 ↓
RS-232 Cable
```

**RS-485** 主要定义差分物理层。UART 可以作为上层字节产生方式：

```
UART TX/RX
    ↓
RS-485收发器
    ↓
A/B差分线
```

因此：

> UART 和 RS-485 并不是同一层级的竞争关系。UART 解决字节如何序列化。RS-485 解决信号如何在线缆上更可靠地传输。

▷ 图：UART / TTL / RS-232 / RS-485 的层级与电气差异图（见原始 mhtml）

### 5.9 实战：UART 单字节与多字节传输全过程

假设 MCU A 发送：

```c
uint8_t data = 0x5A;
```

典型过程为：

```
CPU把0x5A写入UART
      ↓
UART转换为串行Bit
      ↓
Start
      ↓
D0～D7
      ↓
Stop
      ↓
MCU B UART恢复为0x5A
      ↓
RX寄存器
      ↓
CPU读取0x5A
```

但是如果发送 `0x12 0x34 0x56 0x78`，UART 本身只会看到：

```
Byte
Byte
Byte
Byte
```

它不知道这是"一个 32 位整数"还是"四条独立命令"，更不知道数据有没有丢失。于是我们发现：

> UART 解决了 Byte 怎么传，却没有解决 Message 怎么表达。

这个问题会在第九章继续解决。

▷ 图：0x5A 从 MCU A 内存到 MCU B 内存的完整链路（见原始 mhtml）

## 六、与其猜时间，不如直接发送时钟：一步步理解 SPI

### 6.1 异步通信的局限与同步通信的产生

UART 最大的工程特点之一，就是不发送时钟。优点是节省一根 CLK。缺点是：

- 双方必须提前约定波特率；
- 晶振误差不能太大；
- 每一帧需要 Start/Stop；
- 高频率时对时钟误差更加敏感。

于是我们产生一个非常直接的想法：

> 与其让接收端猜什么时候采样，不如发送端直接告诉它。

于是增加一根时钟线。这就是同步串行通信的基本思想。

▷ 图：从异步猜时间到同步随路时钟的思路转变（见原始 mhtml）

### 6.2 增加时钟线如何解决数据采样问题

假设连接 `SCLK` 和 `DATA`。发送端每准备好一个 Bit，就产生一个时钟边沿。接收端规定"SCLK 上升沿读取 DATA"。那么：

```
DATA = Bit0
SCLK ↑
接收Bit0

DATA = Bit1
SCLK ↑
接收Bit1
```

只要信号满足建立时间和保持时间，双方就不需要使用完全相同的本地时钟。主设备控制 SCLK 多快，从设备就按照这个 SCLK 进行采样。

▷ 图：SCLK 边沿逐位锁存 DATA 的同步采样时序（见原始 mhtml）

### 6.3 SPI 四大信号线：SCLK、MOSI、MISO、CS

标准 SPI 常见四根信号：

```
SCLK
MOSI
MISO
CS
```

- **SCLK**：Serial Clock。由主设备产生时钟。
- **MOSI**：Master Out Slave In。主设备发送、从设备接收。
- **MISO**：Master In Slave Out。从设备发送、主设备接收。
- **CS**：Chip Select。选择当前要通信的从设备。通常低有效：

```
CS = 0 → 设备被选中
CS = 1 → 设备不参与当前事务
```

▷ 图：SPI 四线连接的主从拓扑（见原始 mhtml）

### 6.4 SPI 全双工同步传输的底层原理

SPI 内部可以想象成双方各有一个移位寄存器。例如主设备 `10101100`，从设备 `00110101`。

每产生一个时钟：

```
主设备移出1 Bit到MOSI
从设备移出1 Bit到MISO
双方同时移入对方Bit
```

经过 8 个时钟以后：

```
主设备发送8 Bit
同时接收8 Bit
从设备同样发送8 Bit
同时接收8 Bit
```

这就是 SPI 全双工的本质。因此即使主设备"只是读取"，实际上也需要不断产生时钟，而产生时钟通常意味着 SPI 硬件同时会在 MOSI 上发送 Dummy Data。

▷ 图：主从两个移位寄存器随时钟环形交换数据（见原始 mhtml）

### 6.5 CPOL 与 CPHA：四种 SPI 时序模式

现在还有一个问题：

> 时钟究竟在哪个边沿采样？

SCLK 有上升沿、下降沿。另外，SCLK 空闲时可以是低、高。于是产生两个参数。

**CPOL**（Clock Polarity）：决定空闲电平：

```
CPOL = 0 → 空闲低
CPOL = 1 → 空闲高
```

**CPHA**（Clock Phase）：决定数据相对于第一个有效边沿和第二个有效边沿的采样关系。

于是组合出：

```
Mode 0：CPOL=0 CPHA=0
Mode 1：CPOL=0 CPHA=1
Mode 2：CPOL=1 CPHA=0
Mode 3：CPOL=1 CPHA=1
```

工程中最重要的不是死背波形，而是：

> 主设备和从设备必须采用完全一致的模式。

如果 CPHA 错误，最常见表现就是：

```
数据整体错一位
随机错误
读到0xFF
读到0x00
```

▷ 图：Mode 0～3 四种 CPOL/CPHA 组合的时序波形（见原始 mhtml）

### 6.6 CS 如何完成设备选择与事务边界控制

假设 SPI 总线上有三个设备：

```
           ┌── Flash
MOSI/MISO ─┼── ADC
SCLK       └── Display
```

MOSI、MISO 和 SCLK 可以共享。每个设备拥有独立 CS：

```
CS_FLASH
CS_ADC
CS_LCD
```

想访问 Flash：

```
CS_FLASH = 0
CS_ADC   = 1
CS_LCD   = 1
```

因此 CS 同时解决两个问题：

```
当前跟谁通信
当前事务从哪里开始、哪里结束
```

很多 SPI 器件会在 `CS下降沿` 复位内部命令状态机，在 `CS上升沿` 结束当前命令。所以不能认为 CS 只是一个普通 Enable。

▷ 图：多从设备共享三线、各自独立 CS 的连接图（见原始 mhtml）

### 6.7 SPI 为什么速度快、协议开销低

SPI 速度高的原因主要包括：

- 同步时钟；
- 推挽输出；
- 点对点式信号；
- 没有 Start/Stop；
- 没有地址字段的强制要求；
- 没有 ACK 的强制要求；
- 协议逻辑简单。

发送一个 Byte 通常只需要 `8个SCLK`，不像 UART 8N1 需要 `10个Bit时间`。

当然，SPI 的最高速率依然受到以下因素限制：

- MCU 外设能力；
- 从设备最大 SCLK；
- PCB 走线；
- 负载电容；
- 边沿速度；
- 信号完整性。

▷ 图：SPI 一个 Byte 8 时钟 vs UART 8N1 10 位时间的开销对比（见原始 mhtml）

### 6.8 SPI 多设备扩展为什么会遇到引脚瓶颈

SPI 共用 `SCLK`、`MOSI`、`MISO`，但是通常每增加一个从设备，就增加一个 CS。

如果有 `10个SPI设备`，可能需要 `10根CS`。这又开始占用大量 GPIO。

此外，多个设备共用 MISO 时还必须保证"未选中的从设备释放 MISO"，否则多个设备同时驱动 MISO 会发生总线冲突。

于是我们开始思考：

> 有没有办法让多个设备真正共享极少数导线，而且不需要每个设备单独一根 CS？

这就会自然地走向 I²C。

▷ 图：SPI 从设备增多导致 CS 引脚线性膨胀（见原始 mhtml）

### 6.9 实战：MCU 与 SPI Flash 完整读写流程

以读取 SPI Flash 的 JEDEC ID 为例。常见流程：

```
CS拉低
  ↓
发送命令0x9F
  ↓
继续产生SCLK
  ↓
发送Dummy Byte
  ↓
从MISO读Manufacturer ID
  ↓
继续读取Device ID
  ↓
CS拉高
```

伪代码：

```c
uint8_t tx[4] = {
    0x9F,
    0xFF,
    0xFF,
    0xFF
};

uint8_t rx[4];

CS_LOW();

spi_transfer(tx, rx, sizeof(tx));

CS_HIGH();

printf("ID = %02X %02X %02X\n",
       rx[1],
       rx[2],
       rx[3]);
```

这里能够看到 SPI 的一个典型特点：

> 为了从从设备读取 3 个 Byte，主设备仍然需要发送 3 个 Dummy Byte，从而产生对应的 24 个 SCLK。

▷ 图：读取 JEDEC ID 的 SPI 时序（命令 + Dummy + 返回 ID）（见原始 mhtml）

## 七、多设备如何共享总线：从 SPI 扩展痛点理解 I²C

### 7.1 多传感器场景下 SPI 的引脚扩展问题

假设一个 MCU 连接：

```
温度传感器
加速度计
陀螺仪
EEPROM
RTC
光照传感器
压力传感器
```

如果全部使用 SPI，`SCLK`、`MOSI`、`MISO` 可以共享，但是 7 个器件可能需要 `7根CS`。对于引脚紧张的 MCU 并不理想。

于是我们希望：

> 所有设备只共享少数几根线。

但是如果没有 CS，就必须使用另一种方式决定"当前数据到底发给谁"。于是设备地址出现了。

▷ 图：七个外设全走 SPI 时的 CS 引脚困境（见原始 mhtml）

### 7.2 SCL 与 SDA：多设备共享两根信号线

I²C 通常只使用 `SCL` 和 `SDA`。所有设备都并联在这两根线上：

```
              ┌── Sensor A
SCL ──────────┼── EEPROM
SDA ──────────┼── RTC
              └── Sensor B
```

SCL 是时钟。SDA 是双向数据线。于是 I²C 同时获得如下能力：

```
同步通信
少引脚
多设备共享
```

▷ 图：多设备并联在 SCL/SDA 两线上的 I²C 总线拓扑（见原始 mhtml）

### 7.3 设备地址：解决"数据到底发给谁"

没有独立 CS，就必须在数据里面加入地址。假设：

```
Sensor A 地址 = 0x48
EEPROM   地址 = 0x50
RTC      地址 = 0x68
```

主设备首先发送 `0x68` 对应的地址字段。所有设备都能看到总线数据，但是只有地址匹配的设备继续参与当前事务。因此：

> SPI 主要使用物理 CS 选设备。I²C 主要使用逻辑地址选设备。

这就是典型的"硬件资源换成协议复杂度"。

▷ 图：地址匹配决定哪个从设备参与事务（见原始 mhtml）

### 7.4 开漏输出与上拉电阻：解决多设备共线驱动

现在所有设备都连接同一根 SDA。如果全部使用推挽输出，可能出现：

```
设备A输出1
设备B输出0
```

产生电气冲突。于是 I²C 使用开漏思想：

```
任何设备只允许主动拉低
不能主动推高
```

高电平由上拉电阻产生：

```
VCC
 │
 Rpull-up
 │
SDA ───── 各设备开漏输出
```

因此：

```
只要任何设备拉低 → SDA = 0
只有所有设备释放 → SDA = 1
```

这个特性不仅避免了推挽短路，还给后续的 `ACK`、`仲裁`、`Clock Stretching` 提供了物理基础。

▷ 图：开漏 + 上拉电阻构成的线与（Wired-AND）结构（见原始 mhtml）

### 7.5 START 与 STOP：没有 CS 如何定义事务边界

SPI 使用 CS 定义事务边界。I²C 没有每设备独立 CS，于是需要在 SDA 和 SCL 的特殊组合中编码开始和结束。

**START**：当

```
SCL保持高
SDA从高变低
```

表示 START。

**STOP**：当

```
SCL保持高
SDA从低变高
```

表示 STOP。

正常数据传输时，SDA 通常只允许在 SCL 低电平期间改变。因此当 SCL 高电平期间 SDA 发生特定边沿，就可以被识别为控制条件，而不是普通数据。

▷ 图：START / STOP 条件的 SCL、SDA 组合时序（见原始 mhtml）

### 7.6 ACK 与 NACK：如何确认数据是否成功接收

I²C 每发送完 8 Bit 数据以后，第 9 个时钟通常用来进行 ACK/NACK。发送方在第 9 个时钟释放 SDA。接收方如果成功接收，就拉低：

```
ACK = 0
```

如果不拉低：

```
NACK = 1
```

于是每一个 Byte 都可以得到接收反馈。

需要注意：ACK 表示"接收方在 I²C 层面接受了这个 Byte"，并不一定代表"上层业务已经处理成功"。例如 EEPROM 接收到数据，并不意味着 Flash 内部写周期已经结束。

▷ 图：第 9 个时钟上的 ACK/NACK 应答时序（见原始 mhtml）

### 7.7 I²C 完整读写帧与 Repeated START

假设要从地址 `0x68` 的传感器读取寄存器 `0x10`。通常需要先告诉设备寄存器地址，再进行读取。典型流程：

```
START
 ↓
Slave Address + Write
 ↓
ACK
 ↓
Register Address = 0x10
 ↓
ACK
 ↓
Repeated START
 ↓
Slave Address + Read
 ↓
ACK
 ↓
Data High
 ↓
ACK
 ↓
Data Low
 ↓
NACK
 ↓
STOP
```

为什么要 Repeated START？因为主设备希望：

```
不释放总线
直接把方向从写切换成读
```

如果中间发送 STOP，其他主设备可能插入新的事务。Repeated START 可以保持当前事务连续性。

▷ 图：写寄存器地址 + Repeated START + 读数据的完整帧（见原始 mhtml）

### 7.8 仲裁、时钟同步与 Clock Stretching

**多主仲裁**：因为 I²C 是开漏结构，所以某个设备发送 1 的含义其实是"释放 SDA"。如果另外一个设备同时发送 0（拉低 SDA），总线上实际电平一定是 0。

于是一个主设备发送 `1`，却读取到 `0`，就知道：

> 我输了仲裁。

这就是 I²C 仲裁的基础。

**时钟同步**：SCL 同样采用类似的 Wired-AND 行为。只要任何设备保持 SCL 为低，总线就不能真正变高。

**Clock Stretching**：某些从设备处理速度比较慢，可以主动把 SCL 拉低：

```
主设备想继续
从设备暂时保持SCL低
```

相当于告诉主设备："稍等一下，我还没有准备好。"

当然，并不是所有控制器、软件栈或者系统设计都会允许无限制的 Clock Stretching，因此实际使用时必须阅读主控和从设备手册。

▷ 图：开漏线与机制下的仲裁丢失与 SCL 拉伸示意（见原始 mhtml）

### 7.9 实战：MCU 读取 I²C 传感器 16 位数据

假设传感器地址 `0x48`，寄存器地址 `0x01`，数据为两个 Byte。伪代码：

```c
uint8_t reg = 0x01;
uint8_t data[2];

i2c_master_transmit(
    0x48,
    &reg,
    1
);

i2c_master_receive(
    0x48,
    data,
    2
);

uint16_t value =
    ((uint16_t)data[0] << 8) |
    data[1];
```

真实控制器可能把这类组合操作封装为：

```
Write Register Address
Repeated START
Read N Bytes
```

需要特别注意：`7位地址` 和某些 API 要求的 `左移1位后的地址` 并不是同一个表示方式。遇到：

```
设备手册写0x68
程序却要求0xD0
```

这类情况，往往就是地址位和 R/W 位表达方式不同造成的。

▷ 图：7bit 地址与含 R/W 位的 8bit 地址表示对照（见原始 mhtml）

## 八、板子上能传，几十米外还能传吗：RS-485 与 CAN

### 8.1 板级通信为什么不适合直接长距离传输

UART TTL、SPI、I²C 很适合板内通信。但是把普通 MCU GPIO 信号直接拉出去几十米，就会遇到严重问题：

- 电磁干扰；
- 地电位差；
- 线缆电容；
- 信号边沿变慢；
- 反射；
- 共模噪声；
- EMI；
- ESD；
- 浪涌。

因此：

> 能在 PCB 上正常工作的数字信号，不代表可以直接在线缆上长距离传输。

▷ 图：板内信号直接拉长线后面临的多种电气威胁（见原始 mhtml）

### 8.2 单端信号的干扰、地电位差与传输瓶颈

普通单端通信判断的是"Signal 相对于 GND 的电压"。例如：

```
Signal = 3.3V → 1
Signal = 0V   → 0
```

问题在于，两块板子的 GND 并不一定完全相同。例如：

```
板A地 = 0V
板B地 = +1V
```

那么 A 发送的 3.3V，在 B 看来可能只剩 `2.3V`。再叠加线缆噪声，可靠性进一步下降。

▷ 图：两板地电位差侵蚀单端信号有效幅度的示意（见原始 mhtml）

### 8.3 差分信号为什么具有更强的抗干扰能力

差分通信不主要观察某一根线相对于地的绝对电压，而是观察：

```
VA - VB
```

如果外界噪声同时耦合到两根线上：

```
A + 1V
B + 1V
```

二者差值基本不变。因此差分传输对共模干扰具备更强抵抗能力。此外，使用双绞线还可以进一步降低外界磁场耦合以及自身辐射。

RS-485 和 CAN 都大量采用差分传输思想。

▷ 图：共模噪声同时叠加到 A/B 两线、差值不变的原理图（见原始 mhtml）

### 8.4 RS-485：长距离、多节点差分通信

RS-485 使用差分线 `A`、`B`。典型网络：

```
Node A ────── Node B ────── Node C ────── Node D
              A/B双绞线
```

RS-485 主要定义电气层特性。MCU 常见连接方式：

```
MCU UART
   │TX
   │RX
   │DE/RE
   ↓
RS-485 Transceiver
   ↓
A/B差分总线
```

其中 `DE` 用于控制发送驱动器是否使能。因为两线 RS-485 常见为半双工，所以发送完成后要及时释放总线。

▷ 图：UART + RS-485 收发器 + A/B 总线的多节点连接（见原始 mhtml）

### 8.5 UART 与 RS-485：协议逻辑和电气传输的层级区别

一个非常重要的理解是：

```
UART负责把Byte变成Bit时间序列
RS-485负责把逻辑Bit变成差分电信号
```

因此可以组合：

```
Modbus RTU
    ↓
UART Frame
    ↓
RS-485 Physical Layer
```

这里 `Modbus RTU` 负责业务数据格式和地址。UART 负责字符串行化。RS-485 负责线缆传输。这是典型的分层设计。

▷ 图：Modbus RTU / UART / RS-485 三层堆叠关系（见原始 mhtml）

### 8.6 多节点同时发送带来的总线冲突问题

RS-485 可以连接多个节点。但是如果 Node A 和 Node B 同时打开驱动器：

```
A发送1
B发送0
```

总线就可能冲突。RS-485 本身并没有像 CAN 那样定义完整的无破坏仲裁机制。因此必须由上层协议解决：

- 主从轮询；
- Token；
- TDMA；
- 随机退避；
- 固定时间片。

例如 Modbus RTU 经常使用：

```
一个Master
多个Slave
```

Slave 只有被点名以后才能回答。这样就避免多个节点随意抢占总线。

▷ 图：主从轮询避免 RS-485 总线冲突的时序（见原始 mhtml）

### 8.7 CAN 仲裁：显性位、隐性位与消息优先级

CAN 进一步解决了：

> 多个节点可能同时发起通信，怎么办？

CAN 总线上存在：

```
Dominant    显性位
Recessive   隐性位
```

经典逻辑通常理解为：

```
0 = Dominant
1 = Recessive
```

如果一个节点发送隐性位 1，却在总线上读取到显性位 0，就知道：

> 有另外一个更高优先级节点正在发送，我退出仲裁。

假设两个节点同时发送 ID：

```
Node A：0010...
Node B：0011...
```

前面三个 Bit 相同。到了某一位：

```
A发送0
B发送1
```

总线上最终表现为 `0`。B 发现"我发送 1，却读到 0"，于是停止发送。A 继续。整个过程并没有破坏 A 的帧。

这就是 CAN 非破坏性位仲裁的精妙之处。并且由于低 ID 在更高位更早出现 0，因此通常意味着：

```
数值更小的ID拥有更高的仲裁优先级
```

▷ 图：两节点逐位仲裁、隐性位一方退出的过程（见原始 mhtml）

### 8.8 CRC、ACK、错误帧与 CAN 可靠性机制

CAN 不只是解决总线竞争，还设计了丰富的错误检测机制。包括：

- Bit Monitoring；
- Bit Stuffing 检查；
- CRC；
- Frame Check；
- ACK Check。

**CRC**：发送端根据帧内容计算 CRC。接收端重新计算并比较。

**ACK**：发送节点在 ACK Slot 释放总线。只要有一个正确接收帧的节点，就可以在 ACK Slot 发送显性位。发送端因此知道：

```
至少有一个节点正确接收到了这个CAN帧
```

**错误帧**：节点检测到错误以后，可以发送 Error Flag，使当前帧被认为无效。

CAN 控制器还维护错误计数器。错误严重的节点可能逐步从：

```
Error Active
 ↓
Error Passive
 ↓
Bus Off
```

避免一个故障节点持续破坏整条总线。

▷ 图：CAN 五种错误检测机制与错误状态迁移（见原始 mhtml）

### 8.9 CAN 数据帧与多节点通信流程

经典 CAN 数据帧可以高度简化成为：

```
SOF
 ↓
Arbitration Field
 ↓
Control
 ↓
Data
 ↓
CRC
 ↓
ACK
 ↓
EOF
```

假设：

```
发动机ECU 发送转速
ID = 0x100

仪表ECU 发送亮度
ID = 0x300
```

如果两者同时发送，`0x100` 通常会比 `0x300` 赢得仲裁。这意味着系统可以天然把：

```
刹车
发动机
安全控制
```

等关键消息分配更高优先级 ID。

▷ 图：CAN 数据帧字段结构与 ID 优先级示例（见原始 mhtml）

### 8.10 RS-485 与 CAN 的工程选型原则

RS-485 更像"可靠的多点差分物理通道"。

优点：

- 简单；
- 成本低；
- 距离长；
- 协议可完全自定义。

缺点：

- 仲裁通常要自己设计；
- 错误恢复要上层实现；
- 节点管理依赖软件协议。

CAN 则把更多机制放进控制器：

- 仲裁；
- CRC；
- ACK；
- 自动重发；
- 错误隔离；
- 帧结构。

因此在：

```
汽车
工业控制
机器人
高可靠多节点实时通信
```

中非常常见。

如果场景只是"一个主机轮询多个简单从机"，RS-485 可能更加简单。如果场景要求：

```
多个节点随时主动发送
优先级明确
错误处理强
```

CAN 往往更加合适。

▷ 图：RS-485 与 CAN 的选型对比图（见原始 mhtml）

## 九、会用 UART 还不够：从 Byte 到 Packet 设计真正的通信协议

### 9.1 裸 Byte 流为什么无法表达完整业务

假设 UART 接收到：

```
01 02 03 04 05 06
```

问题来了：这是"一条 6Byte 消息"，还是"两条 3Byte 消息"，还是"三条 2Byte 消息"？

UART 不知道。UART 只负责 Byte 的传输。业务协议必须自己解决数据边界。

▷ 图：同一串字节的三种可能切分方式（见原始 mhtml）

### 9.2 从电平、Bit、Byte 到 Frame、Packet、Message

可以建立一个非常重要的层次关系：

```
电平
 ↓
Bit
 ↓
Byte
 ↓
Frame
 ↓
Packet
 ↓
Message
```

- **电平**：物理信号。
- **Bit**：0 或 1。
- **Byte**：8 个 Bit 组成的基本数据单元。
- **Frame**：一组具备明确边界的数据。
- **Packet**：通常包含地址、命令、长度、Payload、校验。
- **Message**：业务语义。例如"设置电机转速为 1200rpm"。

这才是应用真正关心的事情。

▷ 图：电平到 Message 的六层抽象金字塔（见原始 mhtml）

### 9.3 帧头、帧尾与长度字段：如何识别一帧数据

一种简单协议：

```
Header
Length
Payload
Checksum
```

例如：

```
AA 55 03 10 20 30 CRC
```

其中：

```
AA 55 = 帧头
03    = Payload长度
10 20 30 = 数据
CRC   = 校验
```

解析器先寻找 `AA 55`，找到后读取 Length，然后再等待 `Length + CRC` 对应数量的 Byte。这样就知道一帧什么时候完整。

相比单纯使用固定帧尾，长度字段对二进制数据更加友好，因为 Payload 中可能自然出现：

```
0x0D 0x0A
0xAA 0x55
```

等任意数值。

▷ 图：帧头 + 长度字段定界一帧数据的解析过程（见原始 mhtml）

### 9.4 地址、指令、Payload 与校验字段如何组织

可以设计：

```
SOF
Version
Address
Command
Sequence
Length
Payload
CRC
```

例如：

```
AA 55
01
03
10
27
02
04 D2
CRC16
```

含义：

```
AA55    帧头
01      协议版本

10      设置速度命令
27      序号
02      Payload长度
04D2    速度1234
CRC16   校验
```

这样一帧数据已经具备比较完整的工程结构。

▷ 图：一帧完整协议数据的字段划分示例（见原始 mhtml）

### 9.5 序号机制：识别重复、乱序与丢失数据

假设发送 `SEQ = 100`。接收端处理完成以后返回 `ACK 100`。

如果发送端超时，没有收到 ACK，于是重发 `SEQ = 100`。接收端发现"100 已经处理过"，就知道这是重复包。可以：

```
不再次执行命令
只重新返回ACK
```

这对于：

```
扣款
开阀门
电机移动
Flash写入
```

这类不能重复执行的操作非常重要。

▷ 图：SEQ + ACK 配合识别重复包的交互流程（见原始 mhtml）

### 9.6 大数据如何分包、排序与重组

如果需要发送 `100KB固件`，不适合直接作为一整个帧。可以拆成：

```
Packet 0
Packet 1
Packet 2
……
```

每包包含：

```
Image ID
Packet Number
Offset
Length
Payload
CRC
```

接收端按照 `Offset` 写入 Flash。全部完成后，再校验整个镜像 Hash。

这就是从简单串口协议逐渐发展成为真正可靠传输系统的过程。

▷ 图：固件分包传输与按 Offset 重组写入 Flash（见原始 mhtml）

### 9.7 粘包、半包与字节流解析机制

假设发送端连续发送 `Frame A`、`Frame B`。接收端调用一次 `read()`，可能得到：

```
Frame A + Frame B
```

也可能只得到：

```
Frame A的前半部分
```

这就是常说的"粘包"、"半包"。

需要注意：这些并不一定是底层通信错误。对于字节流接口而言，它只是"一次读到了多少当前可用数据"。

应用层必须使用状态机解析。例如：

```
SEARCH_HEADER
READ_HEADER
READ_PAYLOAD
READ_CRC
```

当一帧不完整时，保留数据等待下一批接收。

▷ 图：粘包 / 半包两种读取结果与状态机解析（见原始 mhtml）

### 9.8 Checksum、CRC、ACK、超时与重传机制

**Checksum**：实现简单，但检错能力一般。

**CRC**：适合检测突发错误。例如常见 `CRC8`、`CRC16`、`CRC32`。必须明确：

- Polynomial；
- Initial Value；
- RefIn；
- RefOut；
- XOR Out；
- 字节顺序。

否则双方都说"CRC16"，计算结果也可能完全不同。

**ACK**：解决"对方到底有没有接受数据"。

**Timeout**：发送以后必须规定"等待多久"。如果无限等待，一个失效节点就可能卡死整个系统。

**Retransmission**：超时以后可以"重试 N 次"，但不能无限重试。超过次数应进入：

```
通信故障
离线
降级
重新连接
```

逻辑。

▷ 图：CRC 参数六要素与 ACK/超时/重传闭环（见原始 mhtml）

### 9.9 硬件通信接口与软件通信协议的分层关系

一个完整系统可能是：

```

 ↓
自定义Packet

UART Byte Stream

RS-485差分信号

双绞线
```

也可能是：

```

I²C Transaction
 ↓

```

因此必须学会区分：

```

```

这样排查问题时才不会混乱。

### 9.10 实战：设计一套完整的 MCU 自定义通信协议

定义如下：

```
+--------+---------+------+-----+-----+--------+---------+
| Header | Address | Cmd  | Seq | Len | Payload| CRC16   |
+--------+---------+------+-----+-----+--------+---------+
| 2 Byte | 1 Byte  |1Byte |1Byte|2Byte| N Byte | 2 Byte  |
+--------+---------+------+-----+-----+--------+---------+
```

Header 为 `0xAA 0x55`。

例如发送"设置设备 3 的电机速度为 1000"，数据可能组织成为：

```
AA 55
03
10
25
00 02
03 E8
CRC_L CRC_H
```

接收状态机：

```c
enum parse_state {
    WAIT_HEAD_1,
    WAIT_HEAD_2,
    READ_FIXED,
    READ_PAYLOAD,
    READ_CRC
};
```

核心逻辑：

```c
void protocol_input(uint8_t byte)
{
    switch (state) {

    case WAIT_HEAD_1:
        if (byte == 0xAA)
            state = WAIT_HEAD_2;
        break;

    case WAIT_HEAD_2:
        if (byte == 0x55) {
            index = 0;
            state = READ_FIXED;
        } else {
            state = WAIT_HEAD_1;
        }
        break;

    case READ_FIXED:
        fixed[index++] = byte;

        if (index == FIXED_LEN) {
            payload_len =
                ((uint16_t)fixed[3] << 8) |
                fixed[4];

            index = 0;

            if (payload_len <= MAX_PAYLOAD)
                state = READ_PAYLOAD;
            else
                state = WAIT_HEAD_1;
        }
        break;

    case READ_PAYLOAD:
        payload[index++] = byte;

        if (index >= payload_len) {
            index = 0;
            state = READ_CRC;
        }
        break;

    case READ_CRC:
        crc_buf[index++] = byte;

        if (index == 2) {
            protocol_check_frame();
            state = WAIT_HEAD_1;
        }
        break;
    }
}
```

到这里，我们已经从最开始的一根 GPIO，走到了一套具备：

```
寻址
命令
长度
序号
Payload
CRC
```

的真正软件协议。

## 十、数据能传了，但 CPU 忙不过来：中断、FIFO 与 DMA

### 10.1 CPU 轮询收发数据的基本工作方式

最简单 UART 接收：

```c
while (1) {
    if (UART_RX_READY()) {
        uint8_t data = UART_READ();
        process(data);
    }
}
```

CPU 一直检查：

```
数据来了吗？
数据来了吗？
数据来了吗？
```

这就是 Polling。低速、简单系统中完全可以使用。但是速度提高以后问题就出现了。

▷ 图：CPU 死循环轮询状态寄存器的工作方式（见原始 mhtml）

### 10.2 轮询模式的性能瓶颈与数据丢失风险

假设 UART 每 `86.8us` 收到一个 Byte。CPU 必须保证在下一批数据覆盖接收寄存器以前读取它。如果此时 CPU 正在：

```
Flash擦除
复杂运算
等待其他外设
```

就可能错过数据。此外，即使没有数据，CPU 也要不断检查状态寄存器，浪费处理时间和功耗。

因此我们希望：

> 平时 CPU 去做别的事情，数据来了再通知 CPU。

于是产生中断。

▷ 图：轮询错过接收窗口导致数据被覆盖的时序（见原始 mhtml）

### 10.3 中断通信：让 CPU 摆脱持续等待

UART 接收到数据以后，可以产生中断：

```
UART收到Byte
    ↓
设置RXNE
    ↓
产生IRQ
    ↓
CPU暂停当前任务
    ↓
进入ISR
    ↓
读取UART数据
    ↓
返回原任务
```

伪代码：

```c
void UART_IRQHandler(void)
{
    if (UART_RX_READY()) {
        uint8_t data = UART_READ();

        rx_buffer_put(data);
    }
}
```

这样 CPU 不需要不停轮询。

▷ 图：中断触发 → ISR 取数 → 返回主任务的流程（见原始 mhtml）

### 10.4 高频中断为什么仍然会消耗大量 CPU 资源

中断并不是免费的。每次中断都需要：

- 保存上下文；
- 跳转异常向量；
- 执行 ISR；
- 清除中断；
- 恢复上下文。

如果高速串口 `3Mbps`，每收到一个 Byte 就产生一次中断，CPU 会面对非常高的中断频率。

SPI 高速数据更明显。假设 `20MHz SPI`，每 8 个时钟就产生一次 Byte。不可能每个 Byte 都让 CPU 单独处理中断。

于是我们需要：

```
FIFO
Buffer
DMA
```

▷ 图：高速数据流下逐字节中断的开销累积（见原始 mhtml）

### 10.5 FIFO、Buffer 与 Ring Buffer 的数据缓冲机制

**FIFO**：很多硬件通信外设内部自带 FIFO。例如 `RX FIFO 深度 = 16 Byte`，意味着可以先缓存 16 Byte，再通知 CPU。这样中断可以从"每 1Byte 一次"变成"每 8Byte、每 16Byte"一次。

**软件 Buffer**：中断处理函数可以快速把数据复制到 RAM：

```
UART
 ↓
ISR
 ↓
Software Buffer
 ↓
Main Loop慢慢处理
```

把"数据接收"和"协议解析"解耦。

**Ring Buffer**：环形缓冲区非常适合持续数据流：

```
          ┌─────────────────┐
write →   │0 1 2 3 4 5 6 7  │
          └─────────────────┘
               ↑       ↑
             read    write
```

写指针不断向前。到尾部以后回到开头。读指针同样循环移动。这样不需要频繁移动整块内存。

▷ 图：硬件 FIFO / 软件 Buffer / 环形缓冲区三级缓冲结构（见原始 mhtml）

### 10.6 DMA 如何减少 CPU 逐字节搬运

DMA 的核心思想是：

> 不要让 CPU 亲自搬每一个 Byte。

假设 UART 接收 1024 Byte。没有 DMA：

```
UART每来一个Byte
   ↓
CPU读寄存器
   ↓
CPU写RAM
```

重复 1024 次。使用 DMA：

```
CPU配置：
外设地址 = UART RX Register
内存地址 = buffer
长度 = 1024
        ↓
DMA自动搬运
        ↓
传输完成
        ↓
中断CPU一次
```

CPU 只负责"配置开始、处理结果"，中间 1024 Byte 不需要逐字节干预。

▷ 图：无 DMA 逐字节搬运 vs DMA 整块搬运的对比（见原始 mhtml）

### 10.7 DMA 的数据地址、长度与工作模式

DMA 通常需要配置：

```
Source Address
Destination Address
Transfer Length
Data Width
Increment Mode
Direction
Trigger Source
```

例如 UART RX：

```
Source      = UART_RX_DATA_REG
Destination = rx_buffer
Source Inc  = Disable
Dest Inc    = Enable
Direction   = Peripheral → Memory
```

因为 UART 接收寄存器地址固定不变。而内存地址需要 `buffer[0]`、`buffer[1]`、`buffer[2]`……不断增加。

DMA 常见模式：

```
Normal
Circular
Ping-Pong / Double Buffer
```

- **Normal**：传输指定长度后停止。
- **Circular**：到缓冲区末尾后自动回到开头。适合连续采样和持续串口接收。
- **Double Buffer**：DMA 写 Buffer A 时，CPU 处理 Buffer B。然后交换。适合持续高速数据流。

▷ 图：DMA 配置项与 Normal / Circular / Double Buffer 三种模式（见原始 mhtml）

### 10.8 中断+DMA 协同的高效通信架构

DMA 并不是完全不要中断。更加常见的是：

```
DMA负责搬数据
中断负责通知事件
```

例如：

```
UART → DMA → RAM
             ↓
      Half Transfer IRQ
             ↓
      CPU处理前半区
             ↓
      Transfer Complete IRQ
             ↓
      CPU处理后半区
```

或者：

```
SPI DMA完成
    ↓
DMA IRQ
    ↓
CPU检查结果
    ↓
启动下一次DMA
```

这是一种非常典型的高效架构。

▷ 图：半传输/全传输中断驱动的双半区处理流水（见原始 mhtml）

### 10.9 UART+DMA+空闲线检测的典型接收方案

UART 接收协议经常存在一个难题：

> 我不知道一帧到底有多少 Byte。

如果 DMA 设置固定接收 `256 Byte`，但实际帧只有 `37 Byte`，DMA 永远等不到 256 Byte，就不会完成。

一种很常见的方案是：

```
UART RX
  ↓
DMA Circular/Normal
  ↓
持续写Buffer
  ↓
UART检测IDLE
  ↓
产生空闲线中断
  ↓
CPU读取DMA剩余计数
  ↓
计算本次接收长度
  ↓
交给协议解析器
```

IDLE 的含义可以理解为"UART 一段时间没有继续接收到新的字符"。因此特别适合处理：

```
长度不固定
帧与帧之间存在空闲间隔
```

的串口协议。

▷ 图：DMA 持续接收 + IDLE 中断截帧的方案流程（见原始 mhtml）

### 10.10 SPI/I²C 结合 DMA 的大数据传输

SPI 尤其适合 DMA。例如驱动 LCD 刷屏：

```
Framebuffer
    ↓
SPI TX DMA
    ↓
SPI
    ↓
LCD
```

CPU 只需要准备一块显示数据，然后启动 DMA。如果每一个像素都使用 `spi_write_byte();`，CPU 开销会非常大。

I²C 同样可以结合 DMA，但是由于 I²C 协议中存在：

```
START
Address
ACK
Repeated START
STOP
```

等状态，DMA 通常主要负责 Payload 部分的数据搬运，协议状态仍然需要 I²C 控制器进行管理。

▷ 图：SPI TX DMA 刷屏与 I²C DMA 只搬 Payload 的对比（见原始 mhtml）

### 10.11 实战：DMA+Ring Buffer+数据包解析通信框架

一个比较完整的 UART 接收系统可以设计成为：

```
UART RX
   ↓
DMA Circular Buffer
   ↓
IDLE / DMA Event
   ↓
把新增数据提交到Software Ring Buffer
   ↓
Protocol Parser Task
   ↓
寻找Header
   ↓
读取Length
   ↓
等待完整Frame
   ↓
CRC
   ↓
Command Dispatcher
   ↓
业务逻辑
```

伪代码：

```c
void uart_rx_event(size_t new_len)
{
    size_t i;

    for (i = 0; i < new_len; i++)
        ring_put(dma_rx_data[i]);

    protocol_poll();
}
```

协议解析：

```c
void protocol_poll(void)
{
    uint8_t byte;

    while (ring_get(&byte))
        protocol_input(byte);
}
```

进一步可以做成：

```
ISR/DMA层
只负责数据接收
        ↓
Buffer层
负责暂存
        ↓
Parser层
负责数据组帧
        ↓
Protocol层
负责校验、ACK、重传
        ↓
Application层
负责业务命令
```

到这一步，一套比较成熟的 MCU 通信软件架构已经形成。

▷ 图：DMA + Ring Buffer + 分层解析的完整接收框架（见原始 mhtml）

## 十一、从协议到系统：建立 MCU 通信的统一思维模型

### 11.1 所有通信协议都在解决的七个核心问题

回到文章开头提出的七个问题。

**1. Bit 怎么表示**。可能是：

```
GPIO高低电平
UART单端电平
RS-485差分电平
CAN差分状态
```

**2. 什么时候采样**：

- UART：提前约定波特率
- SPI：SCLK
- I²C：SCL
- CAN：位时序和同步机制

**3. 一帧从哪里开始、哪里结束**：

- UART：Start / Stop
- SPI：CS
- I²C：START / STOP
- CAN：SOF / EOF
- 自定义协议：Header / Length / CRC

**4. 数据发给谁**：

- SPI：CS
- I²C：Slave Address
- CAN：Message ID
- 自定义 RS-485：Node Address

**5. 谁能发送**：

- UART 点对点：双方 TX 独立
- RS-485：上层协议协调
- I²C：Master 控制 + 仲裁
- CAN：逐 Bit 无破坏仲裁

**6. 怎么判断数据有没有错**：

- UART：Parity
- I²C：ACK/NACK
- CAN：CRC + ACK + 多种错误检测
- 软件协议：CRC + ACK + Timeout

**7. 怎么提高效率**：

```
FIFO
Interrupt
DMA
Ring Buffer
Double Buffer
多队列
批量传输
```

这七个问题几乎贯穿所有数字通信系统。

### 11.2 UART、SPI、I²C、RS-485、CAN 横向对比

RS-485更偏物理层

### 11.3 MCU 通信接口的场景化选型方法

如果需求是：

```
两颗MCU简单点对点
速度要求一般
希望调试方便
```

优先考虑 UART。

如果需求：

```
板内高速
连接Flash、ADC、屏幕
协议简单
```

优先考虑 SPI。

如果：

```
大量低速传感器
GPIO紧张
希望两根线挂很多设备
```

优先考虑 I²C。

如果：

```
几十米
工业现场
多个节点
协议希望自己掌控
```

可以考虑 RS-485。

如果：

```
多个节点都需要主动发送
高可靠
需要优先级和硬件错误机制
```

CAN 更加合适。

选型不能只看"最高速度"，还要考虑：

```
距离
节点数量
成本
布线
软件复杂度
错误恢复
实时性
EMC
维护性
```

### 11.4 多协议共存的整机通信架构

真实产品往往不是只使用一种接口。例如一个工业控制器：

```
                    ┌── I²C温度传感器
                    ├── I²C EEPROM
                    │
主MCU ── SPI ───────┼── SPI Flash
  │                 └── SPI ADC
  │
  ├── UART ───── 调试串口
  │
  ├── UART + RS485 ── Modbus设备
  │
  ├── CAN ─────── 电机控制器
  │
  └── Ethernet ── 上位机/云平台
```

不同协议分别解决不同层级的问题。真正的系统设计能力，并不是想办法让一个接口解决全部问题，而是：

> 让最合适的接口承担最合适的任务。

### 11.5 综合实战：多外设 MCU 通信系统设计

假设设计一个机器人控制器。硬件包括：

```
IMU
EEPROM
Motor Driver
External Flash
Debug PC
远程控制器
```

可以设计：IMU 走 SPI 接 MCU。原因：

```
IMU数据频率高
板内距离短
SPI吞吐量高
```

EEPROM 走 `I²C`。因为：

```
数据量小
无需高速
节省引脚
```

External Flash 走 `QSPI/SPI`。

电机控制节点走 `CAN`。因为：

```
多个节点
实时控制
优先级
抗干扰
```

调试走 `UART`。长距离维护接口走 `UART + RS-485`。

这就是系统级通信设计。

### 11.6 从电气层到应用层的分层排错方法

通信失败时，最忌讳直接修改程序里所有参数。更加合理的排查顺序是：

```
第一层：有没有电？
        ↓
第二层：有没有波形？
        ↓
第三层：Bit时序对不对？
        ↓
第四层：Byte对不对？
        ↓
第五层：Frame完整不完整？
        ↓
第六层：CRC是否正确？
        ↓
第七层：业务命令是否正确？
```

例如 I²C 读不到传感器。先看"VCC 是否正常"，再看"SCL/SDA 有没有上拉"，再看示波器"有没有 START"，逻辑分析仪看"地址是不是 0x68、有没有 ACK"，再看软件"寄存器地址对不对"。

而不是一开始就怀疑"HAL 库有 Bug"。

### 11.7 示波器、逻辑分析仪与软件日志的调试方法

**示波器**最适合观察：

- 电压；
- 边沿；
- 上升时间；
- 下降时间；
- 过冲；
- 振铃；
- 毛刺；
- 差分波形；
- 时钟质量。

例如 I²C 上拉电阻过大时，SDA 上升沿可能明显变慢。逻辑分析仪虽然可能把它解码成为 1，但是示波器能直接看到模拟电气质量。

**逻辑分析仪**适合观察：

```
UART字节
SPI命令
I²C地址和ACK
CAN帧
```

它能帮助回答：

```
到底发送了什么
什么时候发送
协议字段是什么
```

**软件日志**可以看到：

```
状态机进入哪个状态
DMA接收了多少Byte
CRC为什么失败
超时发生在哪一步
```

最有效的调试通常是三者结合：

```
示波器看电
逻辑分析仪看协议
软件日志看状态机
```

### 11.8 从 MCU 总线延伸到 USB、Ethernet、Bluetooth 与 Wi-Fi

当我们继续学习 USB、Ethernet、Bluetooth 和 Wi-Fi，会发现问题规模变得更加复杂，但是很多基本思想仍然没有变化。

**USB** 需要解决：

- 设备发现；
- 地址分配；
- Endpoint；
- Packet；
- CRC；
- ACK/NAK；
- 流量调度。

**Ethernet** 需要：

```
MAC地址
Frame
CRC
介质访问
PHY
```

再往上还有：

```
IP
TCP
UDP
```

**Bluetooth** 进一步加入：

- 无线调制；
- 频道；
- 连接管理；
- 配对；
- 加密；
- Profile。

**Wi-Fi** 继续增加：

- 无线介质竞争；
- AP；
- Association；
- Authentication；
- 重传；
- 速率控制。

但是最底层依然没有脱离最开始的几个问题：

```
数据怎么表示？
接收端什么时候读？
帧从哪开始？
数据发给谁？
多个节点怎么抢信道？
出错怎么办？
怎么提升效率？
```

因此，真正掌握 MCU 通信以后，再学习复杂网络协议就会发现：

> 协议虽然越来越复杂，但是工程问题具有惊人的重复性。

## 十二、总结

从最开始的一颗 MCU 内部变量：

```c
uint8_t data = 0x5A;
```

到另一颗 MCU 最终重新得到 `0x5A`，中间经历的过程远比"把数据发过去"这句话复杂得多。

我们首先需要把内存中的逻辑数字转换成为高电平、低电平，于是建立了 `电平 → Bit`。

接下来多个 Bit 需要组合，于是出现 `Bit → Byte`。

当多个 Byte 连续传输的时候，需要知道什么时候开始、什么时候结束，于是出现 `Byte → Frame`。

一条 Frame 还需要描述：

```
地址
命令
长度
序号
Payload
CRC
```

于是得到 `Frame → Packet`。

Packet 最终表达：

```
设置电机转速
读取温度
升级固件
返回状态
```

于是形成 `Packet → Message`。

而多个设备、多个总线、多个软件任务组合以后，最终构成一个完整的通信系统：

```
电压
 ↓
Bit
 ↓
Byte
 ↓
Frame
 ↓
Packet
 ↓
Message
 ↓
通信系统
```

回过头来看各种接口，就会发现它们并不是凭空出现的。

我们只有高低电平，于是首先能够传递一个 Bit。数据越来越多，于是产生并行通信。引脚数量越来越多，于是开始串行化。串行以后无法判断什么时候采样，于是产生两条路线：

```
不发送时钟
→ UART

发送时钟
→ SPI
```

SPI 多设备需要大量 CS，于是引入：

```
地址
共享总线
开漏
START
STOP
ACK
```

逐渐形成 I²C。

板内电平无法可靠跨越几十米，于是开始使用差分信号，产生 RS-485 这类物理层方案。

多个节点同时发送会冲突，于是 CAN 进一步加入：

```
显性位
隐性位
无破坏仲裁
CRC
ACK
错误隔离
```

Byte 能够传输了，但是业务还是无法表达，于是软件层继续增加：

```
Header
Address
Command
Length
Sequence
Payload
CRC
ACK
Timeout
Retransmission
```

最终形成真正的通信协议。

数据速率进一步提高以后，CPU 无法再逐字节搬运，于是又产生：

```
FIFO
Interrupt
DMA
Ring Buffer
Double Buffer
```

因此，学习 MCU 通信真正需要建立的并不是"背接口"的思维，而是"解决问题"的思维。我们应该始终问：

```
Bit如何表示？
什么时候采样？
一帧如何划分？
数据发给谁？
谁拥有发送权？
错误如何发现和恢复？
CPU如何高效处理？
```

只要能够围绕这些问题进行推导，就会发现 UART、SPI、I²C、RS-485、CAN 甚至后面的 USB、Ethernet、Bluetooth、Wi-Fi，本质上都能够放进同一套通信认知框架之中。

最终，从 MCU 通信角度看，复杂协议世界所做的事情，依然可以归结成为一句非常简单的话：

> 把发送端内部的一串 0 和 1，在真实并不完美的物理世界中，尽可能高效、可靠并且有秩序地交给接收端。
