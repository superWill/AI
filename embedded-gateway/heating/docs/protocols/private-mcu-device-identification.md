# 私有 MCU 协议设备识别

> 场景:网关通过 UART/RS485/CAN 等链路接入厂家控制器或自研 MCU 板时,对方可能不跑 Modbus,而是使用私有帧协议。网关必须先知道"这是谁、是什么设备、支持什么能力",再加载对应点表和控制模板。

## 核心原则

协议里应该有设备识别能力。设备类型可以放在每帧里,也可以放在"查询设备信息"响应里。更推荐后者:地址负责标识"谁在说话",握手阶段返回设备类型、型号和协议版本,网关再把地址绑定到设备模板。

不要只靠一个 `device_type` 字段做控制决策。工程上至少要同时看:设备地址、设备类型、型号、协议版本、唯一 ID、能力位图和本地配置点表。

## 推荐启动流程

1. 网关扫描或点名地址。
2. 网关发送查询设备信息命令。
3. MCU 返回设备类型、型号、版本、序列号和能力位图。
4. 网关按 `device_type + model + protocol_version` 加载设备模板。
5. 网关按模板解析后续数据帧,并把字段映射到统一点表。
6. 控制输出前再次经过限幅、互锁、权限、回读确认和失联回退。

## 示例帧格式

```text
AA 55 | addr | cmd | len | payload... | crc16
帧头    地址   命令   长度   数据         校验
```

查询设备信息:

```text
网关 -> MCU:
AA 55 01 01 00 CRC
      地址 命令 长度

MCU -> 网关:
AA 55 01 81 0A 10 02 00 01 12 34 00 05 CRC
      地址 响应 长度 类型 型号 协议版本 设备ID 能力位图
```

字段含义:

| 字段 | 示例 | 含义 |
|---|---:|---|
| `addr` | `0x01` | 总线地址或逻辑地址 |
| `cmd` | `0x01` / `0x81` | 查询设备信息 / 查询响应 |
| `device_type` | `0x10` | 设备大类,如温控器 |
| `model` | `0x02` | 同类设备下的具体型号 |
| `protocol_version` | `0x0001` | 解析规则版本 |
| `device_id` | `0x1234` | 设备唯一编号或短 ID |
| `capability` | `0x0005` | 能力位图,如支持温度采集和继电器输出 |

## 设备类型示例

| 类型码 | 设备类型 | 典型点位 |
|---:|---|---|
| `0x01` | 温度传感器 | 温度、状态、故障码 |
| `0x02` | 压力传感器 | 压力、状态、量程 |
| `0x03` | 阀门控制器 | 开度指令、开度反馈、到位状态、故障 |
| `0x04` | 水泵控制器 | 启停、运行反馈、故障、频率 |
| `0x05` | 电表 | 电压、电流、功率、电能 |
| `0x10` | 温控器 | 温度、设定值、继电器状态、模式 |
| `0x20` | 安全 IO 板 | DI、DO、急停、联锁状态 |

## 模板绑定

网关识别设备后,不要让业务代码直接解析字节。应绑定到模板:

```json
{
  "device_type": "thermostat",
  "model": "0x02",
  "protocol_version": 1,
  "points": [
    { "id": "room_temp", "offset": 0, "type": "u16", "scale": 0.1, "unit": "C" },
    { "id": "setpoint", "offset": 2, "type": "u16", "scale": 0.1, "unit": "C" },
    { "id": "relay_state", "offset": 4, "type": "u8", "unit": "bool" }
  ]
}
```

同样是"温控器",不同厂家或不同固件版本的 payload 布局可能不同。模板必须带型号和协议版本,升级时不能默认兼容。

## 稳定性和安全要求

- 未识别设备只能进入 `unknown` 状态,不能自动控制。
- 设备类型变化、型号变化、协议版本不匹配时,必须报警并停止自动输出。
- CRC 错、长度错、命令不支持、版本不支持都要明确给质量码。
- 控制命令必须有序号和 ACK,必要时回读确认执行结果。
- 安全相关输出不能只相信 MCU 自报类型,还要受本地点表、联锁和人工配置约束。
- 广播发现可以带设备类型,但控制命令必须点名地址或唯一 ID。
