# 热源边缘网关产品需求文档

> 文档用途：先把“我们要做什么产品、第一期做到什么程度、哪些能力后置”梳理清楚，供产品调研、研发排期、领导汇报和后续测试验收使用。  
> 当前版本：需求澄清版  
> 适用场景：供暖公司热源站、换热站、设备间的数据采集、现场展示、普通控制、平台上报和安全兜底。

## 1. 产品一句话

做一台面向热源站/换热站的低成本边缘网关：在现场稳定采集温度、压力、泵阀、报警等数据，完成本地展示、简单控制、MQTT 上报，并通过 MCU 做安全兜底。

## 2. 为什么要做

供暖现场常见问题不是“没有单个传感器”，而是现场设备分散、协议不统一、数据不上平台、异常不易定位、控制依赖人工经验。

当前要解决的核心问题：

- 现场数据看不全：温度、压力、泵阀、报警分散在不同设备里。
- 设备语言不统一：DAQ、Modbus、串口、MCU、PLC、厂家协议各说各话。
- 现场缺少统一 HMI：调试和运维人员不能快速看到设备状态。
- 平台不知道现场实时状态：缺少心跳、遥测、报警、控制回执。
- 断网或主控异常时缺少安全兜底：需要 MCU 做看门狗和安全保护。
- 工控机方案偏重：很多站点只需要采集、控制、展示和上报，用完整工控机成本和维护都偏高。

## 3. 产品定位

本产品不是完整 SCADA，也不是单纯采集卡，更不是替代所有 PLC/MCU 的万能控制器。

它的定位是：

```text
现场协议适配器
+ 标准点位转换器
+ 本地 HMI
+ MQTT 网关
+ 轻量控制器
+ MCU 安全协同节点
```

推荐分层：

| 层级 | 角色 | 典型内容 | 主要职责 |
|---|---|---|---|
| 现场设备层 | 被采集和被控制对象 | 温度、压力、流量、水泵、阀门、锅炉/热泵、报警输入 | 产生数据，执行动作 |
| 安全采集层 | MCU/DAQ/IO 模块 | MCU、DAQ4212、AI/DI 模块、继电器 | 采集信号，安全兜底 |
| 边缘网关层 | RK3506/RK3568 | 采集服务、HMI、MQTT、配置、日志、缓存 | 数据标准化、本地展示、普通控制、上平台 |
| 平台应用层 | 云/私有平台 | MQTT Broker、设备管理、报警、报表、优化策略 | 跨站点分析、远程运维、优化调度 |

核心原则：

```text
MCU 保安全
RK 管现场
平台做优化
```

## 4. 目标用户

### 4.1 现场运维人员

关心：

- 当前温度、压力、泵阀状态是否正常。
- 是否有报警。
- 设备是否在线。
- 能否在现场快速查看和简单操作。
- 出故障时能否定位是传感器、设备、网络还是平台问题。

### 4.2 供暖公司管理人员

关心：

- 各热源站是否在线。
- 能耗和供暖效果是否可追踪。
- 是否能远程看到报警和运行状态。
- 是否能降低人工巡检成本。
- 后续是否能做节能优化。

### 4.3 平台/软件研发人员

关心：

- 设备数据格式是否统一。
- MQTT topic 和 payload 是否稳定。
- 命令下发是否有回执。
- 离线补传和状态同步是否可靠。

### 4.4 嵌入式/硬件研发人员

关心：

- DAQ、MCU、Modbus、串口、网口是否稳定。
- 服务是否能长期运行。
- 异常是否可恢复。
- 日志和测试是否能支撑问题定位。

## 5. 一期 MVP 范围

一期目标不是做一个功能很全的平台，而是做一个可长期运行、可演示、可验证的热源边缘采集控制闭环。

### 5.1 必须实现

| 模块 | 需求 | 说明 |
|---|---|---|
| DAQ 采集 | 接入 DAQ4212，读取至少一路温度传感器 | 当前已打通温度链路，下一步要稳定化 |
| 标准点位 | 把 DAQ 原始值转换成标准点位 | 包含 `point_id/name/value/unit/status/quality/timestamp/source` |
| 本地 HMI | 展示温度、设备状态、报警、网络状态 | 第一版可以是轻量 Web 页面 |
| MQTT 心跳 | 周期上报设备在线状态 | 平台能判断设备在线/离线 |
| MQTT 遥测 | 周期上报标准点位 | 至少包含温度点位 |
| MQTT 报警 | 上报报警发生和恢复 | 支持阈值报警和通信异常 |
| MCU 看门狗 | RK 周期性向 MCU 发心跳 | 第一版可以先定义协议并模拟，后续接真实 MCU |
| 简单控制策略 | 支持基础规则判断 | 例如温度超过阈值报警，控制动作先以模拟/日志为主 |
| 本地日志 | 记录采集、MQTT、报警、控制和异常 | 支持现场问题追踪 |
| 配置文件 | 点位、量程、阈值、MQTT 地址可配置 | 不把现场差异写死在代码里 |

### 5.2 一期暂不做

| 能力 | 暂不做原因 | 后续阶段 |
|---|---|---|
| 多路视频 AI 分析 | 会显著拉高硬件和软件复杂度 | 三期或高配版 |
| 完整规则引擎 | 一期先验证固定策略闭环 | 二期 |
| OPC UA Server | 第一阶段优先 Modbus/MQTT | 二期/大客户定制 |
| Docker 化全套部署 | RK3506 不适合重容器方案 | RK3568 标准版 |
| 多租户权限 | 先做设备能力验证 | 平台阶段 |
| 大规模 OTA | 一期先保留升级接口和脚本 | 二期 |
| 多品牌 PLC 全覆盖 | 先做可复用协议框架 | 按项目扩展 |

## 6. 核心业务场景

### 6.1 场景 A：现场温度采集和展示

目标：现场人员可以在本地 HMI 看到温度值和采集状态。

流程：

```text
温度传感器
  -> DAQ4212
  -> RK DAQ 适配器
  -> 标准点位
  -> 本地 HMI
```

验收标准：

- 温度值可以稳定刷新。
- 页面能显示单位、采集时间、数据质量。
- DAQ 断开时页面显示通信异常，而不是继续显示旧值为正常。

### 6.2 场景 B：数据上报平台

目标：平台能看到设备在线状态和温度遥测数据。

流程：

```text
标准点位
  -> MQTT telemetry
  -> 平台消费
  -> 平台展示/存储
```

验收标准：

- RK 每隔固定周期上报 heartbeat。
- RK 每隔固定周期上报 telemetry。
- MQTT 断开后自动重连。
- 网络恢复后能继续上报。

### 6.3 场景 C：报警判断

目标：温度超过阈值时，本地和平台都能看到报警。

流程：

```text
标准点位
  -> 报警规则
  -> 本地 HMI 告警
  -> MQTT alarm
```

验收标准：

- 支持高温报警阈值配置。
- 支持报警发生和恢复两类事件。
- 报警事件包含点位、值、阈值、时间戳。

### 6.4 场景 D：断网继续运行

目标：平台不可达时，现场采集、HMI 和本地安全逻辑不停止。

流程：

```text
MQTT 断开
  -> RK 继续采集
  -> HMI 继续显示
  -> 本地报警继续判断
  -> 日志记录网络异常
  -> 网络恢复后继续上报
```

验收标准：

- 断网不会导致采集进程退出。
- HMI 能显示平台离线。
- MQTT 模块能自动重连。
- 控制命令不能在恢复后盲目补执行。

### 6.5 场景 E：RK 异常时 MCU 兜底

目标：Linux 应用卡死或 RK 故障时，MCU 能进入安全状态。

流程：

```text
RK 周期性发送心跳
  -> MCU 收到心跳，允许普通控制
  -> MCU 超时未收到心跳
  -> MCU 进入安全模式
```

验收标准：

- RK 心跳周期可配置。
- MCU 超时时间可配置。
- 心跳中断后 MCU 输出安全状态。
- RK 恢复后需要重新握手，不能直接恢复高风险输出。

## 8. 非功能需求

### 8.1 稳定性

| 指标 | 一期要求 |
|---|---|
| 连续运行 | 至少 24 小时无人工干预 |
| 目标验证 | 逐步扩展到 72 小时和 7 天 |
| 进程异常 | 崩溃后能被守护进程拉起 |
| DAQ 异常 | 断开后标记异常，恢复后自动继续采集 |
| MQTT 异常 | 断开后自动重连 |

### 8.2 性能

| 指标 | 一期要求 |
|---|---|
| 采集周期 | 温度点位 1-5 秒可配置 |
| HMI 刷新 | 1-5 秒可配置 |
| 心跳周期 | 10-60 秒可配置 |
| 遥测上报 | 5-60 秒可配置 |
| CPU/内存 | RK3506 上长期运行不应明显增长 |

### 8.3 可维护性

| 指标 | 一期要求 |
|---|---|
| 配置 | 点位、阈值、MQTT 地址不写死 |
| 日志 | 采集、通信、报警、控制均有日志 |
| 部署 | 有启动、停止、状态检查脚本 |
| 诊断 | 能快速判断 DAQ、MQTT、MCU 哪一段异常 |

### 8.4 安全性

| 指标 | 一期要求 |
|---|---|
| 平台命令 | 不能绕过本地安全校验 |
| MCU 兜底 | RK 异常时 MCU 进入安全状态 |
| 远程控制 | 必须有来源、时间戳、回执 |
| 过期命令 | 不得在网络恢复后盲目执行 |

## 9. 产品版本规划

### 9.1 基础版：RK3506 + MCU

适合：

- DAQ/Modbus 采集。
- 本地 HMI。
- MQTT 上报。
- 简单控制。
- MCU 安全兜底。

不适合：

- Docker 多服务。
- 多路视频分析。
- 复杂本地数据库。
- 大规模规则引擎。

### 9.2 标准版：RK3568 + MCU

适合：

- 多协议适配。
- 本地 SQLite 历史数据。
- 更完整 Web 后台。
- 规则引擎。
- Wi-Fi/蓝牙配网。
- 轻量视频接入。
- Docker/Node-RED/Python SDK 等二次开发。

### 9.3 高配版：RK3588 + MCU

适合：

- 5 路视频本地 AI 分析。
- 本地录像缓存。
- 多模型推理。
- 更复杂边缘应用。

注意：高配版不应作为所有站点默认方案，只应在现场确实需要本地视频 AI 时使用。

## 11. 当前最近行动项

按现在“DAQ 温度已经调通”的状态，下一步建议不要先扩很多设备，而是把一条链路做成产品闭环。

优先级从高到低：

1. DAQ4212 温度采集稳定化。
2. 建立标准点位模型。
3. 建立配置文件：通道、量程、单位、阈值。
4. 本地 HMI 展示温度、DAQ 状态、MQTT 状态。
5. MQTT heartbeat 和 telemetry 上报。
6. 报警规则：温度高/通信异常。
7. 日志和状态检查脚本。
8. 每 2 小时自动 smoke test。
9. MCU 心跳协议草案。
10. 24 小时连续运行测试。

## 12. 关键待确认问题

### 12.1 现场设备

- 温度传感器最终类型是什么：热电偶、PT100、0-10V、4-20mA、数字温度计？
- 压力和流量是否也通过 DAQ，还是通过 Modbus 仪表？
- 水泵变频器品牌和协议是什么？
- 阀门控制是 4-20mA、0-10V、DO、Modbus 还是厂家协议？
- 是否已有 PLC 或锅炉/热泵控制板可对接？

### 12.2 平台协议

- MQTT Broker 地址、鉴权方式、QoS、TLS 是否确定？
- 平台需要怎样的 topic 和 payload？
- 平台是否支持命令下发和回执？
- 离线数据需要补传多久？

### 12.3 安全策略

- 哪些报警必须由 MCU 直接兜底？
- RK 心跳超时后 MCU 应该执行哪些动作？
- 哪些控制命令必须禁止远程执行？
- 本地手动/自动/远程模式如何切换？

### 12.4 产品形态

- 第一版硬件目标是 RK3506 还是 RK3568？
- 是否必须有本地屏？
- 是否需要 Wi-Fi/蓝牙配网？
- 是否需要 4G/5G 兜底？
- 是否第一期就要考虑视频？

## 13. 决策建议

第一期建议明确为：

```text
低成本热源边缘采集控制器 MVP
```

第一期核心闭环：

```text
DAQ 温度采集
  -> 标准点位
  -> 本地 HMI
  -> MQTT 上报
  -> 报警判断
  -> 日志记录
  -> MCU 心跳兜底
```

第一期成功标准：

```text
不是接了多少设备，
而是这条链路能不能长期稳定运行、异常可恢复、平台可观测、现场可维护。
```
