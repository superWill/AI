# 热源控制网关 · 设计辩论与决策记录

> 用途：记录"资深产品经理"与"资深热力行业架构师"在本产品定位与实现上的争论，以及最终裁决。每条裁决都会回写到 [`thermal-control-gateway-prd.md`](./thermal-control-gateway-prd.md)，作为该决定的理由存档（ADR 式）。
> 角色：
> - **老陈（产品经理）**：IoT 平台 + 硬件产品背景，关注成本、上市速度、可规模铺设、可演示、客户价值，警惕过度工程。
> - **王工（热力架构师）**：20 年换热站自控/热网调度经验，做过气候补偿与远程监控系统，关注供热物理规律、现场可运行性、故障模式、安全与运维信任。

## 第 1 回合：这产品凭什么存在？——和现成换热站自控柜的差异化

**老陈**：换热站要上平台、要远程调度、要低成本规模铺设，我们用 RK3506+MCU 做一台便宜的边缘控制终端，几百块的料就能干 PLC 自控柜几千上万的活。

**王工**：等一下。换热站自动控制不是新东西。硕人时代、瑞纳智能、金房、唐山这些公司，气候补偿 + 远程监控 + 节能调度已经做了十几年，西门子 S7-200 SMART + 触摸屏的自控柜方案非常成熟可靠。你便宜一点，但人家成熟、有案例、出了事有人担责。**你拿一个没现场验证过的板子，去替代一个已经被验证的安全相关系统，凭什么？** 供热是民生，停热、冻管、烫伤都是事故。差异化讲不清楚，这就是用更差的东西重新发明轮子。

**老陈**：差异化在三点：① 成本——大规模铺到每个小区换热站、楼栋热力入口，自控柜太贵；② 我们有自己的热源数据平台，不想被自控柜厂商的协议和云锁死，要数据自主；③ 边缘自治 + 统一接入我们整个热源生态（和消防、热源厂同一套网关体系）。我们不是在中心大站房跟硕人正面打，是在**它们覆盖不到的、海量的小站/楼栋入口**做下沉。

**王工**：可以接受，但你得把这句话写进定位——**本产品的战场是成本敏感、需要规模下沉、且要数据自主的中小热力站/楼栋入口，不是去替换大型中心站房已有的成熟自控系统**。同时承认一个现实：在我们自己的产品没有跑满一个供暖季、拿到现场数据之前，**第一批必须是试点 + 人工值守并行**，不能当成熟产品卖。

**裁决**：
- PRD 定位章节增加"差异化与战场边界"小节：下沉到中小站/楼栋入口、成本敏感、数据自主、与热源生态统一接入；明确不正面替换大型中心站房成熟自控。
- 明确"第一个供暖季为试点验证期"，默认人工值守并行。

## 第 2 回合：控制方法——分段比例/PID，还是气候补偿曲线？

**老陈**：一期控制先做简单点，分段比例控制阀门开度，验证闭环能跑通，PID 二期再上。

**王工**：这是外行设计。二次侧供水温度控制的**主控制量根本不是反馈，是前馈**——是**室外温度补偿曲线（气候补偿）**：目标供温 = f(室外温度、时段)。换热站的热惯性极大，二次侧热时间常数动辄几十分钟、纯滞后好几分钟。你拿供温的实时偏差去做分段比例或快 PID，结果只有两种：要么剧烈振荡，要么慢到没用。**正确结构是：气候补偿曲线算出目标供温（前馈主导）+ PID 对一次侧阀门做缓慢微调（反馈修正）**，而且必须积分主导、带抗积分饱和、阀门调节速率限制和死区。

**老陈**：那一期就直接上 PID？我本来想把 PID 放二期降复杂度。

**王工**：你把复杂度放错地方了。**气候补偿曲线 + 缓慢 PID 微调，本身就是一期的最小正确形态**，不是进阶功能。真正可以分期的是：曲线的多段/分时优化、节能寻优、回水温度优化、多机组协调——那些放后面。把"PID"当高级功能后置，是因为没理解供热控制的本质。"分段比例"在这个场景不是"简单版本"，是"错误版本"。

**老陈**：行，但我要保留"可整定参数 + 可退化为手动"，怕现场调不好炸锅。

**王工**：同意。而且要承认——**这套曲线和 PID 参数没法出厂设死，每个站的换热器容量、泵特性、建筑负荷都不一样，必须现场整定**。

**裁决**：
- 控制方法改为：**气候补偿曲线（前馈）+ 一次侧阀门 PID 微调（反馈）** 作为一期标准形态；删除"分段比例作为一期方案"。
- PID 必须积分主导、抗饱和、速率限制、死区。
- 明确"曲线 + PID 参数需每站现场整定，不能出厂设死"（引出第 6 回合的调试工作流）。

## 第 3 回合：MVP 边界——"单供温环"成立吗？

**老陈**：MVP 我定的是"单条供温控制环 + 补水保护"，压差控制和循环泵调速放二期，先把一条环跑通。

**王工**：供温环**不能脱离循环单独存在**。二次侧供水温度是靠循环泵把热水送到末端、再回来换热形成的。**循环没建立、压差不够，末端根本没有流量，你测到的"供温"是没有意义的死水温度，调一次侧阀门也调不动真实供热效果。** 启动顺序的物理约束是硬的：先确认定压/补水正常 → 启循环泵 → 建立流量/压差 → 再缓慢开一次侧阀。所以**循环泵 + 压差(或至少压差监测/恒速循环) + 定压补水，是供温环能成立的前提，必须和供温环一起进 MVP，不是二期。**

**老陈**：那 MVP 不就变重了？我担心一期摊子铺太大跑不完。

**王工**：可以裁，但要裁对地方。最小可成立的闭环是：**定压补水保安全 + 循环泵把水循环起来（一期可以先恒速/工频启停，不做变频压差闭环）+ 一次侧阀门按气候补偿+PID 调供温**。也就是说——**压差的"闭环调速"可以一期不做，但循环泵的"启停与建立循环"和定压补水必须做**；否则供温环是空中楼阁。

**老陈**：这个我接受。把"循环泵启停 + 建立循环 + 定压补水"放进 P0，把"变频压差闭环调速"放 P1。

**裁决**：
- MVP（P0）调整为：定压补水 + 循环泵启停/建立循环（一期可恒速）+ 启动顺序联锁 + 气候补偿供温环。
- "变频循环泵压差闭环调速"留 P1。
- 强调启动顺序联锁是物理硬约束，不可省。

## 第 4 回合：安全责任——MCU 软件兜底，够吗？

**老陈**：安全我设计成 MCU 软件兜底：超温、超压、缺水、看门狗都由 MCU 独立处理，不依赖 Linux。

**王工**：方向对，但你把"安全"全压在软件上，这在热力行业是要出事的。真实的安全分层是：**机械安全 > 硬接线联锁 > MCU > RK**。
- **超压**：换热站按规范本来就要装**机械安全阀（泄压阀）**，超压时机械动作泄压，这是不依赖任何软件、不依赖供电的最后防线。软件超压保护是"提前降负荷避免触发安全阀"，不是超压的兜底——兜底是那个机械阀。
- **执行机构失效安全（fail-safe）**：一次侧调节阀最好选**失电关闭（弹簧复位）**型，断电即关、热源断开，这比任何 MCU 逻辑都可靠。
- **急停 / 泵故障联锁**：很多要做成**硬接线**——急停按钮直接断执行回路、变频器故障干接点直接联锁，不经过软件。
- **MCU** 的真正职责是：看门狗（RK 心跳超时进安全态）、需要逻辑判断的软保护（超温降负荷、缺水停泵防空转）、以及对 RK 输出的安全否决。
- **RK** 负责控制策略、调度、上报，不承担最后一道安全。

**老陈**：所以我那张"MCU 兜底全部安全场景"的表是错的？

**王工**：是过度依赖软件。改成四层责任表：哪些是**机械**（安全阀、失电关阀）、哪些是**硬接线**（急停、关键联锁）、哪些是**MCU**（看门狗、软保护、否决）、哪些是**RK**（策略、降级判断、上报）。这样审图、验收、出事定责才清楚。

**裁决**：
- 安全章节重构为四层：**机械 / 硬接线 / MCU / RK**，并明确机械安全阀和失电关阀优先。
- 超压的最终兜底归机械安全阀；MCU 超压保护定位为"提前降负荷"。
- 急停、关键泵故障联锁优先硬接线。
- 一次侧调节阀优先选失电关闭型（写入待确认/选型约束）。

## 第 5 回合：断网自治 vs 传感器故障——风险优先级排错了

**老陈**：断网自治是我们的卖点，平台一断现场照常运行。

**王工**：断网自治在供热场景其实**没那么难、也没那么关键**——供热是慢过程，目标曲线几十分钟才变一次，断网后 RK 拿着最后的曲线继续跑几小时完全没问题。**真正高频、真正会导致误动作的风险是传感器故障**：温度探头断线、漂移、跳变，压力变送器失效。如果供温探头悄悄漂了 10℃，你的"自治"会很自信地把阀开到底，把楼烧穿，或者把人冻着。**传感器数据校验的优先级应该高于网络自治。**

**老陈**：那我们把传感器校验提到和断网自治同等、甚至更高的位置。

**王工**：对。要有：物理量程限幅、断线检测、变化率/跳变检测、相关性校验（供回温矛盾、压力与泵态矛盾）、关键测点故障时**禁止自动调节并安全降级**。这才是自治真正的前提——**没有可信的输入，就没有资格自动控制。**

**裁决**：
- 非功能/控制需求中，把"传感器数据校验与失效安全降级"提为 P0 核心，优先级标注高于网络自治。
- 明确：关键测点（供温、关键压力）故障 → 禁止自动调节 → 安全降级/转手动并告警。

## 第 6 回合：配置文件够不够？——现场调试与整定被低估

**老陈**：现场差异用配置文件解决，点位、量程、阈值、曲线、PID 参数都可配。

**王工**：配置文件是结果，不是过程。**每个换热站投运都要现场调试整定**：测系统能力、试阀门行程与方向、试泵转向、整定补水定压值、整定气候补偿曲线斜率和截距、整定 PID。这是一套**有步骤、有安全约束的调试工作流**，不是开个 JSON 改几个数。你只给配置文件，调试人员到现场会抓瞎，或者凭感觉乱填把站搞坏。

**老陈**：那产品要交付一个调试模式 / 调试向导？

**王工**：至少要有：**调试（手动点动）模式**——能单独点动阀门、点动泵、看反馈，验证接线和方向；**曲线/参数整定界面**；**整定记录**（谁、何时、改了什么，能回溯）。而且调试模式本身要受安全约束，不能在调试时绕过缺水/超压保护。这部分是产品能不能落地的关键，不能当二期。

**裁决**：
- PRD 增加"现场调试与整定"章节，作为一期交付物的一部分。
- 增加 P0 需求：调试/点动模式（验证接线与执行方向，受安全约束）、曲线与参数整定、整定操作留痕。

## 第 7 回合：全自动 vs 顾问模式——运维信任怎么建立

**老陈**：产品目标是自动控制，减少人工。

**王工**：理想没错，但现场运维**第一年不会信任你的自动控制**，尤其我们是新产品。你直接上全自动，第一次调过头把楼烧热了或冻着了，整个项目就废了。成熟的打法是**渐进式**：先上"**顾问模式**"——系统给出建议开度/建议动作，由人确认或自动执行可选；运行一个供暖季、数据证明比人工稳、节能，再切全自动。这既建立信任，也给你攒现场数据整定参数。

**老陈**：这其实对我也有利，顾问模式是很好的采用路径和销售故事。我接受加一个"建议/顾问"模式介于手动和自动之间。

**裁决**：
- 运行模式增加"**顾问模式（建议值 + 人工确认）**"，作为手动到全自动之间的过渡，列入一期。
- 落地路线明确：试点期以顾问/人工值守并行为主，数据验证后再切全自动。

## 第 8 回合：RK3506 裸板"低成本"是不是真便宜

**老陈**：RK3506 料便宜，这是成本优势的核心。

**王工**：芯片便宜不等于产品便宜。换热站环境很恶劣：高湿、无空调、变频器 EMC 干扰强、雷击浪涌。你需要：**隔离的 AI/DI/DO、4-20mA 隔离采集、24V 工业供电、浪涌/防雷、DIN 导轨安装、宽温**。一块裸核心板加上工业级隔离载板、合规的 IO 调理，BOM 不是你想的那么低。还有**存储**——RK3506 的 `/userdata` 很小，但供热是民生，**事故复盘、纠纷举证需要保留足够时长的运行/告警/操作日志**，存储和日志策略要提前设计，否则现场出事拿不出数据。

**老陈**：那成本宣称要诚实，加"工业级载板 + 隔离 IO"进 BOM 考量，存储 retention 写进非功能需求。

**裁决**：
- 非功能需求增加"工业环境适应性"（隔离 IO、EMC/浪涌、宽温、DIN 导轨、24V 供电）。
- 增加"日志留存"要求：运行/告警/操作/急停日志需保留足够时长用于事故复盘与举证，并有空间管理策略（限量、滚动、外接存储或上传）。
- 成本优势表述改为"芯片成本低 + 规模下沉"，不夸大整机成本。
