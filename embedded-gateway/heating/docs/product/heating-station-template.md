# 热能作为第一个行业模板落地(换热站站点运行模型)

> 上游:[行业语义网关定位](industry-semantic-gateway-positioning.md)(四层架构、热能优先)。
> 下游:[设备模板设计笔记](../point-table/device-template-design-notes.md)(硬件模板 vs 业务模板)。
> 本篇补中间缺的一层:**站点运行模型**——别抽象地说"热能行业",拆成产品能配置、程序能采集、
> HMI 能展示的结构。
>
> **记忆句:热能模板不是设备列表,而是站点运行模型。**

## 1. 四层结构:站点 → 系统 → 业务设备 → 点位

```text
站点(某小区换热站)
  └ 系统(一次侧 / 二次侧 / 补水 / 循环泵 / 计量 / 通信)
      └ 业务设备(调节阀 / 循环泵 / 补水泵 / 热量表 / 压力测点…)
          └ 点位(供温 / 回温 / 压力 / 阀位 / 运行反馈 / 故障…)
```

这一步把现场从"很多线、很多寄存器"变成"可理解的运行结构"。它要让系统知道:
哪里是一次侧、哪里是二次侧、哪个点参与控制、哪个设备是执行器、哪个反馈能证明动作成功、
哪个异常要报警、哪个状态要给现场人员看。

## 2. 换热站 = 子系统模板的组合

换热站模板由子系统模板拼成;每个子系统定义 **必需点 / 建议点 / 可选点**(不强制每个项目都全):

| 子系统 | id | 核心点(必需) | 关注/告警 | HMI 卡片 |
|---|---|---|---|---|
| 一次侧 | `primary_loop` | 供温、回温、供压、(流量) | 超温、超压、阀命令-反馈偏差、热量不足、采集质量 | 供温/回温/压力/流量/阀命令/阀反馈/状态 |
| 二次侧 | `secondary_loop` | 供温、回温、供压、回压、压差 | 供温偏差、低压/高压、压差不足、回温异常、质量码 | 供温/回温/供压/回压/压差/流量/室外温度 |
| 补水 | `refill` | 供水压力、补水泵启停命令、运行反馈、故障反馈 | 低压、补水超时、缺水、泵故障、质量码非GOOD禁补 | 状态/启动原因/未启动原因/反馈/已运行时间/超时倒计时 |
| 循环泵 | `circulation` | 启停命令、运行反馈、故障反馈、频率给定、频率反馈、压差 | 压差不足、指令-反馈偏差、变频器故障、主备切换 | 泵状态/频率命令/频率反馈/压差目标/当前压差/故障码/主备 |
| 计量 | `metering` | 瞬时流量、累计热量、瞬时功率、累计电量 | 倍率/单位/大小端、累计溢出、表计离线、采集周期 | 今日热量/累计热量/瞬时流量/电耗/通信状态 |
| 通信 | `communication` | 上行在线状态 | 断网→本地自治+缓存补传 | 在线/离线 |

> 控制闭环重点在 **补水** 和 **循环泵**(执行器),两者都已对到阶段8 的写前联锁/写后回读确认:
> - 补水:`<0.25MPa` 持 5s 启动 / `>0.35MPa` 持 10s 停(回差防频繁启停);`>120s` 未恢复→停泵报警;
>   质量码非 GOOD / 缺水 / 泵故障→禁止自动补水。
> - 循环泵:压差低升频 / 高降频;频率限幅 + 变化率限制;故障泵切备用;指令-反馈偏差报警。

## 3. "添加行业模板:换热站" 应该生成什么

不是创建一个空对象,而是一次性生成**骨架**,用户再按现场逐步绑定:

```text
生成: 一次侧/二次侧/补水/循环泵/计量 卡片 + 默认点位清单 + 控制策略骨架
      + 调试清单 + MQTT 数据结构
绑定: 这个点来自哪个 AI 模块? 这个泵命令接在哪个 DO? 热量表 Modbus 地址?压力量程?
```

## 4. MVP:先跑通一条完整链,别铺大

第一版只做 **二次侧供水压力 + 补水泵 + 补水状态机 + 本地 HMI 卡片 + MQTT 上报 + 事件记录**:

```text
压力采集 → 质量码 → 补水状态机 → DO 输出 → DI 反馈 → HMI 显示 → MQTT 上报 → 事件记录
```

这条链跑通,再扩温度、阀门、循环泵、热量表。

## 5. 锚定现状:这套模型对到编译管线还差哪层(诚实)

当前 `current_draft.json` + `compiler.py` 已有的,正是**底两层**:

- ✅ **业务设备层 / 点位层**:`business_devices`(`business_template` 枚举:temperature_point /
  pressure_point / circulation_pump / makeup_pump / control_valve / heat_meter / energy_meter /
  vfd / safety_io)+ `bindings`(measurement/feedback/command/setpoint/fault/derived)→ 点位。
- ⚠️ **系统层 = 只是隐式**:子系统现在靠 `display.page`(`overview/primary_loop/secondary_loop/
  pumps/makeup/...`)弱表达,是**展示分组**,不是拥有设备的结构实体。
- ❌ **站点层不存在**:只有顶层 `industry` 字段,没有"站点"实体;一个网关=一个站点是隐含约定。
- ❌ **行业模板生成器不存在**:`current_draft.json` 是**手写**逐个 business_device,没有
  "选换热站→自动生成子系统骨架+默认点+控制骨架"的那一步。

所以这一节描述的是**目标模型**;落地路径 = 在草稿 schema 上加 `station` / `systems` 结构层
(或先把 `display.page` 升格为真正的 system 归属),再写一个换热站模板生成器产出草稿骨架,
最后仍走 `compiler → loader → app.py`。这是把"行业语义"真正做进配置层的下一步。
