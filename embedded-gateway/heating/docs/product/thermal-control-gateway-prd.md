# 热源控制网关产品文档

> 文档用途：定义"热源控制网关"这一产品做什么、第一期控制能力做到什么程度、安全责任如何划分、哪些后置。供产品立项、研发排期、领导汇报和测试验收使用。
> 当前版本：立项澄清版

## 1. 产品一句话

做一台面向换热站/热力站的**热源控制网关**：在现场以**气候补偿曲线（前馈）+ 一次侧阀门 PID 微调（反馈）**自动完成二次侧供温调节，配合定压补水与循环建立保证供热成立，用**机械/硬接线/MCU 分层安全**做不可绕过的兜底，本地可视可操作，断网能自治，联网受平台统一调度。`[决策2]`

## 2. 为什么做（控制视角）

供热现场的控制痛点不是"没有控制器"，而是：

- **调节靠人工经验**：阀门开度、泵频率多靠值班人员手调，供温波动大、能耗高。
- **安全逻辑散落各处**：超温、超压、缺水、泵故障的保护分散在 PLC、变频器、人工巡检里，责任不清。
- **本地控制与平台割裂**：要么纯本地无法远程调度，要么过度依赖平台、断网即失控。
- **离线即失控**：网络一断，自动调节和保护停摆，只能人工值守。
- **传统 PLC/工控方案偏重**：很多站点只需要"几路控制环 + 安全联锁 + 上平台"，整套 SCADA/工控机成本和维护偏高。

本产品要解决：**把供热调节做成可自动运行、可远程调度、断网可自治、安全有硬兜底的本地控制闭环。**

## 3. 产品定位与分层

本产品**不是**完整 SCADA，**不是**纯采集卡，**不是**替代所有 PLC 的万能控制器。

它的定位是：

```text
本地供热调节器（控制环 + 状态机）
+ 安全联锁执行体（与 MCU 协同）
+ 现场协议适配 / 标准点位
+ 本地 HMI（可视可操作）
+ MQTT 平台联动节点
```

分层与责任（沿用调研报告与采集 PRD 的统一分层）：

```text
MCU 保安全     —— 急停 / 超压 / 缺水 / 看门狗，独立于 Linux 运行
RK 管控制      —— 控制环、状态机、调度、HMI、上报，断网自治
平台做优化     —— 目标曲线、跨站点调度、远程运维、节能策略
```

> 控制对象、输入信号、输出控制的完整清单见 [`thermal-energy-co-controller-logic.md` §3–§5](../business/thermal-energy-co-controller-logic.md)。

### 3.1 差异化与战场边界 `[决策1]`

换热站自动控制不是新事物——硕人时代、瑞纳智能、金房等厂商的"气候补偿 + 远程监控 + 节能"，以及西门子 S7-200 SMART 等 PLC 自控柜方案，已在大型中心站房成熟运行多年、有大量现场案例。本产品**不去正面替换这些已被验证的成熟系统**。

本产品的战场是它们覆盖成本过高、难以下沉的场景：

- **中小热力站 / 楼栋热力入口的规模下沉**：自控柜单点造价高，难以铺到海量小站；本产品靠芯片成本低 + 规模化下沉切入。
- **数据自主**：不被自控柜厂商的私有协议和云锁定，数据进自有热源平台。
- **生态统一**：与热源厂、消防等同属一套 `embedded-gateway` 网关体系，统一接入与运维。

> 成本表述要诚实：优势在**芯片成本 + 规模下沉**，而非整机绝对低价——工业级隔离载板与合规 IO 会显著抬高 BOM，见 §10。
>
> **成熟度约束**：在本产品跑满一个完整供暖季、拿到现场数据之前，第一批必须按**试点 + 人工值守并行**对待，不可当成熟产品规模交付（见 §12）。

## 5. 控制范围（产品级裁剪）

工程逻辑里有完整的控制环与保护规则，产品分期落地，避免一期就追求全功能。

### 5.1 控制环（一期成立的最小闭环） `[决策2][决策3]`

供温环**不能脱离循环单独存在**：循环未建立、压差不足时末端没有流量，测到的"供温"是死水温度，调一次侧阀也调不动真实供热效果。因此**定压补水 + 循环建立 + 启动顺序联锁是供温环成立的前提，必须与供温环一同进 MVP**。

| 控制环 | 目标 | 一期形态 | 引用 |
|---|---|---|---|
| 定压补水 | 系统压力不低于安全下限 | **P0**：低压启补水/到压停/补水失败保护 | [§6.4](../business/thermal-energy-co-controller-logic.md) |
| 循环建立 | 二次侧水循环起来、末端有流量 | **P0**：循环泵启停（一期可恒速/工频）+ 启动顺序联锁 | [§8.4](../business/thermal-energy-co-controller-logic.md) |
| 供水温度控制 | 二次侧供温跟随目标曲线 | **P0**：气候补偿前馈 + 一次侧阀门 PID 微调 | [§6.1](../business/thermal-energy-co-controller-logic.md) |
| 压差控制 | 二次侧供回水压差在目标区间 | **P1**：变频泵压差闭环调速（一期先恒速循环） | [§6.2](../business/thermal-energy-co-controller-logic.md) |

> 回水温度优化（大流量小温差治理）属节能进阶，列入二期。
> **注意**：被删除的"分段比例作为一期方案"是错误形态——见 §5.4。

### 5.2 控制方法：前馈 + 反馈（不是裸 PID/分段比例） `[决策2]`

二次侧供热是**大惯性、大纯滞后**过程（热时间常数可达几十分钟、纯滞后数分钟）。用供温实时偏差直接做分段比例或快 PID 必然振荡或迟钝。正确结构是：

```text
室外温度 / 时段 ──► 气候补偿曲线（前馈，主导）──► 目标供温
                                                  │
二次侧实际供温 ──► 偏差 ──► PID（反馈，缓慢微调）──┴──► 一次侧调节阀开度
```

控制器约束（一期即需满足）：

- **积分主导 + 抗积分饱和**：滞后大，比例项不能急。
- **阀门开度限幅 + 调节速率限制 + 死区**：防频繁满行程动作与振荡。
- **气候补偿曲线 + PID 参数不能出厂设死**：每站换热器容量、泵特性、建筑负荷不同，必须现场整定（见 §6bis 现场调试与整定）。

### 5.3 运行模式 `[决策7]`

模式：自动 / **顾问** / 手动 / 远程 / 本地，外加**急停（Emergency）**。模式切换规则与优先级见 [§7](../business/thermal-energy-co-controller-logic.md)。产品硬约束：

- 任何模式下，硬保护（超压、缺水、泵故障联锁）都不可被绕过。
- 远程指令必须做权限、范围、安全校验，不能覆盖现场保护条件。
- 本地模式优先级高于远程，切换状态需在 HMI 与平台同时可见。

**顾问模式（建议值 + 人工确认）**是手动到全自动之间的过渡，列入一期：系统按控制策略算出建议开度/建议动作，由运维人员确认后执行（或可配置为自动执行）。它用于在新产品取得信任前积累现场数据、验证策略，避免第一年直接全自动一旦调过头就砸掉整个项目（见 §12 落地路线）。

### 5.4 状态机

采用工程文档建议的状态机：`上电 → 自检 → 待机 → 启动 → 运行 → 调节 → 告警 → 急停 → 待机`，详见 [§8](../business/thermal-energy-co-controller-logic.md)。一期至少打通：**自检 → 待机 → 启动 → 运行 → 调节 → 告警/急停** 的主干。

## 6. 安全责任划分（本产品核心） `[决策4][决策5]`

控制网关与纯采集网关最大的区别在于"会动设备"，因此**安全责任划分是第一性问题**。

**核心原则不是"全靠 MCU 软件兜底"，而是分层——越靠下越可靠：机械 > 硬接线 > MCU > RK。** 软件不是最后一道防线。

### 6.1 四层安全责任

| 层级 | 谁执行 | 负责什么 | 关键点 |
|---|---|---|---|
| **机械** | 安全阀、失电关闭阀 | 超压最终泄压；断电时一次侧阀关闭切断热源 | 不依赖供电与软件，是最后防线。换热站按规范本就要装机械安全阀 |
| **硬接线** | 急停回路、干接点联锁 | 急停直接断执行回路；变频器/泵故障干接点直接联锁 | 不经过软件，响应最快、最可信 |
| **MCU** | 独立 MCU | 看门狗（RK 心跳超时进安全态）；需逻辑判断的软保护（超温降负荷、缺水停泵防空转）；对 RK 输出的安全否决 | 独立于 Linux 运行 |
| **RK** | Linux 应用 | 控制策略、调度、传感器校验与降级判断、上报 | **不承担最后一道安全** |

### 6.2 典型安全场景的分层落点

| 安全场景 | 最终兜底 | 软件侧动作（MCU/RK） |
|---|---|---|
| 超压（二次侧供压越高限） | **机械安全阀**泄压 | MCU/RK 提前降泵频、停补水、降负荷，避免触发到机械阀 |
| RK/Linux 卡死或宕机 | **MCU 看门狗** | 心跳超时 → MCU 进安全态（关/减一次侧阀、按策略停泵） |
| 断电 | **失电关闭阀** | 优先选弹簧复位失电关阀，断电即切断热源 |
| 急停 | **硬接线急停回路** | RK/MCU 同步进入急停态并上报 |
| 泵故障/变频器故障/过载 | **硬接线干接点联锁** | MCU 检测停故障泵、启备用泵（若有），RK 上报 |
| 超温（一/二次侧供温越高限） | MCU 软保护 | 减/关一次侧阀，循环泵维持散热后停，上报 |
| 缺水/低压 | MCU + RK | 启补水；补水失败则停循环泵防空转 |
| **传感器故障** | RK 判定（优先级高，见 §6.3） | 降级运行或**禁止自动调节**，关键测点故障转手动/停机保护 |

> 保护规则的触发条件与处理动作清单见 [`thermal-energy-co-controller-logic.md` §10](../business/thermal-energy-co-controller-logic.md)。
>
> 关键约束：RK 心跳恢复后**必须重新握手**，MCU 不得直接恢复高风险输出；过期的远程命令在网络恢复后**不得盲目补执行**。
>
> 选型约束：一次侧调节阀**优先选失电关闭（弹簧复位）型**（见 §14.1）。

### 6.3 传感器可信度优先于网络自治 `[决策5]`

供热是慢过程，断网后 RK 拿最后的目标曲线跑数小时无碍——**网络自治不是主要风险**。真正高频、会导致误动作的是**传感器故障**：供温探头漂移 10℃，自动控制会"很自信地"把阀开到底烧穿或把楼冻着。

因此**传感器数据校验是自动控制的前提（P0），优先级高于网络自治**：

- 物理量程限幅、断线检测、变化率/跳变检测；
- 相关性校验（供回温矛盾、压力与泵态矛盾）；
- 关键测点（供温、关键压力）故障 → **禁止自动调节 → 安全降级/转手动并告警**。

**没有可信的输入，就没有资格自动控制。**

## 6bis. 现场调试与整定（一期交付物） `[决策6]`

配置文件是结果，不是过程。**每个换热站投运都要现场调试整定**：测系统能力、试阀门行程与方向、试泵转向、整定补水定压值、整定气候补偿曲线斜率/截距、整定 PID。只交付一份 JSON，调试人员到现场会抓瞎或凭感觉乱填把站搞坏。

一期必须交付：

- **调试/点动模式**：可单独点动阀门、点动泵并观察反馈，验证接线与执行方向；调试模式**不得绕过缺水/超压等保护**。
- **曲线与参数整定界面**：气候补偿曲线、补水定压值、PID 参数、限幅与死区可现场整定。
- **整定操作留痕**：谁、何时、改了什么，可回溯。

## 7. 一期 MVP 范围

一期目标：**做出一条能长期稳定运行、断网自治、安全有兜底的供热控制闭环**，而不是接入很多设备或很多控制环。

### 7.1 必须实现（P0）

| 模块 | 需求 | 说明 |
|---|---|---|
| 采集与点位 | 接入二次侧供/回温、关键压力、阀位/泵态反馈，转标准点位 | 复用采集 PRD 的点位模型 |
| 传感器校验 | 量程限幅、断线、跳变、相关性校验；关键测点故障禁自动调节 | **自动控制前提，优先级高于网络自治** `[决策5]` |
| 定压补水 | 低压启补水、到压停补水、补水失败保护 | 压力安全，供温环成立前提 |
| 循环建立 | 循环泵启停（一期可恒速/工频）+ 启动顺序联锁 | 供温环成立前提，物理硬约束 `[决策3]` |
| 供温控制环 | 气候补偿曲线（前馈）+ 一次侧阀门 PID 微调（反馈） | 一期标准形态，非"分段比例" `[决策2]` |
| 状态机 | 自检→待机→启动→运行→调节→告警→急停 主干 | 控制网关的骨架 |
| 模式切换 | 自动/**顾问**/手动 + 急停，含安全校验 | 顾问模式列入一期 `[决策7]`；远程/本地可后置 |
| 现场调试 | 点动/整定模式 + 曲线/参数整定 + 整定留痕 | 一期交付物，否则现场无法投运 `[决策6]` |
| 分层安全协同 | 机械/硬接线优先 + RK↔MCU 心跳 + MCU 看门狗/软保护 | 软件非最后防线 `[决策4]` |
| 本地 HMI | 展示供温、压力、阀位、泵态、模式、告警，支持手动操作 | 控制网关的 HMI 需可操作，不只是展示 |
| 平台联动 | 心跳/遥测/告警上报 + 目标温度/曲线下发 + 命令回执 | 控制命令必须带回执与超时 |
| 日志 | 采集、控制动作、模式切换、告警、急停、整定全记录 | 支撑现场问题追踪与事故复盘/举证 |
| 配置 | 气候补偿曲线、死区、阀门限幅、补水压力、保护阈值可配 | 现场差异不写死 |

| 视频/AI、Docker 化部署 | 高配版 RK3588 |
| 多站点远程批量调度 | 平台阶段 |

> 注意：气候补偿前馈 + PID 微调**不在暂不做之列**——它是一期供温环的标准形态（§5.2），不是高级功能。

## 8. 核心控制场景

### 8.1 场景 A：供温自动调节

```text
室外温度/时段/目标曲线 → 计算目标供温
  → 读二次侧实际供温 → 计算偏差
  → 调节一次侧阀门开度（带限幅、死区、调节速率限制）
  → 供温进入目标区间
```
验收：供温能跟随目标曲线收敛；阀门动作平滑不振荡；偏差进入死区后保持稳定。

### 8.2 场景 B：低压补水

```text
系统压力 < 补水启动压力 → 启补水
  → 压力到补水停止压力 → 停补水
  → 长时间补不上压 → 判泄漏/补水故障 → 告警并停循环泵防空转
```
验收：补水启停阈值可配；补水失败能识别并保护；高压时停补水并告警。

### 8.3 场景 C：超温/超压保护

```text
供温越高限 → MCU 软保护：减/关一次侧阀，泵维持散热后停 → 锁定告警
供压越高限 → 软件提前降泵频/停补水降负荷 → 仍越限则机械安全阀泄压 → 严重停机
```
验收：超压最终由机械安全阀兜底，软件提前降负荷避免触发到机械阀；超温软保护 Linux 在/不在线都生效；告警需人工确认复位。

### 8.4 场景 D：断网自治

```text
MQTT 断开 → 控制环继续运行 → HMI 继续可视可操作
  → 本地保护继续生效 → 日志记录网络异常
  → 网络恢复后续传 → 过期远程命令不盲目补执行
```
验收：断网不停控制、不停保护；恢复后命令安全幂等。

### 8.5 场景 E：RK 异常 MCU 兜底

```text
RK 周期发心跳 → MCU 收到则允许普通控制
  → 心跳超时 → MCU 进安全态（关/减阀、按策略停泵）
  → RK 恢复 → 重新握手 → 不直接恢复高风险输出
```
验收：心跳周期/超时可配；中断后 MCU 输出安全状态；恢复需握手。

## 12. 落地路线

```text
Phase 1：可成立的供热闭环（RK3506 + MCU）
  传感器校验 → 定压补水 → 循环泵启停建立循环 → 启动顺序联锁
  → 气候补偿曲线 + 一次侧阀门 PID 微调 → 状态机主干
  → 调试/点动模式 + 现场整定 → HMI 可视可操作
  → 分层安全（机械/硬接线/MCU 看门狗）→ 24h 连续运行

Phase 2：控制能力补全
  变频泵压差闭环 → 多泵轮换/一用一备 → 远程模式 + 命令回执 → 断网缓存补传

Phase 3：平台联动与优化
  目标曲线下发 → 远程参数配置 → 节能策略 → 跨站点调度

Phase 4：按需升级
  本地历史库/规则引擎（→RK3568）或视频事件（→RK3588）
```

**试点期约定 `[决策1][决策7]`**：第一个完整供暖季为试点验证期，以**顾问模式 + 人工值守并行**运行，用现场数据整定参数、证明比人工稳定且节能后，再逐站切全自动。不在取得信任前直接规模上全自动。

第一版原则：**先把一条供热闭环（含循环、补水、安全边界）做扎实，再扩控制环和设备，不要先上重平台、Docker、视频。**

## 13. 验收标准（控制专项）

阶段验收在采集 PRD 验收清单基础上，增加控制专项：

- [ ] 启动顺序联锁正确：未建立循环/水压不足时不开一次侧阀。
- [ ] 供温按气候补偿曲线 + PID 收敛，稳态无持续振荡。
- [ ] 阀门动作受限幅、死区、速率约束，无频繁满行程动作。
- [ ] 低压补水启停正确，补水失败能保护（停泵防空转）。
- [ ] 超压触发机械安全阀泄压；软件提前降负荷避免触发到机械阀。
- [ ] 断电时一次侧阀失电关闭（若选失电关阀型）。
- [ ] 关键测点（供温/关键压力）故障 → 禁止自动调节 → 安全降级/转手动并告警。
- [ ] 急停（硬接线）在任何模式下立即生效，需人工确认复位。
- [ ] 手动/顾问模式下硬保护联锁不被绕过。
- [ ] 顾问模式给出建议且人工确认后才执行。
- [ ] RK 心跳中断后 MCU 进入安全态；恢复需重新握手。
- [ ] 断网后控制环与保护继续运行；恢复后过期命令不盲目执行。
- [ ] 远程命令有来源、超时、回执，越权/越界命令被拒绝。
- [ ] 现场整定可改曲线/PID/定压值且操作留痕。
- [ ] 连续运行 72 小时，控制动作、整定与保护全程有日志可追溯。

## 14. 关键待确认问题

控制网关相对采集网关，需额外确认控制与执行侧信息（部分已在工程文档 [§14](../business/thermal-energy-co-controller-logic.md) 确认）：

### 14.1 执行机构
- 一次侧调节阀：**调节型（0–100% 连续）还是三点浮动型（开/关/停脉冲）**？控制方式 4–20mA / 0–10V / DO 脉冲 / Modbus？有无开度反馈？`[决策2]`
- 一次侧调节阀能否选**失电关闭（弹簧复位）型**？（强烈建议，作为断电安全兜底）`[决策4]`
- 循环泵：定频还是变频？变频器品牌与协议？是否一用一备/多泵轮换？
- 补水泵/补水阀：启停方式与压力测点位置？定压方式？
- 控制输出落点：RK 直驱执行机构，还是 **MCU 执行 + RK 决策**？（决定控制环住在哪一侧）`[决策4]`

### 14.2 控制策略
- 气候补偿曲线由谁定义：平台下发整条曲线，还是给室外温度补偿参数让 RK 本地算？`[决策2]`
- 现场人工运行时的阀开度/泵频经验值、曲线斜率截距是否有参考（用于整定初值与限幅）？
- 哪些控制动作必须本地优先、禁止远程？

### 14.3 安全边界
- 超压机械安全阀的整定压力，与软件"提前降负荷"阈值的关系？`[决策4]`
- 哪些联锁走**硬接线**（急停、泵故障干接点），哪些走 MCU 软保护？需确认完整清单。`[决策4]`
- RK 心跳超时后 MCU 的具体安全输出（阀位、泵态）目标值？
- 急停的硬件形态：物理按钮 / 钥匙开关（优先硬接线）？

### 14.4 产品形态
- 一期硬件确定 RK3506 还是直接上 RK3568？
- 本地屏尺寸与是否需要触摸操作？
- 是否需要 4G/5G 兜底链路？

## 15. 决策建议

一期建议明确为：

```text
一条可成立的供热闭环 + 分层安全的热源控制终端 MVP（RK3506 + MCU），试点期顾问模式并行
```

一期核心闭环：

```text
传感器采集 + 校验（可信输入）
  → 定压补水保安全
  → 循环泵启停建立循环（一期恒速）
  → 启动顺序联锁
  → 气候补偿曲线 + 一次侧阀门 PID 微调（调供温）
  → 状态机 + 急停（硬接线）
  → 顾问/手动/自动模式 + 现场整定
  → 本地 HMI 可视可操作
  → 机械安全阀 + 硬接线联锁 + MCU 看门狗/软保护（分层兜底）
  → MQTT 上报 + 气候补偿曲线下发 + 命令回执
```

一期成功标准：

```text
不是接了多少设备、跑了多少控制环，
而是这一条供热闭环能不能长期稳定收敛、断网能自治、
输入可信（传感器故障能识别）、异常能分层保护、
现场可整定、动作全程可追溯——并在一个供暖季的试点中被现场数据证明。
```
