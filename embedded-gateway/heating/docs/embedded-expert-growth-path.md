# 嵌入式工程师成长路径：从入门到进阶（AI 协作版）

> 用途：新人带教大纲。一条从入门 → 进阶 → 专家的真实路径，**结合 AI 一起学**。
> 核心理念：**AI 能做的，人理解 + 会验收即可，不必死练；不能外包给 AI 的硬功夫和常识判断，人必须亲手磨。常识最重要。**
> 落点：每个阶段都绑到本项目真实模块（RK3506 + MCU、PID、MQTT、安全分层），边做边长。
> 版本：2026-06-03

---

## 0. 先讲清楚：AI 时代，嵌入式专家长什么样

过去培养嵌入式工程师，是把"会写寄存器配置、会查手册、会写协议解析"这些**当本事**练。
现在这些 AI 几分钟就给你初稿。**所以专家的定义变了：**

> 专家 = 能把 AI 当一个**很快但没碰过真硬件、会一本正经胡说**的实习生用——
> 让它干脏活累活，自己守住**判断、验收、根因、安全、常识**这几道它过不了的关。

AI 在嵌入式里有个根本短板：**它没有物理世界的常识**。它不知道 3.3V 的 IO 不可能量出 5V、不知道这颗传感器物理上不可能 1ms 刷新、不知道这条 PCB 走线这么长信号早衰减了。**这些"一眼看出不可能"的常识，正是嵌入式最值钱、也是 AI 最缺的能力。** 这份路径就是围绕这个分工设计的。

### 贯穿全程的「AI 协作三原则」

1. **AI 写初稿，人做验收。** 任何 AI 生成的寄存器配置/驱动/协议代码，**人必须能逐行讲清"为什么是这个值"**——讲不清就是没懂，没懂就不许合入。
2. **物理层不外包。** 量波形、看时序、定位偶发死机、判断"这个数对不对"——这些 AI 做不了，是人的立身之本，必须亲手练到成肌肉记忆。
3. **常识当裁判。** AI 给的每个答案，先用常识过一遍 sanity check（见文末清单）。**AI 会自信地错，常识是你唯一的刹车。**

## 阶段一：入门（第 0–1 月）—— 打通"代码 → 硬件"的第一条链路

**目标**：让代码真的驱动一块板子动起来，建立工具链 + 烧录 + 调试器的完整回路。

| 维度 | 内容 |
|---|---|
| 亲手练（不外包） | 装工具链、烧录、连 SWD/JTAG 单步、点灯、串口打印、按键中断。**第一次让灯亮、让串口出字，必须自己踩通。** |
| AI 帮你（理解即可） | 生成工程骨架、CMake/Makefile、启动文件解释、报错信息翻译。**人只需看懂结构、会改。** |
| 常识 sanity check | 灯不亮先想：供电对吗？引脚号对吗？复位脚状态？——而不是先改代码。 |
| 项目落点 | 在 RK3506 / MCU 上跑通最小工程，参考 [核心板 bringup 流程](hardware/core-board-custom-carrier-bringup-flow.md)。 |
| 验收标准 | 能讲清"按下按键到串口打印，中间经过了哪几层"。 |

> 入门期最大的坑：用 AI 生成一大坨能跑的代码，但**自己不知道为什么能跑**。规矩：**这一个月宁可写得慢，每一行都要懂。**

---

## 阶段二：驱动与总线（第 1–3 月）—— 学会和芯片"对话"

**目标**：能独立驱动一个没人写过库的外设。这是嵌入式的真正门槛。

| 维度 | 内容 |
|---|---|
| 亲手练（不外包） | **裸读 datasheet** 的寄存器表与时序图；用**逻辑分析仪/示波器**看 I2C/SPI/UART 真实波形；I2C 不通先量 ACK，而不是改代码碰运气。 |
| AI 帮你（理解即可） | 把 datasheet 某一节贴给 AI 让它**解释时序/寄存器含义**、生成驱动初稿、生成寄存器位定义。**人对照手册核对它有没有读错（它经常读错）。** |
| 常识 sanity check | AI 说"配这个寄存器就行"——先问：时钟使能了吗？上拉电阻有吗？电平匹配吗？**波形不会骗人，AI 会。** |
| 项目落点 | 驱一颗温度/流量传感器并接进 [初始点表](point-table/initial-point-table.md)；调通一次侧阀反馈采集，参考 [BL410 接口调试](hardware/bl410-interface-debugging.md)。 |
| 验收标准 | 拿到一颗全新芯片的 datasheet，能自己点亮它——**不慌**。 |

> 这一阶段是"AI 能做 vs 人必须做"分界最清晰的地方：
> **读懂手册写代码——AI 能帮；把探针扎上去看波形对不对——只能你自己。** 后者才是本事。

---

## 阶段三：系统与控制（第 3–6 月）—— 从"驱动一个外设"到"跑一个系统"

**目标**：理解 RTOS 在干什么、把控制环真正跑稳，建立**实时性**直觉。

| 维度 | 内容 |
|---|---|
| 亲手练（不外包） | 调一个跑飞的 PID、定位采样抖动/中断延迟、判断"实时性够不够"；理解任务优先级、临界区、为什么会丢数据。 |
| AI 帮你（理解即可） | 解释 FreeRTOS 调度器源码、生成 PID 框架、解释"为什么这里要关中断"。**人读懂上下文切换的本质即可，不必背 API。** |
| 常识 sanity check | 控制环震荡先想物理：执行器响应慢？采样太快？传感器滞后？——**控制问题常是物理问题，不是代码问题。** |
| 项目落点 | 把气候补偿（前馈）+ 一次侧阀 PID（反馈）跑稳，对照 [控制逻辑](business/thermal-energy-co-controller-logic.md) 与 [运行时循环](architecture/runtime-loops.md)。 |
| 验收标准 | 能讲清"这个控制环慢一拍/震荡，是哪一层的问题"，并能用数据证明。 |

> 关键认知：**控制和实时性的直觉，AI 给不了**——因为它没见过你这套阀门的真实响应曲线。AI 能讲 PID 公式，调稳你这台设备的是你。

---

## 阶段四：通信与可靠性（第 6–9 月）—— 让系统在真实世界里不死

**目标**：协议、容错、断网重连、掉电保护——从"能跑"到"工业级可靠"。

| 维度 | 内容 |
|---|---|
| 亲手练（不外包） | 设计/调试状态机；复现"断网那一刻丢帧"；看门狗、掉电保护、OTA 失败回滚的实测；抓真实链路的丢包/重连。 |
| AI 帮你（理解即可） | 生成协议解析代码、状态机骨架、序列化/CRC、测试用例。**人守住边界条件和异常分支的设计。** |
| 常识 sanity check | AI 写的重连逻辑——断网 3 天再上线会怎样？时间戳错乱怎么办？缓存满了呢？**异常路径是 AI 最容易漏的，也是工业现场最常发生的。** |
| 项目落点 | 实现 [MQTT 协议](protocols/mqtt-protocol-draft.md) 的遥测/事件/断网补传；MCU↔RK 通信容错，参考 [职责分配](hardware/rk3506-mcu-responsibility-split.md)。 |
| 验收标准 | 能主动列出"这个功能有哪些失效场景、各自谁兜底"。 |

---

## 阶段五：进阶 → 专家（第 9–18 月）—— 疑难、安全、架构

**目标**：能定位别人定位不了的偶发 bug；能做安全/可靠性的架构判断。这是专家的分水岭。

| 维度 | 内容 |
|---|---|
| 亲手练（不外包） | **偶发死机/复位的根因定位**（栈溢出？时钟毛刺？DMA 竞争？errata？）；**安全失效思维**；架构取舍；带新人复盘。 |
| AI 帮你（理解即可） | 帮你查 errata、分析 core dump/寄存器现场、列假设清单、解释一段晦涩的 reference manual。**它是你的"假设生成器"，不是结论。** |
| 常识 sanity check | 最难的 bug，AI 几乎一定给不出答案（因为它没你的现场）。**这时拼的是你"假设 → 仪器验证 → 二分定位"的科学调试法，AI 只能陪你列假设。** |
| 项目落点 | 守住 [安全规则](safety/safety-rules-draft.md) 的 `机械 > 硬接线 > MCU > RK` 分层；处理 [RK3506 NAND 开发问题](hardware/RK3506-IOT_NAND-development-issues.md) 这类真实疑难。 |
| 验收标准 | 换一颗芯片、换一个行业也能快速上手——**会的不是这个项目，是方法。** |

> 安全这一条要单独强调：**软件永远不是最后一道防线**。你们的 `valid_until` 超时回退本地策略、平台失联自治，就是这种思维的体现。**这种对失效的敬畏，AI 不会主动提醒你——它只会把你要的功能写出来，不会告诉你"它坏了会烧锅炉"。**

## 「人 vs AI」分工总表（一页速查）

| 工作 | 谁主导 | 人要达到的程度 |
|---|---|---|
| 写样板/驱动/协议初稿 | 🤖 AI | 看得懂、能逐行讲清、会改 |
| 解读 datasheet / 源码 | 🤖 AI 初读，👤 人核对 | 不盲信，对照手册查它有没有读错 |
| 查 errata / 列假设 | 🤖 AI | 当线索，不当结论 |
| 写测试用例 | 🤖 AI | 守住边界与异常分支 |
| **量波形 / 看时序** | 👤 **人** | **核心立身技能，必须精** |
| **偶发 bug 根因定位** | 👤 **人** | **科学调试法，专家分水岭** |
| **实时性 / 控制调参** | 👤 **人** | **物理直觉，AI 给不了** |
| **安全 / 失效判断** | 👤 **人** | **对失效的敬畏，AI 不会提醒** |
| **常识 sanity check** | 👤 **人** | **AI 唯一的刹车** |

> 一句话：**AI 把"会查会写"贬值了，把"判断、动手、常识"升值了。** 这份路径就是少花时间在前者、把人逼向后者。

## 常识 Sanity-Check 清单（贴在工位上）

每次 AI 给你答案、或现象不对时，先过一遍：

1. **电气合理吗？** 电压/电平/电流/上拉，物理上可能吗？（3.3V 量不出 5V）
2. **时间合理吗？** 这个刷新率/响应时间，器件物理上做得到吗？
3. **数量级对吗？** 温度 800℃？流量负数？——**先怀疑数据，别先信。**
4. **波形 > 日志 > 猜测。** 能量就别 print，能 print 就别猜。
5. **改之前先复现。** 不能稳定复现的 bug，改了也不知道好没好。
6. **它坏了会怎样？谁兜底？** 每个功能都问一遍。
7. **AI 这段，我能讲清为什么吗？** 讲不清 = 不许合入。

## 配套习惯（团队铁规矩）

- **踩坑库**：每个非平凡 bug 写一句"根因 + 当时为什么没想到"，攒成团队 know-how。
- **讲给我听**：定期讲自己的设计，讲不清就是没真懂。
- **够得着的失败**：放手让他自己栽一次坑、自己爬出来，我在评审和上电前兜底。
- **精读不泛读**：一颗主芯片 reference manual 读穿、一个 RTOS 调度器读懂，胜过翻十本书。
