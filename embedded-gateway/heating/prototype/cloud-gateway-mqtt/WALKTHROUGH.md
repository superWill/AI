# 工业机网关 ↔ 平台 通讯流程（小白版）

> 讲清楚：现场的工业机（网关）怎么把数据传给平台、又怎么接收平台的命令。
> **只有两个角色：网关 和 平台。** 尽量大白话，不懂编程也能看明白。
> 配套文件：`gateway_mqtt.py`（装在工业机上的程序）、`parse_stream.py`（平台侧读数据示例）

---

# 一、就两个角色：网关 和 平台

```
   网关（现场工业机）  ◄──────► 平台（云端）
   - 采集温度/流量             - 收数据、存数据
   - 上报数据                  - 做分析/优化
   - 接收并执行命令            - 下发命令
                              └─ 里面有个「收发室」负责收发消息
```

| 角色 | 是谁 | 干什么 |
|---|---|---|
| **网关** | 现场的工业机（BL412B） | 采集现场数据 → 上报；收平台命令 → 执行 → 回执 |
| **平台** | 云端服务器 | 接收/存储数据、跑优化算法、下发设定值 |

## 那个「收发室」（技术名 broker）是什么

网关和平台之间用的通讯方式叫 **MQTT**，它有个规定：**双方不直接对话，消息都先经过一个"收发室"。**

> ⚠️ 关键：**这个收发室是平台的一部分，不是第三方。**
> 就像你给公司寄文件，是寄到"公司的收发室"——收发室属于这家公司。

所以还是**两个角色**。"收发室"只是平台对外收发消息的那个口子，技术上叫 **broker**，跑在平台服务器上。

# 二、通讯流程（数据怎么来回跑）

```
┌──────────────────┐                         ┌──────────────────────────────┐
│  网关（工业机）    │                         │  平台（云端）                  │
│                  │   ① 上报数据             │  ┌──────────┐   ┌──────────┐ │
│  采集 ──────────►│ ──────────────────────► │  │ 收发室    │──►│ 业务系统  │ │
│                  │      (每30秒一次)        │  │ (broker) │   │ 存/算/决策│ │
│                  │                         │  │          │◄──│          │ │
│  执行 ◄──────────│   ② 下发命令             │  └──────────┘   └──────────┘ │
│      │           │ ◄────────────────────── │                              │
│      └───────────│   ③ 回执（执行结果）      │                              │
│                  │ ──────────────────────► │                              │
└──────────────────┘                         └──────────────────────────────┘
```

**① 上行（网关 → 平台）**：网关每隔 30 秒，把测到的温度、流量等数据"寄"到平台收发室，平台业务系统收下、存库、分析。

**② 下行（平台 → 网关）**：平台算出"该把供水温度设成 50℃"，把命令发给收发室，网关一直"守"着收发室、收到就执行。

**③ 回执（网关 → 平台）**：网关执行完，回一条"收到了/做到了/被安全拦下了"，让平台知道命令落地没有。

> 上行、下行用的是不同的"频道地址"，互不打架（下一节讲地址）。

---

# 三、网关侧要做什么（工业机上）

就跑一个程序 `gateway_mqtt.py`，它自动干三件事：定时上报、守着收命令、执行后回执。

**唯一要配的**：告诉它平台在哪。打开 `config.json`，改这一行：

```json
"broker_host": "平台的地址",
"broker_port": 1883
```

- 测试时填的是临时假平台的地址（局域网 IP）。
- **真上线就填平台的公网域名或 IP**，工业机通过 4G/以太网连过去。**程序代码一行都不用改，只改这个地址。**

然后启动（让它在后台一直跑）：
```bash
python3 gateway_mqtt.py --config config.json -v
```

> 现在程序里上报的是**写死的假数据**（演示用）。真接现场时，改 `gateway_mqtt.py` 里 `read_points()` 那一段，让它去读真实传感器/MCU 的值即可——其它都不用动。

---

# 四、平台侧要有什么

平台只要具备两样：

1. **一个收发室（broker）**——接收所有网关来的数据、转发命令。开源的 mosquitto、EMQX 都行；云厂商也有现成的（阿里云 IoT、AWS IoT 等）。
2. **一套业务系统**——从收发室拿数据存进数据库、跑优化算法、把决策结果当命令发回去。

> 测试时我们用一台机器装了最简单的 broker（mosquitto）来**临时假装平台**，验证网关能正常上报和收命令。真实平台把"收发室"换成正式的、把"业务系统"补上就行，**网关侧完全不变**。

# 五、数据长什么样、怎么读懂

## 每条消息都有个「地址」

```
station / stn-001 / telemetry
  固定     哪个网关    什么内容
```

`telemetry` = 上报的测量数据。其它地址：`heartbeat`(报平安)、`command_reply`(命令回执)、`alarm`(报警)、`property/set`(平台下发命令)。

## 一条「数据」长这样

```json
{
  "device_id": "stn-001",          // 哪个网关发的
  "ts": 1780463433508,             // 什么时候测的（时间戳）
  "clock_sync": "synced",          // 网关的表准不准
  "seq": 6,                        // 第几条（流水号）
  "points": {                      // 各项测量值
    "pri_supply_temp": { "v": 78.4, "q": "good" },   // 一次供水温 78.4℃，质量"好"
    "sec_supply_temp": { "v": 52.3, "q": "good" }
  }
}
```

## 平台读数据要记住 4 件事

**① 时间看 `ts`，不看"收到的时间"。**
数据可能因断网晚到，以它自带的测量时刻为准。（`ts` 是一串数字，电脑能换算成几点几分。）

**② 用 `seq`（流水号）查有没有漏。**
上条是 6、这条该是 7；要是跳到 9，说明中间漏了 7、8。

**③ 看到 `replay: true` 是"补送的旧数据"。**
网关断网时先把数据存着，恢复后补送，会标 `replay`。存档时按它的原始时间放，**别当成最新值**。

**④ 用数前先看 `q`（质量）。**
`good`好放心用 / `stale`有点旧 / `bad`传感器坏了别用 / `est`网关猜的仅参考 / `manual`人工填的别算。
> 一句话：**`v` 是数值，`q` 是这数值可不可信，永远先看 `q` 再用 `v`。**

## 另外两种消息

**报平安（heartbeat）**，每分钟一次：
```json
{ "device_id":"stn-001", "online":true, "buffer":0 }
```
`buffer` = 积压了多少没发出去的数据。`0`=健康；数字大=网络可能在断。

**命令回执（command_reply）**，平台下命令后网关的回复：
```json
{ "command_id":"set-001", "status":"accepted", "reason":"" }
```
`status`：`accepted`接受 / `success`成功 / `blocked_by_safety`被安全规则拦下（`reason`说明原因）。

## 想亲眼看解析效果

平台侧用 `parse_stream.py` 能把原始数据**翻译成人话**：

```bash
mosquitto_sub -h 平台地址 -t 'station/#' -v | python3 parse_stream.py
```

实测输出：
```
[05:21:04] stn-001 遥测 seq=27 sync=synced 点数=7
        pri_supply_temp   =     78.4  (good)
        sec_supply_temp   =     52.3  (good)
[05:21:04] stn-001 心跳 online=True buffer=0
[05:21:34] stn-001 遥测 seq=28 ...        ← 流水号 27→28 连着，没漏数据
```

它就是把上面 4 件事做了一遍。真实平台把"打印"换成"存数据库"即可。

# 六、从测试到真实上线：只改一个地址

| | 测试（我们验过的） | 真实上线 |
|---|---|---|
| 网关 | 工业机 BL412B | 工业机（不变） |
| 平台 | 一台机器临时装 mosquitto 假装 | 正式云平台（broker + 业务系统） |
| `broker_host` | 局域网地址 | 平台公网域名/IP |
| 网络 | 一根网线 | 4G / 以太网 / 专网 |
| 程序代码 | —— | **完全不用改** |
| 上报数据 | 写死的假数据 | 改 `read_points()` 接真实传感器 |

**核心结论**：网关程序写好后，对接不同平台**只改 `config.json` 里的 `broker_host` 一行**。上报真实数据只改 `read_points()` 一处。其余的上报/收命令/回执/断网补传逻辑都已就绪。

# 附：测试时网络是怎么搭的（仅测试细节，可跳过）

测试时网关和"假平台"在同一个局域网，用网线直连，所以多了一步"配网络让两台机器互相看见"（给网口分配地址、加路由）。**真实上线时网关直接连平台公网地址，没有这一步。** 这部分纯属测试环境的临时搭法，不影响你理解通讯架构。
