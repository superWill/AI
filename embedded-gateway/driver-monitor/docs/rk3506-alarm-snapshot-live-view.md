# 产品方案：RK3506 烟感抓拍上云 + 手机看直播

> 平台：RK3506（供热/工业网关，无 VPU/NPU/外网）。复用已建并真机验证的媒体上行管线。
> 定位：在 RK3506 网关上，叠加"烟雾报警实时抓图上云 + 手机看实时视频"两项能力，控制业务不变。
> 更新日期：2026-07-10。

## 1. 目标与非目标

**目标（本方案交付）：**
1. **烟雾报警实时抓拍上云**：烟感触发的瞬间，抓一张现场 JPEG 快照，上传云端（OSS），手机可看。
2. **手机看实时视频**：手机拉流看摄像头直播（本地/远程）。
3. **控制业务不受影响**：RK3506 原有 Modbus 采集 / 设定值下发 / HMI / MQTT 照常。

**非目标（明确不做，避免范围蔓延）：**
- ❌ **AI 检测**（人体/人脸/行为）——RK3506 无 NPU，本方案不含。需要则另配视觉盒（RK3568/BL410）。
- ❌ **视频转码**——RK3506 无 VPU。摄像头必须出 H.264，全程 passthrough 不转码。
- ❌ **连续 7×24 视频上云 / 云录像**——带宽与成本另议；本方案只上"报警快照"，不上连续流。
- ❌ **NVR / 集中录像**——如需连续录像，用摄像头 SD 卡，本方案不含 NVR。

## 2. 三个前提（必须先满足，否则方案不成立）

1. **摄像头子码流设为 H.264**（主码流可留 H.265 录 SD）。浏览器/passthrough 只吃 H.264。
2. **摄像头提供 JPEG 快照接口**（ONVIF `GetSnapshotUri` 或厂家 JPEG CGI）。抓图靠它，不解码。
3. **一个有外网的节点**（下称"网关代理"，现用小龙虾）：承担 ①快照上云出口 ②远程看直播的公网入口。RK3506 无外网，这条绕不过。

## 3. 系统架构

```
烟感 ─(DI/Modbus/LoRa)─► RK3506 ◄─(RTSP 子码流 H.264 / ONVIF snapshot)─ IP 摄像头
                          │                                              └(主码流→SD 卡,可选连续录像)
             报警 ────────┤─► GET snapshot.jpg → 板子侧 spool ─┐
                          │                                    │ 本地网
             手机看 ──────┴─► go2rtc 拉子码流 passthrough        │
                              → WebRTC(本地手机浏览器)           ▼
                                                          网关代理(小龙虾,有外网)
                                                          ├─ media_agent → OSS(快照,presign 给人看)
                                                          └─(远程看)go2rtc/中转 → 手机(4G)
```

**职责划分**：RK3506 = 报警触发 + 抓图 + 本地视频 passthrough + 控制；代理节点 = 上云出口 + 远程视频入口；OSS = 快照持久存储。

## 4. 硬件清单（BOM）

| 件 | 数量 | 说明 |
|---|---|---|
| RK3506 网关 | 1 | 内存 512MB 够；要余量上 1GB（RK3506B/J，上限 1GB）。存储 8GB 足够（含落盘缓冲） |
| IP 摄像头（H.264 双码流 + ONVIF snapshot；连续录像加 SD 卡） | 按点位 | 雄迈等；子码流设 H.264 |
| 网关代理（有外网、双网卡的小机器） | 1 | 现用小龙虾；跑 media_agent + （远程时）go2rtc |

| 云：阿里云 OSS | — | 存快照（`ubuntu-oss-313`）；远程看另配端口转发/内网穿透 |

**不采购**：AI 摄像头、视觉盒、NVR（本方案不涉及 AI/连续录像）。

## 5. 功能规格

### 5.1 烟雾报警抓拍上云

- **触发**：烟感信号进 RK3506（DI/GPIO 电平、或 Modbus 寄存器、或 LoRa 上报）。RK3506 本行。实现见 `src/alarm/alarm_source.py`（MVP 用 `FileAlarmSource`，`touch` 触发文件模拟；真硬件替换）。
- **抓图**：RK3506 `HTTP GET` 摄像头快照 → 得一张 JPEG（**不解码**，只下载字节）。**实测接口（雄迈 .217）**：`http://192.168.1.217/webcapture.jpg?command=snap&channel=0`（HTTP Basic `admin:` 空口令）→ 200 image/jpeg ~80KB。实现 `src/alarm/snapshot.py::HttpSnapshotGrabber`。
- **上传**：JPEG 入板子侧 spool（`MediaOutbox` + `RelayUploader`）→ ship 到代理 → `media_agent` → OSS。key 确定性，可预算 URL。编排见 `src/alarm/pipeline.py::AlarmSnapshotPipeline`，入口 `scripts/alarm_snapshot_rk3506.py`。
- **离线不丢**：代理/网络不可达时留本地队列（8GB 落盘），恢复后按序补传（已真机验证）。
- **查看**：`presign_get` 生成临时 URL，手机/平台点开即看那张报警图。
- **时效**：抓图=1 次 HTTP GET（几百毫秒级）；上云异步，不阻塞报警链。

### 5.2 手机看实时视频

- **媒体服务器**：**go2rtc**（单二进制，armv7 版可跑 RK3506 A7）拉摄像头子码流（H.264），**passthrough** 转 WebRTC/HLS，**on-demand**（有人看才拉流，没人看零负载；转后台可用 Page Visibility API 立即断）。
- **本地看**（手机同局域网）：go2rtc 跑在 **RK3506**，手机浏览器开 `RK3506:1984` 走 WebRTC，亚秒延迟。RK3506 512MB 跑 1 路够。
  - 备选：手机用播放器 App 直接拉摄像头 RTSP（RK3506 不进视频链，更省）。
- **远程看**（手机 4G）：RK3506 无外网 → go2rtc 改跑**代理节点**（有外网、够得着摄像头），配端口转发/内网穿透/TURN，手机从公网连。
- **码流**：AI 不需要，故用子码流即可；不转码，浏览器直接解 H.264。
- **⚠️ 实测（雄迈 .217）**：主/子码流**当前都是 H.265**（`rtsp://192.168.1.217:554/user=admin&password=&channel=1&stream=1.sdp?real_stream`，800×448/25fps）。浏览器/passthrough 播不了 H.265，RK3506 又不能转码 → **上线前必须把子码流改成 H.264**（相机 ONVIF 查到支持 H.264，web UI 改设置即可）；主码流可留 H.265 录 SD。详见 memory `xiongmai-camera-217`。

### 5.3 控制业务（不变）

RK3506 原有 Modbus/RS485 采集、设定值下发、安全校验、HMI、MQTT 上报照常。**视频/上传服务独立（独立进程 + 资源限制），不得抖动控制回路**——控制是第一职责。

## 7. 关键约束与边界（RK3506 硬限制）

1. **无外网**：上云、远程看必须经代理节点。
2. **无 VPU**：只能 passthrough H.264，**不能转码**；摄像头出 H.265 则播不了（改子码流为 H.264 解决）。
3. **无 NPU**：无 AI；报警靠烟感硬件触发，不靠视频分析。
4. **A7 算力弱**：本地视频建议 1 路；多路/多观看者需更强节点。
5. **时钟**：板子时钟若不准，OSS 直传会拒签——本方案上云走代理（时钟正确），规避；板子仍建议 NTP。

## 8. 资源预算与边界（CPU 是瓶颈，不是内存）

**绑定约束是 CPU（3×Cortex-A7 @ 1.5GHz），不是内存/存储**——512MB/1GB 内存和 8GB 存储都够，先耗尽的一定是 A7 算力。

### 各功能资源画像

| 功能 | CPU | 内存 | 网络 | 特性 |
|---|---|---|---|---|
| 控制业务 | 轻、**受保护** | 几十 MB | 小 | 常驻，第一职责，不可饿死 |
| 报警抓图上云 | 突发（一次 GET+写盘），可忽略 | 一张 JPEG + 队列 | 报警时几百 KB | 事件驱动，无连续负载 |
| **手机看视频（go2rtc passthrough）** | **连续、重、是变量** | 每流/每观看者数十 MB | 子码流码率×观看者（出） | on-demand，有人看才耗 |

### 视频的具体边界

- **1 路 + on-demand**：安全工作点。没人看 = 零负载。
- **并发观看者**：
  - **WebRTC**：每个观看者一份 **SRTP 逐包加密**，在 A7 上吃 CPU → **~1–2 人**封顶。
  - **HLS/LL-HLS**：分段**一次封装、多人共享、无逐包加密** → 多人更省，代价是 **+几秒延迟**。
  - → **多人看优先 HLS；低延迟少人用 WebRTC**。
- **多路摄像头**：每路都要持续拉流 + 重封装 → **2 路可能是实际天花板**，再多 offload 到代理/BL410。

### 隔离是硬边界（架构要求）

视频/上传**必须独立进程 + 更低调度优先级 + CPU 配额**（cgroups / `nice` / `cpulimit`），保证**视频负载永远饿不死控制回路**。控制是第一职责——宁可视频卡，不能控制抖。

### "到顶了"的信号（怎么判断越界）

- 控制回路周期**出现抖动** → 视频在抢控制的 CPU → 立即降级/停视频。
- CPU **持续 >~80%** → 到算力天花板。
- go2rtc **缓冲增长 / 丢帧 / 观看端卡顿** → 单板扛不住，该 offload。

### 存储与网络边界

- **存储 8GB**：存报警快照绰绰有余（每张几百 KB，上千张才几百 MB）；**别让视频段填满**——若做本地视频缓冲，要环形 + 封顶。
- **网络**：局域网 100M 够本地；**远程看的真瓶颈在代理节点的外网上行**（蜂窝/WiFi 上行有限），不是 RK3506。

### 安全工作点（一句话）

**RK3506 的安全边界 = 1 路视频 + on-demand + 少量观看者（多人用 HLS）+ 视频进程降级隔离 + 控制优先**。出了这个点（多路 / 多人 / 低延迟高并发），就把视频 offload 到代理或 BL410，别硬扛。

## 9. 实施与验收（测试板上分步真机验）

1. **看视频**：摄像头子码流设 H.264 → RK3506 装 go2rtc → 手机本地浏览器 WebRTC 看到画面。
2. **报警上云**：模拟报警信号 → RK3506 GET snapshot → spool ship 代理 → OSS → presign 看到图。
3. **远程看**：go2rtc 挪代理节点 + 端口转发/穿透 → 手机 4G 看到。
4. **隔离验证**：视频/上传满负载时，控制回路周期无抖动（独立进程 + 资源限制）。
5. **故障**：断代理/断网/掉电 → 报警快照留队补传不丢；视频 on-demand 无人看零负载。

## 10. 未来扩展（本方案不含，按需）

- **要 AI（人体/人脸）** → 加视觉盒 RK3568/BL410（有 VPU+NPU），RK3506 退控制面。
- **要连续录像** → 摄像头 SD 卡 或加 NVR。
- **要连续视频上云/云录像** → 代理或云端加流媒体服务器（SRS 等）+ 评估带宽成本。
- **多路视频** → 换更强节点或多节点。

## 11. 一句话

RK3506（512MB/1GB + 8GB）**能独立完成"烟感报警抓图 + 本地手机看直播 + 控制业务"**；唯一必须借外部的是"上云出口"和"远程看入口"（RK3506 无外网，交给代理节点）。**不含 AI、不转码、不做连续录像**——这三样是 RK3506 的硅/网络硬边界，需要则另配设备。
