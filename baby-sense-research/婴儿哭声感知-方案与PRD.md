# 婴儿哭声短时分析助手 — 技术方案与 PRD

> 版本 v0.4 · 2026-06-10 · 状态：草案（已含自有数据实测验证）
> v0.4 变更（定位收敛，更轻更稳）：产品改名"**婴儿哭声短时分析助手**"。v1 **不下任何 ML 判断**——只输出可测量的事实（强度/持续时长）+ 上下文表单 + 非医疗排查清单 + 反馈。L1 降级为"**录音质量检查**"；L2 紧急度与 L3 意图**全部后置**、由反馈数据驱动再评审。
> 历史：v0.3 主动式 App+主打L2；v0.2 App端侧+实测；v0.1 边缘硬件。

---

## 1. 一句话定位

**婴儿哭声短时分析助手（iOS/Android）**：宝宝哭了 → 家长打开 App 录 5–15 秒 → 本地分析 → **帮家长快速记录、分析哭声强度、按步骤排查原因，并积累个性化反馈**。

> **v1 卖点不是"翻译宝宝哭声"**，而是"哭的时候帮你冷静地记录 + 分析 + 排查 + 攒经验"。更轻、更可信、更容易上线。

主用户旅程：
```
宝宝哭 → 打开 App 录 5–15s → 本地质量检查(是不是哭声/吵不吵/够不够)
       → 强度与持续性分析(纯测量,无模型,永远准)
       → 结合上下文表单 → 非医疗排查清单(按情况排序)
       → 记录这次哭闹 → 家长反馈"最后怎么解决" → (可选)匿名捐赠音频
```

**v1 明确不输出**："宝宝饿了/困了/肚子疼"这类原因判断（公开数据撑不住，§2.4）；也不输出"要不要紧"的模型紧急度（L2 无数据，后置）。v1 只说**可测量的事实 + 按上下文排序的排查清单 + 就医红线**。

## 2. 背景与调研结论

### 2.1 技术可行性边界（核心认知）

| 能力层级 | 学术/产业现状 | **本项目实测（见 §2.4）** | 可行性 |
|---|---|---|---|
| L1 哭声事件检测（哭没哭） | CNN 类 95%+（CNN-SCNet） | **AUC 0.999，召回@5%误报 1.000±0.000**（YAMNet训练，公开数据） | ✅ 公开数据强，真实家庭待验证 |
| L2 痛苦 vs 非痛苦 | ChatterBaby 痛苦哭声 90.7% | 待自采数据验证 | ✅ 较可靠（需验证） |
| L3 具体意图（饿/困/不适/烦躁） | ChatterBaby 71.5%；论文 ~60% | **三分类 balanced acc 0.290（低于随机），公开数据≈噪声** | ⛔ 公开数据做不到，移出 MVP |
| L4 病理性哭声（窒息/脑损伤/耳聋） | 论文可达 95%（Baby Chillanto） | 不做 | ⛔ 属医疗器械，本产品不做 |

**结论（已被实测修正）：产品地基是 L1（公开数据上实测很强，真实家庭场景待验证）+ L2（赌自采真值）；L3 在公开数据下连方向都看不到，必须等 App 反馈闭环攒够自采数据后才评审上线；L4 明确排除。**

> ⚠️ **L1 实测的适用边界**：哭声来自 donateacry（近场录音），"噪声"来自 ESC-50 的 5 秒**干净剪辑**。这证明"方向可行 + 公开数据上很强"，但**不等于真实家庭场景已解决**——手机远场麦克风、家庭环境底噪、电视/人声/宠物/白噪声/安抚音乐、多声源叠加均**未测试**。对外只能说"哭声检测方向可行"，"真实家庭可用"需经真实录音验证（清单见 [`baseline/实验结果.md`](baseline/实验结果.md) 「尚未验证」）。

### 2.2 竞品扫描

| 产品 | 形态 | 哭声相关能力 | 弱点 |
|---|---|---|---|
| ChatterBaby (UCLA) | 免费 App | 痛/饿/烦躁三分类，云端推理 | 需手动触发录音，无监护硬件，录音上云 |
| CuboAi Monitor 3 | 摄像头监护器（2.5K） | 哭声/咳嗽检测告警，AI 较快 | 贵（$200+），依赖云，意图分类弱 |
| Nanit | 摄像头监护器 | 睡眠分析为主，哭声告警 | 订阅制，哭声只是附属功能 |
| Dunstan 婴语 | 方法论/课程 | 5 种反射音理论 | 无严格科学验证，非技术产品 |

**直接对标 ChatterBaby**（同为"主动录音→判断"形态）。我们的差异化：①**端侧推理、音频不上云**（ChatterBaby 上云）；②**诚实定位**——主打可靠的"要不要紧"(L2)，不像多数产品硬承诺"饿/困"翻译然后翻车；③**数据闭环**靠行为反馈攒自采数据，是后期解锁意图的唯一正路；④国内市场本地化（隐私敏感、母婴生态）。**机会：市面"婴语翻译"普遍过度承诺、口碑差，一个诚实+隐私+越用越准的产品有空间。**

| 数据集 | 规模 | 标签 | 用途 |
|---|---|---|---|
| [donateacry-corpus](https://github.com/gveres/donateacry-corpus) | 457 条 | 饿/拍嗝/困/腹痛/不适 | L3 意图分类起步（量小、用户自标、噪声大） |
| Baby Chillanto (INAOE, 墨西哥) | 2,268 条 1s 片段 | 窒息/耳聋/饿/正常/痛 | L2 痛苦分类参考（需邮件申请） |
| ICSD (2024, 开源) | 哭声+鼾声事件 | 事件检测 | L1 哭声检测训练 |
| CryCeleb (2023) | 6 千+ 段，786 婴儿 | 说话人(婴儿)身份 | 预训练/嵌入学习，非意图标签 |
| AudioSet (Google) | 海量含 "Baby cry" 类 | 事件级 | L1 预训练（YAMNet 即基于此） |

**数据结论：L1 数据充足；L2/L3 公开数据总量 < 3000 条且标注质量参差——自建数据闭环是中期壁垒，产品设计必须内置"家长反馈标注"机制。**

### 2.4 自有数据实测（2026-06-10，关键决策依据）

用 donateacry(457条/221婴儿) + ESC-50(2000条环境音)，MFCC 特征 + 逻辑回归，**严格按婴儿 ID 组切分**（杜绝同一宝宝哭声跨训练/测试泄漏）。完整报告见 [`baseline/实验结果.md`](baseline/实验结果.md)，可一键复现。

> 低误报召回为**按折 mean±std、保守口径**（满足 fpr≤目标的最高召回，不突破误报预算）。

| 实验 | MFCC 基线 | YAMNet 确认(1024维强特征) | 判定 |
|---|---|---|---|
| A) L1 哭声 vs 环境音 | AUC 0.986，召回@5% 0.917±0.053 | **AUC 0.999，召回@5% 1.000±0.000** | ✅ 公开数据强 |
| B) hungry vs rest | AUC 0.479（≈随机 0.5） | AUC 0.449（仍≈随机） | ⛔ 无可分信号 |
| C) hungry/tired/discomfort 三分类 | bal.acc 0.290（随机=0.333） | bal.acc 0.315（仍低于随机） | ⛔ 公开数据≈噪声 |
| D) 泄漏对照 | 随机切分 0.379 vs 按婴儿 0.290，虚高 +0.089 | — | 🔍 文献高分=多数类基线+泄漏+强特征 |

> **决定性证据**：从 MFCC 升级到 YAMNet，L1 从 0.986 冲到 0.999（强特征确实有用）；同样升级用在 L3 却纹丝不动钉在随机线。同一管线下这种反差证明——**L3 的瓶颈是数据（每类几十条+83%全是饿），不是特征/模型，换任何强模型都救不了。**

**这组实测直接锁定三条产品约束：**
1. **L3 意图（原因）后置**——公开数据下连方向都看不到，v1 不输出"饿/困/肚子疼"，待自采数据达标再评审。
2. **L2 紧急度也后置**——无痛苦数据、未验证；v1 不下模型判断，待数据到位再评审。
3. **少数类死结**：discomfort/tired/burping 公开世界各仅 8–27 条，增广救不了"类别样本不存在"，唯一出路是 App 反馈闭环的行为验证标注。
> v1 因此只交付**不依赖判断模型**的能力：录音质量检查(L1) + 强度/持续测量(DSP) + 上下文表单 + 排查清单 + 反馈。

## 3. 用户与场景

**目标用户**：0–12 月龄婴儿的父母/看护人，尤其**新手父母**（核心 0–6 月，哭声声学特征最稳定期、家长最焦虑）。

主用户旅程：**宝宝哭 → 打开 App 录 5–15s → 质量检查 + 强度/持续分析 → 填几项上下文 → 按情况排序的排查清单 + 就医红线 → 记录 → 反馈"最后怎么解决"。**

| 场景 | 用户痛点 | 产品响应 |
|---|---|---|
| S1 手足无措不知先做什么 | 新手不知先喂还是先哄 | 录一段 + 填上下文（距上次喂奶/是否刚醒/月龄）→ **按情况排序的排查清单**（尿布/饥饿/困倦/胀气/体温） |
| S2 不知道严不严重 | 怕错过危险信号 | **就医红线清单**（发热/呕吐/呼吸异常等，由上下文表单的"伴随症状"直接触发），不靠音量判断 |
| S3 哭声强度/持续想有个客观参照 | "是不是哭得比平时凶" | 强度与持续时长（纯测量，永远准）+ 与自己历史对比；**强度高≠更严重，中性呈现** |
| S4 想知道哭闹规律 | 一天哭几次、是否变频繁 | 哭声事件记录与趋势（时段/时长/频次，仅元数据，纯统计不做发育评价） |
| S5 反馈纠错（闭环核心） | 想让 App 越用越准、积累经验 | 事后单击"最后怎么解决：喂奶/拍嗝/抱睡/换尿布/仍未解决/不是哭声" → **反馈即标注** |
| S6 隐私焦虑 | 不想录音上云 | 端侧分析，音频不出手机；仅反馈后单独授权才匿名捐赠片段 |
| S7（远期可选）夜间监护 | 分房睡怕听不到 | 双端常驻监护模式，远期扩展（受 iOS 后台限制，非 MVP，见 §6.3） |

## 4. 产品原则（不可妥协）

> **第 0 原则 · 错误的情绪成本不对称（一切设计的出发点）**：
> 与猫语翻译(MeowTalk)那类"娱乐玩具"根本不同——用户打开本 App 时已经**焦虑、恼火、濒临崩溃**。猫语猜错是乐趣（错误成本为负），婴儿哭声**猜错是伤害**：既没帮上忙，还在一个快爆发的人身上再踩一脚（"更上头"）。
> 推论：① 产品的首要任务是**安抚/降焦虑**，其次才是给信息——"翻译机"思维是错的；② **宁可不说，绝不说错**——没把握时坦承"不确定"远好过瞎猜；③ 必须**为出错而设计**：永远谦逊、绝不嘴硬、语气共情先接住家长情绪；④ 这是 v1 **只输出可测量事实、不下 ML 判断**的根本理由——测量值没有对错，不会惹怒家长。

1. **安抚优先**：UI/文案先接住家长情绪（"宝宝哭得有点凶，辛苦了"），再给信息；给掌控感（可照做的清单）而非可能出错的结论。
2. **v1 只说可测量的事实**：强度/持续时长（DSP 直接测，永远准）、录音质量。**不下任何 ML 判断**（不报原因、不报紧急度），把会出错的判断全部后置到数据到位。
3. **强度高 ≠ 更严重（医学硬常识）**：响亮哭常是健康有力；虚弱低弱的呜咽反而可能病重。强度必须**中性呈现 + 配安抚语**，绝不暗示"越响越危险"。真正的危险信号由就医红线清单（症状）判断，不靠音量。
4. **隐私零上云**：原始音频不离开设备；可选上传仅限用户主动捐赠的片段（明示授权）。
5. **非医疗**：不做病理判断，不出现"诊断/健康筛查"字样；危险信号直接推向就医，App 不接管。
6. **先有用、再升级**：v1 用"质量检查+测量+上下文+清单+反馈"立身（不靠判断模型）；L2 紧急度、L3 原因等判断能力，靠反馈数据攒够后再评审上线。

## 5. 功能需求

### P0 — v1 MVP（决策辅助流程，全部不依赖判断模型）

> v1 一个 ML 判断都不下——只交付可测量的事实 + 上下文 + 清单 + 反馈。轻、稳、可信、易上线。

| ID | 需求 | 验收标准 |
|---|---|---|
| F1 | 手动录音 5–15s | 家长点录，采 5–15s（静音自动停）；前台，音频只在内存 |
| F2 | **录音质量检查（L1 降级用途）** | 判定：是不是婴儿哭声 / 噪声是否过大 / 是否太短 / 是否太远（声压过低）→ 不合格则引导重录。不"证明在哭"，只把关质量 |
| F3 | 强度与持续性分析 | **纯 DSP 测量**（RMS 强度、时长、停顿比），无模型、永远准；**强度中性呈现，不暗示严重程度** |
| F4 | 上下文表单 | 快速填：距上次喂奶/是否刚睡醒/是否刚换尿布/月龄/哭了多久/伴随发热呕吐呼吸异常(→直接喂就医红线)。智能默认、可跳过 |
| F5 | 非医疗排查清单 | 结合 F3+F4 **按情况排序**输出"建议先检查：尿布/饥饿/困倦/胀气/体温"；客观、可勾选；不报原因 |
| F6 | 就医红线 | 固定症状清单（发热/呕吐/呼吸异常等），由 F4 伴随症状触发并置顶；导向就医，App 不接管 |
| F7 | 哭声事件记录与趋势 | 每次记录元数据（时间/时长/强度/上下文/反馈）；时段/时长/频次统计（不存音频） |
| F8 | **反馈：最后怎么解决（闭环核心）** | 单击"喂奶后好了/拍嗝后好了/抱睡后好了/换尿布后好了/仍未解决/不是哭声"→ 反馈即标注 |
| F9 | 隐私与可选捐赠 | 端侧分析、音频不上云；F8 后可单独授权匿名捐赠片段 |

### P1+ — 判断能力（数据驱动，全部后置、设闸门）

> §2.4 实测：公开数据撑不住原因/紧急度判断。以下全部靠 F8 反馈 + 自采数据攒够、离线按婴儿组切分达标后才评审上线。**达标前 v1 绝不输出这些。**

| ID | 需求 | 上线闸门 |
|---|---|---|
| F10 | 紧急度判断（L2 要不要紧） | 自采痛苦数据 AUC≥0.90（组切分）；呈现"更像…(xx%)"+免责 |
| F11 | 端上个性化 | 累积 ≥200 条本机反馈后微调（Core ML MLUpdateTask / LiteRT），零上传 |
| F12 | 原因预测（L3 意图） | 自采标注离线 macro-F1≥0.55（组切分）；Top-2+概率+免责，永不断言 |

### 明确不做 / 后置（Non-goals）

- 后台常驻监听、双端监护模式、夜间自动推送（绕开 iOS 后台限制；夜间监护为远期可选 §6.3）
- "长时家庭噪声误报率"作为核心指标（主动录音场景不适用）
- 婴语翻译 / 原因断言（"宝宝饿了/困了/肚子疼"）
- 病理/医疗诊断（医疗器械红线）
- 云端音频存储/回放、视频能力

## 6. 技术方案

### 6.1 总体架构（主动触发，全端侧）

```
家长点"录一段" (主动触发, 无后台常驻)
  → 采音 5–15s (16kHz mono, AVAudioEngine / AudioRecord), 仅内存
  → [质量检查 L1] 是婴儿哭声? 噪声大不大? 太短? 太远(声压低)?  ——不合格→引导重录
  → [测量, 纯DSP] RMS 强度 + 时长 + 停顿比   ← 永远准, 无模型
  → 结合 [上下文表单] (距上次喂奶/刚醒/月龄/伴随症状)
  → 结果卡片: 客观读数 + 按情况排序的排查清单 + 就医红线 + 写记录
  → 家长反馈"最后怎么解决" → (授权后)片段+标签入数据闭环
  ┄┄ 后置(数据驱动): [L2 紧急度] / [L3 原因] 达标才接入此处 ┄┄
```

v1 的好处：①无需后台常驻，**绕开 iOS 后台限制**；②单手机即可，轻；③**判断模型全部后置**，v1 只靠"质量检查(L1)+测量(DSP)+上下文+清单"，不会因模型出错而惹怒家长。端侧：iOS **Core ML**、Android **LiteRT**。音频只在内存、不落盘（除非授权捐赠）。

> 远期"被动夜间监护"才需要常开 VAD + 三级漏斗 + 双端推送（见 §6.3 远期模式），当前 MVP 不涉及。

### 6.2 模型路线

**路线 A（v1）：质量检查 + 测量，无判断模型**
- **L1 质量检查（已有基础）**：YAMNet 迁移 + Keras 小头判"是不是婴儿哭声"（实测 AUC 0.999，`baseline/train_l1_model.py`）；再加简单规则判噪声(SNR)、时长、声压(太远)。ESC-50 为 NC，仅实验，商用须换可商用负样本。
- **强度/持续测量（DSP，非 ML）**：RMS 能量、时长、停顿比，直接算，**永远准、无对错**。
- 部署：L1 经 coremltools 导 Core ML、TFLite 导 LiteRT；DSP 端侧直接算。无服务器推理。

**路线 B（后置判断能力，数据驱动）**
- L2 紧急度 / L3 原因：同 YAMNet embedding + 小头（或 log-mel CNN）。**必须先有自采数据**（L2 痛苦真值、L3 行为标签），离线组切分达标才上（§6.5 闸门）。
- 升级方向：wav2vec 2.0 / HuBERT / Whisper encoder 蒸馏（Springer 2025、arXiv 2509.02259）；云端训练教师→蒸馏端侧学生→OTA 下发。**训练在云、推理永远在端。**

### 6.3 端侧运行环境与产品形态

**MVP = 单手机、前台主动使用、纯 App 无硬件。** 家长哭时打开录音，全程前台，**不触碰 iOS 后台限制**——这是相比"被动监护"最大的工程简化（无需双端、无需后台常驻、无需跨端通信/推送）。iOS/Android 各自原生推理核（Core ML / LiteRT），特征提取与决策逻辑跨端严格对齐。

**远期可选：被动夜间监护模式（非 MVP）。** 若后续要做"分房睡自动告警"，才需引入：常开能量 VAD + 三级漏斗（VAD→L1→L2）+ 双端模式（旧手机插电常驻当监护端、父母手机收推送，局域网 mDNS/WebRTC 直连、弱网云信令兜底、仅传事件信号不传音频）。该模式受 iOS 后台限制约束，作为独立里程碑评估，不阻塞 MVP。

### 6.4 数据策略（中期壁垒）

1. **冷启动**：YAMNet 迁移 + ESC-50/AudioSet 负样本（L1，已验证 AUC 0.986）；donateacry 仅作 L3 天花板参照（实测不可商用，见 §2.4）。
2. **自采**：疫苗接种/采足跟血场景采集痛苦哭声（客观真值，ChatterBaby 同款方法，需伦理授权）；母婴社区招募种子家庭采集日常哭声。
3. **闭环**：F10 家长反馈 = 行为验证标注（"喂奶后停止哭"≈饿），比人工听音标注更接近真值，这是对学术数据集的本质改进。
4. **数据回传方案（App 形态，按成本递增）**：
   - **A 明示授权片段捐赠（MVP 首选）**：哭声事件→内存滚动缓冲留 10s→家长反馈后弹一次性确认→Opus 压缩(10s≈20–30KB)→仅 WiFi 上传。法律最干净（单独同意）、带行为标签、流量可忽略。**反馈即标注，捐赠即回传。**
   - **C 端上个性化零上传（与 A 并行）**：Core ML MLUpdateTask / LiteRT 端上训练，本机反馈微调分类头，解决"我家宝宝"个性化，完全不碰传输。
   - **B 只传特征不传音频（隐私模式选项）**：上传 log-mel/embedding 而非波形；代价是无法人工复核、特征改版历史作废，故作可选不作默认。
   - **D 联邦学习**：进 backlog，DAU 过万再评估（单用户样本少 + 标签噪声，对 MVP 不划算）。

### 6.5 评估指标

| 能力 | 指标 | 目标 | 当前 |
|---|---|---|---|
| L1 质量检查（v1） | 哭声 vs 非哭声 AUC | ≥0.95 | 0.999（公开数据；真实场景待验证） |
| 强度/持续测量（v1） | — | 测量值，无准确率概念 | DSP 直接算，永远准 |
| 排查清单/上下文（v1） | 有用性（家长主观） | 内测满意度 | 待内测 |
| L2 紧急度（后置） | AUC（按婴儿组切分） | ≥0.90 才上 | 未验证、无数据 |
| L3 原因（后置） | 离线 macro-F1（组切分） | ≥0.55 才上 | 0.295（公开数据，不上） |
| 系统 | 录音→结果延迟 | ≤3s（单机前台） | — |

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **v1 价值是否够"留得住人"** | 高（**新主风险**） | v1 不下判断、只给测量+清单+记录，可能显得"不够聪明"。对策：①把"客观记录+排查清单+趋势"做到真的省心好用；②上下文表单让清单**精准排序**而非泛泛；③用历史趋势/个性化增强黏性；④快速验证内测留存 |
| 强度被误读为"严重程度" | 高 | 第3原则：强度**中性呈现 + 配安抚**，绝不暗示"越响越危险"；危险只看就医红线（症状），不看音量 |
| **真实场景未验证** | 高 | L1 质量检查只在公开数据(ESC-50 干净剪辑)成立；上线前需真实录音验证手机远场麦/电视/人声/宠物/白噪声 |
| 数据不足（决定能否做判断） | 高 | F8 反馈即标注(行为验证) + 疫苗场景自采痛苦真值；攒够才解锁 L2/L3，月龄分桶建模 |
| "婴语翻译"预期落差致差评 | 中 | 文案严格不承诺"饿/困"、不承诺"要不要紧"；定位为"记录+排查助手" |
| 隐私合规（儿童数据） | 中 | 端侧零上传默认；捐赠单独同意 + 法务评审（个保法：儿童信息按敏感个人信息，监护人同意、境内存储） |
| 医疗宣称越界 | 中 | 禁用词表进 CI（诊断/病症/筛查）；危险信号直接推就医，App 不接管 |
| iOS 后台限制（仅远期监护模式） | 低（MVP 已规避） | MVP 前台主动录音不触碰；远期监护模式再用双端+插电应对 |
