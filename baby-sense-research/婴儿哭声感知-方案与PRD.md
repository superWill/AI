# 婴儿哭声感知 — 技术方案与 PRD

> 版本 v0.3 · 2026-06-10 · 状态：草案（已含自有数据实测验证）
> v0.3 变更（产品形态重大调整）：从"被动双端监护"改为**主动式 App**——孩子哭了之后家长打开 App 录一段，App 判断"**这次哭要不要紧**"(L2) 并记录，靠家长反馈攒数据。理由：①"告诉你为什么哭(饿/困)"实测做不到(§2.4)；②主动式绕开 iOS 后台监听难题；③录音用户主动触发，天然适配数据闭环。
> 历史：v0.2 改 App 端侧+实测回填；v0.1 边缘硬件。

---

## 1. 一句话定位

**主动式婴儿哭声理解 App（iOS/Android）**：孩子哭了，家长打开 App 对着录一段 → App 给出"**这更像要紧/痛苦的哭，还是普通烦躁**"(L2 紧急度) + 哭声特征 + 安抚参考 + 记录，并请家长反馈"实际是什么"。**主打"要不要紧"，不承诺"翻译婴语(饿/困)"**；音频端侧处理、不上云；反馈即标注，为未来能力攒数据。

> 形态选择：**主动触发**（家长哭时打开），不是后台常驻监听。被动夜间监护（双端常驻）作为远期可选模式，不在当前 MVP（见 §6.3）。

## 2. 背景与调研结论

### 2.1 技术可行性边界（核心认知）

| 能力层级 | 学术/产业现状 | **本项目实测（见 §2.4）** | 可行性 |
|---|---|---|---|
| L1 哭声事件检测（哭没哭） | CNN 类 95%+（CNN-SCNet） | **AUC 0.999，召回@5%误报 1.000±0.000**（YAMNet训练，公开数据） | ✅ 公开数据强，真实家庭待验证 |
| L2 痛苦 vs 非痛苦 | ChatterBaby 痛苦哭声 90.7% | 待自采数据验证 | ✅ 较可靠（需验证） |
| L3 具体意图（饿/困/不适/烦躁） | ChatterBaby 71.5%；论文 ~60% | **三分类 balanced acc 0.290（低于随机），公开数据≈噪声** | ⛔ 公开数据做不到，移出 MVP |
| L4 病理性哭声（窒息/脑损伤/耳聋） | 论文可达 95%（Baby Chillanto） | 不做 | ⛔ 属医疗器械，本产品不做 |

**结论（已被实测修正）：产品地基是 L1（公开数据上实测很强，真实家庭场景待验证）+ L2（赌自采真值）；L3 在公开数据下连方向都看不到，必须等 App 反馈闭环攒够自采数据后才评审上线；L4 明确排除。**

> ⚠️ **L1 实测的适用边界**：哭声来自 donateacry（近场录音），"噪声"来自 ESC-50 的 5 秒**干净剪辑**。这证明"方向可行 + 公开数据上很强"，但**不等于真实家庭场景已解决**——手机远场麦克风、家庭环境底噪、电视/人声/宠物/白噪声/安抚音乐、多声源叠加均**未测试**。对外只能说"哭声检测方向可行"，"真实家庭可用"需经真实录音验证（清单见 [`baseline/实验结果.md`](baseline/实验结果.md) 「尚未验证」）。

### 2.2 竞品扫描

| 产品 | 形态 | 哭声相关能力 | 弱点 |
|---|---|---|---|
| ChatterBaby (UCLA) | 免费 App | 痛/饿/烦躁三分类，云端推理 | 需手动触发录音，无监护硬件，录音上云 |
| CuboAi Monitor 3 | 摄像头监护器（2.5K） | 哭声/咳嗽检测告警，AI 较快 | 贵（$200+），依赖云，意图分类弱 |
| Nanit | 摄像头监护器 | 睡眠分析为主，哭声告警 | 订阅制，哭声只是附属功能 |
| Dunstan 婴语 | 方法论/课程 | 5 种反射音理论 | 无严格科学验证，非技术产品 |

**直接对标 ChatterBaby**（同为"主动录音→判断"形态）。我们的差异化：①**端侧推理、音频不上云**（ChatterBaby 上云）；②**诚实定位**——主打可靠的"要不要紧"(L2)，不像多数产品硬承诺"饿/困"翻译然后翻车；③**数据闭环**靠行为反馈攒自采数据，是后期解锁意图的唯一正路；④国内市场本地化（隐私敏感、母婴生态）。**机会：市面"婴语翻译"普遍过度承诺、口碑差，一个诚实+隐私+越用越准的产品有空间。**

### 2.3 可用公开数据集

| 数据集 | 规模 | 标签 | 用途 |
|---|---|---|---|
| [donateacry-corpus](https://github.com/gveres/donateacry-corpus) | 457 条 | 饿/拍嗝/困/腹痛/不适 | L3 意图分类起步（量小、用户自标、噪声大） |
| Baby Chillanto (INAOE, 墨西哥) | 2,268 条 1s 片段 | 窒息/耳聋/饿/正常/痛 | L2 痛苦分类参考（需邮件申请） |
| ICSD (2024, 开源) | 哭声+鼾声事件 | 事件检测 | L1 哭声检测训练 |
| CryCeleb (2023) | 6 千+ 段，786 婴儿 | 说话人(婴儿)身份 | 预训练/嵌入学习，非意图标签 |
| AudioSet (Google) | 海量含 "Baby cry" 类 | 事件级 | L1 预训练（YAMNet 即基于此） |

**数据结论：L1 数据充足；L2/L3 公开数据总量 < 3000 条且标注质量参差——自建数据闭环是中期壁垒，产品设计必须内置"家长反馈标注"机制。**

### 2.4 自有数据实测（2026-06-10，关键决策依据）

用 donateacry(457条/221婴儿) + ESC-50(2000条环境音)，MFCC 特征 + 逻辑回归，**严格按婴儿 ID 组切分**（杜绝同一宝宝哭声跨训练/测试泄漏）。完整报告见 [`baseline/实验结果.md`](baseline/实验结果.md)，可一键复现。

> 低误报召回为**按折 mean±std、保守口径**（满足 fpr≤目标的最高召回，不突破误报预算）。

| 实验 | MFCC 基线 | YAMNet 确认(1024维强特征) | 判定 |
|---|---|---|---|
| A) L1 哭声 vs 环境音 | AUC 0.986，召回@5% 0.917±0.053 | **AUC 0.999，召回@5% 1.000±0.000** | ✅ 公开数据强 |
| B) hungry vs rest | AUC 0.479（≈随机 0.5） | AUC 0.449（仍≈随机） | ⛔ 无可分信号 |
| C) hungry/tired/discomfort 三分类 | bal.acc 0.290（随机=0.333） | bal.acc 0.315（仍低于随机） | ⛔ 公开数据≈噪声 |
| D) 泄漏对照 | 随机切分 0.379 vs 按婴儿 0.290，虚高 +0.089 | — | 🔍 文献高分=多数类基线+泄漏+强特征 |

> **决定性证据**：从 MFCC 升级到 YAMNet，L1 从 0.986 冲到 0.999（强特征确实有用）；同样升级用在 L3 却纹丝不动钉在随机线。同一管线下这种反差证明——**L3 的瓶颈是数据（每类几十条+83%全是饿），不是特征/模型，换任何强模型都救不了。**

**这组实测直接锁定三条产品约束：**
1. **L3 意图卡片移出 MVP**——公开数据下连方向都看不到，上线即翻车（F9 改为 P2-后置，待自采数据达标再评审）。
2. **L1 是确定可交付的地基**，L2 是下一个待验证赌注（疫苗场景自采客观真值）。
3. **少数类死结**：discomfort/tired/burping 公开世界各仅 8–27 条，增广救不了"类别样本不存在"，唯一出路是 App 反馈闭环的行为验证标注。

## 3. 用户与场景

**目标用户**：0–12 月龄婴儿的父母/看护人，尤其**新手父母**（核心 0–6 月，哭声声学特征最稳定期、家长最焦虑）。

主用户旅程（主动式）：**宝宝哭 → 家长打开 App 对着录 10–20s → App 给出紧急度判断+特征+建议+记录 → 家长照做 → 事后单击反馈"实际是什么"。**

| 场景 | 用户痛点 | 产品响应 |
|---|---|---|
| S1 哭了不知道要不要紧 | 新手分不清"普通烦躁"和"该担心的哭" | 录一段 → "**更像痛苦/要紧的哭 (xx%)**"或"普通烦躁"(L2) + 哭声特征(高音调/时长/间歇) |
| S2 手足无措不知先做什么 | 不知先喂还是先哄 | 安抚指引 + **上下文规则建议**（如"距上次喂奶 3h，可能饿"——标注为经验提示，非听声音判断） |
| S3 想知道哭闹规律 | 一天哭几次、是否变频繁 | 哭声记录与趋势（时段/时长/频次，仅元数据，纯统计不做发育评价） |
| S4 反馈纠错（闭环核心） | 想让 App 越用越准 | 事后单击"其实是：喂奶解决/哄睡/换尿布/送医…" → **反馈即标注，喂养 L2/L3 数据集** |
| S5 隐私焦虑 | 不想录音上云 | 端侧推理，音频不出手机；仅在反馈后单独授权才捐赠片段 |
| S6（远期可选）夜间监护 | 分房睡怕听不到 | 双端常驻监护模式，作为后续扩展（受 iOS 后台限制，非 MVP，见 §6.3） |

## 4. 产品原则（不可妥协）

> **第 0 原则 · 错误的情绪成本不对称（一切设计的出发点）**：
> 与猫语翻译(MeowTalk)那类"娱乐玩具"根本不同——用户打开本 App 时已经**焦虑、恼火、濒临崩溃**。猫语猜错是乐趣（错误成本为负），婴儿哭声**猜错是伤害**：既没帮上忙，还在一个快爆发的人身上再踩一脚（"更上头"）。
> 推论：① 产品的首要任务是**安抚/降焦虑**，其次才是给信息——"翻译机"思维是错的；② **宁可不说，绝不说错**——没把握时坦承"不确定"远好过瞎猜；③ 必须**为出错而设计**：永远谦逊（"看起来更像"不用"他就是"）、绝不嘴硬、语气共情先接住家长情绪；④ 这是"主打 L2 要不要紧、不碰 L3 翻译"的根本理由——L2 答的是家长最大的恐惧"我该担心吗"，且可向谨慎侧偏，错了不致命。

1. **安抚优先**：UI/文案先接住家长情绪（"宝宝哭得有点凶，辛苦了"），再给判断；给掌控感（可照做的清单）而非可能出错的结论。
2. **诚实呈现**：紧急度/意图永远显示概率 + "仅供参考"，永不输出"宝宝饿了"这种断言句式；没把握就说不确定。
3. **隐私零上云**：原始音频不离开设备；可选上传的仅为用户主动捐赠的标注片段（明示授权）。
4. **非医疗**：不做病理判断，UI/文案/商详页不出现"诊断""健康筛查"字样；检测到持续异常只提示"建议咨询医生"。
5. **先有用、再升级**：L2"要不要紧"是主打但**尚未用自有数据验证**（§7 风险 #1）。v1 先交付能上线且能攒数据的版本（录音+L1确认+记录+反馈闭环），L2 一旦数据到位即作为主功能上线。

## 5. 功能需求

### P0 — v1 MVP（主动录音 + 记录 + 反馈闭环，能上线、能攒数据）

> v1 不强行承诺"要不要紧"——L2 还没数据验证。v1 立身点是"客观记录哭声 + 有用的上下文建议 + 反馈纠错"，同时把数据飞轮转起来。

| ID | 需求 | 验收标准 |
|---|---|---|
| F1 | 主动录音 + 哭声确认 | 家长点录 → 采 10–20s → L1 确认"确实是哭声"(端侧，实测 AUC 0.999) + 提示非哭声/太吵重录 |
| F2 | 哭声特征展示 | 时长、强度、音调高低、间歇——客观可解释信息（非"翻译"） |
| F3 | 哭声记录与趋势 | 每次记录元数据；时段/时长/频次统计（不存音频，不做发育评价） |
| F4 | **反馈标注（闭环核心）** | 事后单击"实际是什么"（喂奶/哄睡/换尿布/送医/其他）→ 反馈即标注；这是攒 L2/L3 数据的关键 |
| F5 | 上下文规则建议 | 基于"距上次喂奶/睡眠时长"等规则给经验提示，**明确标注"经验参考，非听声音判断"** |
| F6 | 隐私与麦克风 | 端侧推理音频不上云；录音状态可见；捐赠片段需 F4 后单独授权 |

### P1 — L2 紧急度（主打功能，数据到位后上线）

> ⚠️ 闸门：L2 需自采"痛苦 vs 非痛苦"数据（疫苗场景客观真值 / 反馈累积），且离线 AUC≥0.90、按婴儿组切分验证后才上线。当前**未验证、无数据**。

| ID | 需求 | 验收标准 |
|---|---|---|
| F7 | 痛苦/要紧哭声判断 | 痛 vs 非痛 AUC ≥ 0.90（自有数据组切分，参照 ChatterBaby 0.90+） |
| F8 | 紧急度呈现 | "更像痛苦/要紧 (xx%)"vs"普通烦躁"+ 免责；高紧急度给"建议尽快查看/必要时就医" |
| F9 | 持续哭闹提醒 | 单次会话内连续哭 > N 分钟给提示 |

### P2 — 个性化 + 意图（闸门解锁，远期）

> §2.4 实测：公开数据无法支撑 L3 意图(饿/困/不适)。靠 F4 反馈闭环攒够自采标注后才评审。

| ID | 需求 | 验收标准 |
|---|---|---|
| F10 | 端上个性化 | 累积 ≥ 200 条本机反馈后端侧微调分类头（Core ML MLUpdateTask / LiteRT），零上传 |
| F11 | 意图概率卡片（**闸门**） | 自采数据离线 macro-F1≥0.55（按婴儿组切分）才上线；显示 Top-2+概率+免责；永不断言 |

### 明确不做（Non-goals）

- 病理/疾病检测（医疗器械红线）
- "婴语翻译机"式断言输出（饿/困/不适的肯定句）
- 云端音频存储/回放
- 视频能力（纯音频，降低隐私门槛与成本）
- v1 不做后台常驻监听（绕开 iOS 后台限制；夜间监护为远期可选）

## 6. 技术方案

### 6.1 总体架构（主动触发，全端侧）

```
家长点"录一段" (主动触发, 无后台常驻)
  → 采音 10–20s (16kHz mono, AVAudioEngine / AudioRecord)
  → 前处理 (log-mel) → YAMNet embedding (端侧)
  → [L1] 哭声确认：是哭声? (实测 AUC 0.999)  ——否→提示重录/太吵
  → [L2] 紧急度：痛苦/要紧 vs 普通烦躁 (数据到位后接入)
  → 结果卡片：紧急度概率 + 哭声特征 + 安抚/上下文建议 + 写入记录
  → 事后家长反馈"实际是什么" → (授权后)片段+标签入数据闭环
```

主动式的好处：①无需后台常驻，**绕开 iOS 后台音频限制**；②单手机即可，产品轻；③录音用户主动触发，天然适配隐私与数据采集。端侧推理：iOS 走 **Core ML**，Android 走 **LiteRT(TFLite)**，由同一 YAMNet 迁移训练分别导出。音频只在内存处理、不落盘（除非反馈后用户授权捐赠）。

> 远期"被动夜间监护"才需要常开 VAD + 三级漏斗 + 双端推送（见 §6.3 远期模式），当前 MVP 不涉及。

### 6.2 模型路线

**路线 A（MVP 首选）：经典轻量路线**
- L1（已验证）：YAMNet（AudioSet 预训练，MobileNet-v1 骨干）迁移 + Keras 小头，可蒸馏到 <1MB；ESC-50/AudioSet 补负样本（**ESC-50 为 NC，仅实验，商用须换可商用负样本**）。**实测：YAMNet 训练后 AUC 0.999、召回 1.000±0.000@5%误报；零样本即 0.986。** 训练脚本见 `baseline/train_l1_model.py`。
- L2（主打，**未验证、无数据**）：同 YAMNet embedding + 小头（或 log-mel + 轻量 CNN）。信心来自 ChatterBaby ~0.90，但**必须先有自采"痛苦 vs 非痛苦"数据**才能训/验证（见 §7 风险 #1、§6.4）。
- 部署：训练产物经 coremltools 导 Core ML（iOS）、TFLite 导 LiteRT（Android）；模型小，CPU/ANE/NNAPI 均可，无需服务器推理。

**路线 B（P2 升级）：预训练语音大模型蒸馏**
- 2025 年方向：wav2vec 2.0 / HuBERT / Whisper encoder 的逐层特征对低资源哭声分类显著优于手工特征（Springer 2025、arXiv 2509.02259）。
- 做法：云端用大模型在自建数据上训教师模型 → 蒸馏成端侧学生模型 → OTA 下发新模型权重。**训练在云，推理永远在端**，不破坏隐私承诺。

### 6.3 端侧运行环境与产品形态

**MVP = 单手机、前台主动使用、纯 App 无硬件。** 家长哭时打开录音，全程前台，**不触碰 iOS 后台限制**——这是相比"被动监护"最大的工程简化（无需双端、无需后台常驻、无需跨端通信/推送）。iOS/Android 各自原生推理核（Core ML / LiteRT），特征提取与决策逻辑跨端严格对齐。

**远期可选：被动夜间监护模式（非 MVP）。** 若后续要做"分房睡自动告警"，才需引入：常开能量 VAD + 三级漏斗（VAD→L1→L2）+ 双端模式（旧手机插电常驻当监护端、父母手机收推送，局域网 mDNS/WebRTC 直连、弱网云信令兜底、仅传事件信号不传音频）。该模式受 iOS 后台限制约束，作为独立里程碑评估，不阻塞 MVP。

### 6.4 数据策略（中期壁垒）

1. **冷启动**：YAMNet 迁移 + ESC-50/AudioSet 负样本（L1，已验证 AUC 0.986）；donateacry 仅作 L3 天花板参照（实测不可商用，见 §2.4）。
2. **自采**：疫苗接种/采足跟血场景采集痛苦哭声（客观真值，ChatterBaby 同款方法，需伦理授权）；母婴社区招募种子家庭采集日常哭声。
3. **闭环**：F10 家长反馈 = 行为验证标注（"喂奶后停止哭"≈饿），比人工听音标注更接近真值，这是对学术数据集的本质改进。
4. **数据回传方案（App 形态，按成本递增）**：
   - **A 明示授权片段捐赠（MVP 首选）**：哭声事件→内存滚动缓冲留 10s→家长反馈后弹一次性确认→Opus 压缩(10s≈20–30KB)→仅 WiFi 上传。法律最干净（单独同意）、带行为标签、流量可忽略。**反馈即标注，捐赠即回传。**
   - **C 端上个性化零上传（与 A 并行）**：Core ML MLUpdateTask / LiteRT 端上训练，本机反馈微调分类头，解决"我家宝宝"个性化，完全不碰传输。
   - **B 只传特征不传音频（隐私模式选项）**：上传 log-mel/embedding 而非波形；代价是无法人工复核、特征改版历史作废，故作可选不作默认。
   - **D 联邦学习**：进 backlog，DAU 过万再评估（单用户样本少 + 标签噪声，对 MVP 不划算）。

### 6.5 评估指标

| 层 | 指标 | 目标 | 当前实测 |
|---|---|---|---|
| L1（哭声确认） | 召回 @ 误报率 | 召回 ≥0.95 @ FPR≤5% | 1.000±0.000 @5%（YAMNet训练，**仅公开数据/ESC-50 干净剪辑，真实家庭待验证**） |
| L2（主打:要不要紧） | AUC（按婴儿组切分） | ≥0.90 才上线 F7/F8 | **未验证、无数据**（信心源自 ChatterBaby ~0.90） |
| L3（远期意图） | 离线 macro-F1（闸门） | ≥0.55 才解锁 | 0.295（公开数据，未达标，不上） |
| 系统 | 录音→结果延迟 | ≤3s（单机前台推理） | — |

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **主打功能 L2 未验证、无数据** | 高（**最大风险**） | L2"要不要紧"是产品卖点，但我们没测过、没痛苦数据。对策：①v1 不承诺 L2，先靠记录+反馈+上下文建议立身；②优先去疫苗场景自采痛苦哭声(客观真值)；③L2 离线 AUC≥0.90 才上线。**在此之前对外不宣称能判断"要不要紧"。** |
| L3 意图准确率不及预期 | 高（**已实测坐实**） | 已移出主线；靠反馈闭环攒数据，macro-F1≥0.55 闸门才上 |
| **真实家庭场景未验证** | 高 | L1 强结果只在公开数据(ESC-50 干净剪辑)成立；上线前需真实录音验证手机远场麦/电视/人声/宠物/白噪声 |
| 数据不足/标注真值难 | 高 | 主动式录音 + F4 反馈即标注(行为验证)；疫苗场景自采痛苦真值；月龄分桶建模 |
| "婴语翻译"预期落差致差评 | 中 | 文案严格不承诺"饿/困"；主打"记录+要不要紧"，意图永远概率化+免责 |
| 隐私合规（儿童数据） | 中 | 端侧零上传默认；捐赠单独同意 + 法务评审（个保法：儿童信息按敏感个人信息，监护人同意、境内存储） |
| 医疗宣称越界 | 中 | 文案白名单制，"病理/诊断/筛查"禁用词表进 CI；高紧急度仅提示"建议就医"不下结论 |
| 主动式留存（用完即走） | 中 | 用记录/趋势/个性化增强黏性；推送"今日哭闹小结"等轻召回 |
| iOS 后台限制（仅远期监护模式） | 低（MVP 已规避） | MVP 前台主动使用不触碰；远期监护模式再用双端+插电应对 |
