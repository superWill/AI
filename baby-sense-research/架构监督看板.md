# Baby Sense 架构监督看板

> 角色：用架构师视角守住方向、边界、阶段门和交付证据。本文是每次推进前后的检查清单。

## 1. 北极星

宝宝哭的时候，帮助家长顺手完成一次闭环：**记录 → 上下文 → 建议 → 尝试 → 追问 → 档案沉淀 → 下次更准**。

判断任何需求是否该做，只问三件事：

- 是否让家长更容易走完整个闭环？
- 是否让“动作 → 结果 → 下次排序”更可靠？
- 是否守住隐私、安全和不做医学判断的边界？

## 3. 不偏航原则

- 不做“判断宝宝为什么哭”的产品承诺，v1 只做排查辅助。
- 不做健康评分、严重程度诊断、发育判断或医疗解释。
- 不默认上传音频；捐赠必须单独授权、可撤回、可审计。
- 不用复杂图表制造专业感，档案页只保留“下次有帮助的记忆”。
- 不让模型盖过闭环；模型只是质量检查/输入分析器，核心资产是反馈数据链。

## 4. 阶段门

每个阶段合入前必须满足：

| 阶段 | 必过条件 |
|---|---|
| 产品流 | 家长能从一次哭闹顺手走到反馈和档案 |
| 数据链 | `CryRecord → Context → Suggestion → Action → Outcome → BabyProfile` 可追溯 |
| 建议排序 | 排序理由可解释，历史有效/无效会改变下次建议 |
| 音频分析 | 不合格录音必须拦截，不能瞎给建议 |
| 模型接入 | 黄金集可重复验证，端侧输出有固定阈值和失败降级 |
| 隐私能力 | 默认不上云，任何上传路径都有显式授权入口 |

## 5. 当前风险

| 风险 | 现象 | 处理原则 |
|---|---|---|
| M1c 工程半成品 | 新增 `CryDetector` / `MelFrontend` / `ML` 后，项目尚未稳定构建 | 先让 Xcode project 纳入新文件和资源，再跑测试 |
| 模型权重过早影响产品话术 | 可能把质量检查说成“识别原因” | 文案继续保持中性，只说录音质量和客观强度 |
| 文档多而分散 | PRD、闭环、技术、页面流、档案页各自存在 | README 负责入口，本看板负责方向与阶段判断 |
| 体验被工程复杂度拖偏 | 端侧模型、Core ML、mel 前端容易吃掉注意力 | 每次技术推进后回归闭环手感 |

## 6. 下一步

1. 收口 M1c：生成工程、纳入模型资源、修编译、跑单元测试。
2. 建立黄金集回归：哭声/噪声样本输出稳定，失败时降级到现有质量规则。
3. 回到产品手感：确认“录音失败 / 非哭声 / 太吵 / 手动记录”都能继续闭环。
4. 更新 `app-ios/README.md` 的当前状态，避免文档说 M1b、代码已到 M1c。

## 7. 我后续监督方式

- 每次开始前先判断：当前是在做闭环、音频质量、模型接入、隐私，还是偏航功能。
- 每次完成后检查：文档、测试、演示路径是否同步。
- 遇到新需求先归类到阶段门；不满足当前阶段目标的，放入后续列表。
- 任何涉及医疗、安全、儿童隐私的改动，默认提高一级审查。
