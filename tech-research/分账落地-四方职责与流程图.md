# 分账落地　四方职责与流程图

> **给谁看**：技术、产品、平台、运营
> **目的**：在分账模式下，把**服务端 / 小程序 / 平台（运营）/ 收款方（乙方）**各自要做什么、按什么顺序做、画成图说清
> **配套文档**：《合规分账模式-服务商特约商户方案》（原理与条件）
> **前提**：平台已是微信支付服务商；乙方=特约商户收款拿 97%；平台作分账接收方抽 3%。

---

## 0. 一句话职责

| 角色 | 一句话 |
|---|---|
| **平台（运营/商务）** | 办资质、收乙方材料、推动乙方签约 —— "**搞定资格**" |
| **服务端** | 进件、存 `sub_mchid`、下单、请求分账、解冻、对账 —— "**所有决策和资金指令**" |
| **小程序** | 只调起支付 —— "**点一下付款**" |
| **收款方（乙方）** | 交材料、扫码签约、提现 —— "**配合开户、收钱**" |

> 记住：**钱怎么分、用谁的号、打不打分账标记，全在服务端**；小程序碰不到这些。

## 2. 分阶段流程（每段一张图）

### 阶段一　开通与进件（让乙方"能收款"）

```
平台运营            服务端                 微信支付            乙方
  │                   │                      │                 │
  │ 办服务商+ICP/EDI ─────────────────────→ 审核通过           │
  │                   │                      │                 │
  │ 收集乙方资料 ←──────────────────────────────────────────── 提供执照/身份证/卡
  │ ──转交──────────→ │                      │                 │
  │                   │ 进件API(带out_request_no)→ 审核(1-3天)  │
  │                   │                      │                 │
  │                   │ ←── applyment_id ────│                 │
  │                   │ 轮询审核状态 ────────→│                 │
  │                   │ ←── 通过+sub_mchid ──│                 │
  │                   │                      │ 推送签约 ───────→│
  │                   │                      │ ←──── 法人扫码签约 │
  │                   │ 存"乙方↔sub_mchid"   │                 │
  │                   │ 绑定平台为分账接收方 →│                 │
  ▼                   ▼                      ▼                 ▼
            乙方上线，可收款
```

**各方做什么**
- **平台运营**：办平台资质；收乙方材料并转交；催乙方完成签约。
- **服务端**：调进件 API（带可反查乙方的 `out_request_no`）；轮询拿 `sub_mchid`；落库映射；调"添加分账接收方"绑定平台。
- **乙方**：提供执照/身份证/银行卡；**法人扫码完成开户意愿确认+签约**（这步谁也代替不了）。
- **微信**：审核进件、推送签约页。

> ⚠️ 进件**通过 ≠ 能用**，必须乙方签约后商户号才激活。

---

### 阶段二　交易支付（甲方付款，钱进乙方并冻结）

```
甲方        小程序            服务端                微信支付
 │            │                 │                     │
 │ 选乙方下单 →│                 │                     │
 │            │ 建订单(乙方ID) ─→│                     │
 │            │                 │ 查乙方sub_mchid      │
 │            │                 │ JSAPI下单           │
 │            │                 │  (sub_mchid +        │
 │            │                 │   profit_sharing=true)→ 生成prepay_id
 │            │                 │ ←── 支付参数 ────────│
 │            │ ←── 支付参数 ────│                     │
 │ ←调起支付──│                 │                     │
 │ 输密码付款 ───────────────────────────────────────→ 钱进乙方[冻结]
 │            │                 │ ←── 支付成功通知 ────│
 ▼            ▼                 ▼                     ▼
                    订单已支付，资金冻结待分
```

**各方做什么**
- **小程序**：把"选了哪个乙方/订单"传给服务端；拿到支付参数后 `wx.requestPayment` **调起付款**。仅此而已。
- **服务端**：按乙方 ID 查出 `sub_mchid`；调 JSAPI 下单，**务必带 `profit_sharing=true`**（否则钱不冻结、事后无法分）；接收支付成功通知。
- **微信**：收单，把钱冻结在乙方特约商户号。

> ⚠️ 第一坑：下单**忘打 `profit_sharing=true`** → 钱直接结算给乙方，平台再也分不到 3%。

---

### 阶段三　验收与分账（平台抽 3%、剩余给乙方）

```
甲方       小程序        服务端                微信支付         乙方
 │           │             │                     │              │
 │ 点"验收通过"→│ ──────────→│                     │              │
 │           │             │ 请求分账(300→平台) ─→│ 分300给平台   │
 │           │             │ 查询分账结果 ────────→│              │
 │           │             │ ←── 分账成功 ────────│              │
 │           │             │ 解冻剩余资金 ────────→│ 9700结算给乙方→│
 │           │             │                     │              │ 可提现
 ▼           ▼             ▼                     ▼              ▼
                 平台得300，乙方得9700
```

**各方做什么**
- **平台运营**：定义验收规则（什么算"通过"）。
- **小程序**：把甲方的"验收通过"动作传给服务端。
- **服务端**：调**请求分账**（分 300 给平台接收方）→**查询分账结果**→调**解冻剩余资金**（9700 结算给乙方）。
- **乙方**：到账后自行提现到银行卡。

---

### 阶段四　退款 / 回退（出问题时）

```
服务端                         微信支付            乙方/平台
  │                              │                  │
  │ 已分账? ──是──→ 分账回退 ────→│ 从乙方/平台追回   │
  │              │               │                  │
  │ 申请退款 ─────────────────────→│ 原路退甲方        │
  ▼                              ▼                  ▼
              资金退回甲方
```

**服务端做什么**：若该单已分账，**先调"分账回退"**把已分出的钱追回，**再调退款**原路退给甲方。

## 4. 服务端要建的数据 / 接口

### 4.1 核心映射表（一一对应的锚点）

| 字段 | 含义 |
|---|---|
| `userId` | 乙方在平台的账号（主键、反查锚点）|
| `out_request_no` | 进件时自定义的业务申请号，绑定 userId |
| `applyment_id` | 微信返回的申请单号，查审核状态 |
| `sub_mchid` | 审核通过返回的特约商户号 |
| `status` | 进件中 / 已通过 / 已签约 / 已激活 |

### 4.2 要对接的微信 API

| 阶段 | API |
|---|---|
| 进件 | 特约商户进件 / 查询申请状态 / 开户意愿确认 |
| 绑定 | 添加分账接收方 / 查询最大分账比例 |
| 交易 | JSAPI 下单（带分账标记）/ 支付结果通知 |
| 分账 | 请求分账 / 查询分账结果 / 解冻剩余资金 / 分账回退 / 查询剩余待分金额 |
| 对账 | 资金账单 / 分账账单 |

## 5. 各方 Checklist

**平台运营 ☑**
- [ ] 公司主体 + 微信支付服务商 + ICP/EDI
- [ ] 乙方进件材料收集流程（执照/身份证/卡）
- [ ] 乙方签约催办机制
- [ ] 验收规则定义 + 乙方话术（引导办个体户）

**服务端 ☑**
- [ ] 进件 API + 轮询审核 + 落库 `sub_mchid`
- [ ] "乙方↔`sub_mchid`"映射表
- [ ] 绑定平台为分账接收方
- [ ] 下单**带 `profit_sharing=true`**
- [ ] 请求分账 / 查询 / 解冻
- [ ] 分账回退 + 退款
- [ ] 对账任务

**小程序 ☑**
- [ ] 下单时传乙方/订单标识给服务端
- [ ] 拿支付参数调起 `wx.requestPayment`
- [ ] 验收通过动作回传服务端
- （不碰 `sub_mchid`、不决定分账）

**收款方乙方 ☑**
- [ ] 提供进件资料（建议办个体工商户）
- [ ] 法人扫码完成开户意愿确认 + 签约
- [ ] 到账后提现

## 6. 五个最容易踩的坑

| # | 坑 | 后果 | 防 |
|---|---|---|---|
| 1 | 下单没打 `profit_sharing=true` | 钱不冻结，**分不了** | 下单强制带标记 |
| 2 | 进件过了但乙方没签约 | 商户号没激活，分账失败 | 签约完成才置"可用" |
| 3 | `sub_mchid` 放到小程序前端 | 可被篡改盗用 | 只存服务端 |
| 4 | 分账后未及时解冻 | 超账期自动解冻给乙方 | 分账成功即解冻 |
| 5 | 退款没先做分账回退 | 钱已分出，退款失败/亏空 | 先回退再退款 |
