# 飞书免费版实现方案

## 目标

用飞书免费版先跑通一个简单业务闭环：

- 群里派发任务
- 群里收集反馈
- 反馈自动写入表格
- 输出简单报表

## 适用范围

适合：

- 内部员工使用
- 任务流程不复杂
- 先验证流程可行性
- 报表以简单统计和视图为主

不适合：

- 外部客户参与
- 复杂审批链
- 高并发生产系统
- 强审计和复杂权限治理

## 一句话方案

飞书群 + 飞书机器人/应用 + 消息监听 + 多维表格

## 最小架构

```text
飞书群
  ↓
机器人发任务消息
  ↓
员工在群里回复反馈
  ↓
飞书消息事件监听
  ↓
解析任务编号和状态
  ↓
写入多维表格
  ↓
表格视图/统计报表
```

## 具体实现

## 1. 群里派发任务

做法：

- 建一个任务群或班组群
- 由机器人发送任务消息

建议消息格式：

```text
#派单
任务号：T20260507-001
类型：上门检修
地址：XX小区3栋
要求：今天18:00前完成
```

目的：

- 让后续反馈能和任务号绑定
- 减少自由表达导致的解析困难

## 2. 群里收集反馈

做法：

- 员工直接在群里按固定格式回复

建议反馈格式：

```text
#反馈 T20260507-001 已接单
#反馈 T20260507-001 已到场
#反馈 T20260507-001 已完工
#反馈 T20260507-001 异常 客户不在
```

不要一开始就追求自然语言识别。

先把格式约束住，系统会稳很多。

## 3. 监听群消息

做法：

- 创建飞书自建应用/机器人
- 把机器人拉进群
- 订阅群消息事件
- 接收用户在群里的反馈消息

核心作用：

- 把群消息送到你的服务端
- 服务端识别是不是反馈消息

## 4. 解析反馈

服务端做最简单规则解析：

- 提取任务号
- 提取状态
- 提取异常说明
- 记录发送人
- 记录时间

第一版不要上 AI，先走规则解析就够。

## 5. 写入多维表格

建议建一张任务台账表。

字段建议：

| 字段 | 说明 |
| --- | --- |
| 任务号 | 主键 |
| 派发时间 | 任务创建时间 |
| 任务类型 | 检修/安装/巡检等 |
| 地址 | 任务地点 |
| 负责人 | 电工姓名 |
| 当前状态 | 已接单/已到场/已完工/异常 |
| 最新反馈时间 | 最近一次反馈时间 |
| 异常类型 | 如有异常则记录 |
| 异常说明 | 文字说明 |
| 完工时间 | 完工时填写 |

## 6. 出简单报表

直接用多维表格先出轻量报表：

- 今日任务数
- 已完工数
- 未完工数
- 异常任务数
- 每个电工完成数

第一版不需要独立 BI。

直接靠：

- 视图筛选
- 分组统计
- 简单图表

就够用了。

## 推荐流程

1. 调度员在群里发任务
2. 机器人同步记录任务
3. 电工按固定格式回复反馈
4. 服务端监听消息并解析
5. 自动更新多维表格
6. 管理者在表格里看状态和简单统计

## 最小开发内容

你真正要做的只有 4 块：

1. 飞书机器人/应用配置
2. 群消息监听接口
3. 反馈解析逻辑
4. 写入多维表格逻辑

## 人日估算

按 MVP 算：

- `24-46 人日`

如果只是超轻量版本，甚至可以再低一点，但那会比较依赖手工配置和流程约束。

## 月成本理解

如果你只是先做内部验证：

- 飞书免费版本体：`0`
- 主要成本是研发
- 如果研发按 12 个月摊销：
  - `约 4000 - 11500 元 / 月`

如果你们已经有后端服务基础，边际成本还可以更低。

## 优点

- 起步快
- 免费版可先验证
- 群、消息、表格都在飞书里
- 不需要先开发完整后台

## 风险

- 免费版更适合内部试点，不适合长期复杂生产
- 反馈格式如果不统一，数据质量会下降
- 复杂流程最终还是要升级到更完整方案

## 推荐结论

对于你现在这个“简单业务、收集反馈、出报表”的需求：

- `飞书免费版值得先做`

最合理的做法不是一上来做重系统，而是先用免费版把流程跑通，再决定要不要升级。
